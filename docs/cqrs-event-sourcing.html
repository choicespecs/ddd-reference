    Architecture

    CQRS & event sourcing

    Two patterns that often appear alongside DDD. Both are optional, both are powerful in the right place, and both add real complexity in the wrong one.

    CQRS

    Command Query Responsibility Segregation
    Use one model to change state (the write side: aggregates enforcing invariants) and a different model to read it (the read side: views shaped for screens and reports).

    The motivation is that aggregates are designed for consistency, not for display. A seat map screen wants data from the seating aggregate, price tiers and the venue plan in one fast query. Loading three aggregates and mapping them in memory is slow and awkward. CQRS says: don't force it. Build a read model for that screen.

    flowchart LR
  UI["UI / API"] -- "commands" --> W["Write side<br/>Application service → Aggregates"]
  W --> WDB[("Write store")]
  W -- "domain events" --> P["Projector"]
  P --> RDB[("Read store<br/>seat_map_view")]
  UI -- "queries" --> Q["Query service"] --> RDB

    Levels of CQRS

    LevelWhat changesWhen it's enough
    1. Separate query codeQueries use plain SQL or views and return DTOs; commands use aggregates. Same databaseMost systems. Start here; it's nearly free
    2. Separate read tablesProjectors update denormalised tables from events, in the same databaseExpensive screens; complex search
    3. Separate read storesRead models in a different technology (search index, cache, document DB)Very different read/write scale; full-text search
    Java
    // Level 1: the query side skips the domain model entirely.
public class SeatMapQueries {
    private final Jdbc jdbc;
    public SeatMapView seatMap(EventId event) {
        return jdbc.query("""
            select s.seat_id, s.section, s.row_label, s.status, t.name as tier, t.price
            from seat_allocation s join price_tier t on t.id = s.tier_id
            where s.event_id = ?""", event.value()).as(SeatMapView::from);
    }
}
    Costs

    Levels 2 and 3 bring eventual consistency to your own UI. A buyer holds a seat, and for a moment the seat map still shows it as available. Handle it with optimistic UI updates, by reading your own writes from the write side, or by explaining the delay in the UI.

    Event sourcing

    Event sourcing
    Instead of storing an aggregate's current state, store the full sequence of domain events that happened to it. Current state is rebuilt by replaying those events.
    Java
    public class Hold {
    private HoldStatus status;
    private Instant expiresAt;

    // Decide: validate the command, return new events. No state change here.
    public List<HoldEvent> convertToOrder(PaymentRef payment, Instant now) {
        if (status != ACTIVE)          throw new HoldNotActive(id, status);
        if (now.isAfter(expiresAt))    throw new HoldAlreadyExpired(id);
        return List.of(new HoldConverted(id, payment, now));
    }

    // Evolve: apply an event to state. Must never fail; the event already happened.
    void apply(HoldEvent e) {
        switch (e) {
            case HoldPlaced p    -> { status = ACTIVE; expiresAt = p.expiresAt(); }
            case HoldConverted c -> status = CONVERTED;
            case HoldExpired x   -> status = EXPIRED;
        }
    }

    static Hold rehydrate(List<HoldEvent> history) {
        Hold h = new Hold(); history.forEach(h::apply); return h;
    }
}

    Benefits

    • Complete audit trail for free, which matters in finance, compliance and disputes.
    • Temporal queries: "what did this order look like on 3 March?"
    • New read models from history: build a projection you didn't think of at launch and replay every past event into it.
    • Events are first-class, so integration and debugging get easier.

    Costs

    • Schema evolution: you keep events forever, so you need upcasters or versioning for old shapes.
    • Read side required: you can't query "all active holds" from an event stream, so you need CQRS projections.
    • Long streams need snapshots.
    • Unfamiliar to most teams; tooling and operations are less mature than for plain databases.
    • Hard to undo. Moving away from event sourcing later is painful.

    When to use which

    SituationRecommendation
    Any DDD codebaseCQRS level 1: keep queries out of aggregates. Almost always worth it
    Heavy, varied read screensCQRS level 2 projections
    Audit/history is a core business needConsider event sourcing for that context
    Supporting or generic contextNeither; plain CRUD
    "Event sourcing everything" across the systemDon't. Choose it per context, deliberately

    Event sourcing and DDD fit together naturally because domain events are already in your model, but neither requires the other. Most DDD systems store current state, and that's fine.
