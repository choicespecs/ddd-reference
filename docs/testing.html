    Testing

    In a DDD codebase the business rules live in plain Java objects, so most of your tests can be fast, Spring-free unit tests. Here is the full test strategy.

    The shape of the test suite

    flowchart TB
  E2E["E2E (Playwright)<br/>a handful of critical journeys"]
  INT["Integration (@SpringBootTest + Testcontainers)<br/>wiring, transactions, SQL, events"]
  SLICE["Slices (@WebMvcTest, @DataJpaTest)<br/>one adapter at a time"]
  APP["Application service tests<br/>with in-memory fakes"]
  DOM["Domain unit tests<br/>pure JUnit — the majority"]
  E2E --- INT --- SLICE --- APP --- DOM
    LevelTests whatSpeedIn template
    Domain unitInvariants, state transitions, value objects, events raised~1 ms eachOrderTest

    cd backend

    Domain unit tests

    No Spring, no mocks, no database. Build the aggregate, call a method, and assert on the state and the events raised:

    Java
    class OrderTest {
    private final Clock clock = Clock.fixed(Instant.parse("2026-01-01T10:00:00Z"), ZoneOffset.UTC);

    @Test
    void placing_changes_status_and_raises_event() {
        Order order = Order.startDraft(new CustomerEmail("ada@example.com"), clock);
        order.addLine(book, "DDD", Money.of("50.00", "USD"), 2);

        order.place(clock);

        assertThat(order.status()).isEqualTo(OrderStatus.PLACED);
        assertThat(order.placedAt()).isEqualTo(clock.instant());       // deterministic thanks to Clock
        assertThat(order.peekDomainEvents())
                .singleElement()
                .isInstanceOfSatisfying(OrderPlaced.class, e ->
                        assertThat(e.total()).isEqualTo(Money.of("100.00", "USD")));
    }

    @Test
    void placed_order_is_frozen() {
        …
        assertThatThrownBy(() -> order.addLine(mug, "Mug", Money.of("1.00", "USD"), 1))
                .isInstanceOf(DomainException.class)
                .hasMessageContaining("PLACED");
    }
}

    Tips:

    • Name tests as rules: shipped_order_cannot_be_cancelled. The test list then reads like a spec.
    • Inject time. Pass a Clock instead of calling Instant.now(), and you get deterministic assertions.
    • Group with @Nested by behaviour (Placing, Cancelling).
    • Use test data builders once construction gets noisy: anOrder().withLine(book, 2).placed().build().

    Value object tests

    Java
    class MoneyTest {
    @Test void normalizes_scale()        { assertThat(Money.of("5", "USD")).isEqualTo(Money.of("5.00", "USD")); }
    @Test void rejects_negative()        { assertThatThrownBy(() -> Money.of("-1", "USD")).isInstanceOf(DomainException.class); }
    @Test void rejects_unknown_currency(){ assertThatThrownBy(() -> Money.of("1", "XYZ")).isInstanceOf(IllegalArgumentException.class); }
    @Test void cannot_add_mixed_currency(){ assertThatThrownBy(() -> Money.of("1","USD").plus(Money.of("1","EUR"))).isInstanceOf(DomainException.class); }
}

    Application service tests with fakes

    Ports make this easy. Write a tiny in-memory implementation instead of mocking:

    Java
    class InMemoryOrderRepository implements OrderRepository {
    private final Map<OrderId, Order> store = new HashMap<>();
    public Optional<Order> findById(OrderId id) { return Optional.ofNullable(store.get(id)); }
    public List<Order> findRecent(int limit)    { return store.values().stream().limit(limit).toList(); }
    public Order save(Order o)                  { store.put(o.id(), o); return o; }
}

class OrderApplicationServiceTest {
    InMemoryOrderRepository orders = new InMemoryOrderRepository();
    ProductCatalog catalog = id -> Optional.of(new OrderableProduct(id, "DDD", Money.of("50", "USD"), true));
    List<Object> published = new ArrayList<>();
    OrderApplicationService service = new OrderApplicationService(
            orders, catalog, published::add, Clock.systemUTC());

    @Test
    void place_publishes_order_placed() {
        var view = service.startOrder(new Commands.StartOrder("ada@example.com"));
        service.addLine(new Commands.AddLine(view.id(), UUID.randomUUID(), 1));

        service.place(view.id());

        assertThat(published).hasAtLeastOneElementOfType(OrderPlaced.class);
    }
}

    published::add works because ApplicationEventPublisher is a functional interface. Fakes like this are easier to read and less brittle than chains of Mockito when(...) calls.

    Web slice: @WebMvcTest

    Java
    @WebMvcTest(OrderController.class)
@Import(GlobalExceptionHandler.class)
class OrderControllerTest {
    @Autowired MockMvc mvc;
    @MockBean OrderApplicationService orders;     // Spring Boot 3.4+: @MockitoBean

    @Test
    void domain_exception_becomes_409_problem() throws Exception {
        when(orders.place(any())).thenThrow(new DomainException("Cannot place an empty order"));

        mvc.perform(post("/api/orders/{id}/place", UUID.randomUUID()))
           .andExpect(status().isConflict())
           .andExpect(content().contentType("application/problem+json"))
           .andExpect(jsonPath("$.detail").value("Cannot place an empty order"));
    }

    @Test
    void rejects_quantity_over_99() throws Exception {
        mvc.perform(post("/api/orders/{id}/lines", UUID.randomUUID())
               .contentType(APPLICATION_JSON)
               .content("{\"productId\":\"" + UUID.randomUUID() + "\",\"quantity\":100}"))
           .andExpect(status().isBadRequest());
        verifyNoInteractions(orders);
    }
}

    JPA slice: @DataJpaTest

    This verifies that the mapping round-trips. It's especially valuable for embeddables, enums, and collections:

    Java
    @DataJpaTest
@Import(JpaOrderRepository.class)       // the adapter is package-private: put this test in the same package
class JpaOrderRepositoryTest {
    @Autowired OrderRepository orders;
    @Autowired TestEntityManager em;

    @Test
    void round_trips_aggregate_with_lines_and_money() {
        Order order = Order.startDraft(new CustomerEmail("a@b.co"), Clock.systemUTC());
        order.addLine(UUID.randomUUID(), "DDD", Money.of("54.99", "USD"), 2);
        orders.save(order);
        em.flush(); em.clear();                         // force a real reload from SQL

        Order loaded = orders.findById(order.id()).orElseThrow();
        assertThat(loaded.lines()).hasSize(1);
        assertThat(loaded.total()).isEqualTo(Money.of("109.98", "USD"));
    }
}

    Full integration tests

    OrderFlowIntegrationTest drives the real HTTP layer through MockMvc, against real Flyway migrations, and checks cross-context behaviour, for example:

    Java
    @Test
void overselling_rolls_back_the_whole_placement() throws Exception {
    String orderId = startOrder();
    addLine(orderId, STICKERS, 5);                 // only 2 in stock

    mvc.perform(post("/api/orders/{id}/place", orderId))
       .andExpect(status().isConflict())
       .andExpect(jsonPath("$.detail").value(containsString("Insufficient stock")));

    mvc.perform(get("/api/orders/{id}", orderId))
       .andExpect(jsonPath("$.status").value("DRAFT"));   // the order change was rolled back too
}

    Testcontainers: test against real PostgreSQL

    H2 is convenient, but it isn't PostgreSQL. For production fidelity, add Testcontainers. Spring Boot 3.1+ wires the connection for you with @ServiceConnection:

    XML
    <dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-testcontainers</artifactId>
  <scope>test</scope>
</dependency>
<dependency>
  <groupId>org.testcontainers</groupId>
  <artifactId>postgresql</artifactId>
  <scope>test</scope>
</dependency>
<dependency>
  <groupId>org.testcontainers</groupId>
  <artifactId>junit-jupiter</artifactId>
  <scope>test</scope>
</dependency>
    Java
    @TestConfiguration(proxyBeanMethods = false)
class PostgresTestConfig {
    @Bean @ServiceConnection
    PostgreSQLContainer<?> postgres() {
        return new PostgreSQLContainer<>("postgres:16-alpine");
    }
}

@SpringBootTest
@Import(PostgresTestConfig.class)
class OrderFlowPostgresTest { … }

    A bonus: SpringApplication.from(ShopApplication::main).with(PostgresTestConfig.class).run(args) in a test-scoped TestShopApplication gives you a dev mode that starts its own database.

    Test data isolation

    ApproachHowCaveat
    @Transactional on the testEvery test rolls backHides commit-time behaviour (AFTER_COMMIT listeners, flush errors). Don't use it for event tests.
    Self-restoring tests (template)Tests leave data as they found itDiscipline required
    Truncate in @BeforeEachJdbcTestUtils.deleteFromTables(jdbc, "ordering_order_line", "ordering_order")Remember to reseed reference data
    @DirtiesContextNew context per testSlow, and an in-memory DB with DB_CLOSE_DELAY=-1 survives anyway

    What not to test

    • Getters, records, and Spring Data derived queries with obvious names.
    • The framework itself (that @Transactional starts a transaction).
    • The same rule at four levels. Test it thoroughly in the domain test, and check once that the wiring works.
