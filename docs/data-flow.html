    DB to screen: the full data flow

    How rows in the database become things on the Vue page and back again. One click traced through all seven hops.

    The short answer

    Yes, the UI is "populated from the DB", but never directly. Vue never sees a table or an entity. It sees JSON shaped for the screen. Each layer in between changes the data's shape on purpose:

    flowchart TB
  A["SQL row<br/>ordering_order + ordering_order_line"] -->|"Hibernate maps rows → objects"| B["Order aggregate<br/>(JPA entity, rich behaviour)"]
  B -->|"Application service maps → read model"| C["OrderView<br/>(immutable, flat, no behaviour)"]
  C -->|"Jackson serializes"| D["JSON over HTTP<br/>{ id, status, lines[], total }"]
  D -->|"fetch() + TypeScript interface"| E["Order (TS type)<br/>in a Vue ref()"]
  E -->|"reactivity re-renders"| F["Table rows, badges, buttons"]
    ShapeLives inOptimized for
    Table rowsPostgreSQL / H2Storage, integrity constraints, queries
    Aggregate (Order)ordering.domainEnforcing business rules
    Read model (OrderView)ordering.applicationGiving the caller exactly what it needs
    JSONThe wireA stable contract between backend and frontend
    TS interface + reffrontend/src/api, viewsType-safe rendering and reactivity

    Read path: opening an order page

    The user navigates to /orders/7f3c…. Here is every hop.

    1. Vue route → view component

    TypeScript
    // frontend/src/router.ts
{ path: '/orders/:id', component: () => import('./features/ordering/OrderDetailView.vue'), props: true }
    Vue SFC
    <!-- frontend/src/features/ordering/OrderDetailView.vue -->
<script setup lang="ts">
const props = defineProps<{ id: string }>()
const order = ref<Order | null>(null)

onMounted(async () => {
  order.value = await orderingApi.get(props.id)   // ← triggers hop 2
})
</script>

    2. API module → HTTP

    TypeScript
    // frontend/src/api/ordering.ts
get: (id: string) => get<Order>(`/api/orders/${id}`)

    The request goes to http://localhost:5173/api/orders/…, and Vite's dev proxy forwards it to Spring Boot on :8080. In production the built Vue app is usually served from the same origin as the API, so the relative URL keeps working.

    3. Controller (web adapter)

    Java
    // ordering/web/OrderController.java
@GetMapping("/{id}")
OrderView get(@PathVariable UUID id) {
    return orders.get(id);
}

    The controller's only job is to translate between HTTP and Java. It contains no logic.

    4. Application service opens a transaction

    Java
    // ordering/application/OrderApplicationService.java
@Transactional(readOnly = true)
public OrderView get(UUID orderId) {
    return OrderView.from(load(orderId));
}

    The readOnly = true lets Hibernate skip dirty checking, and some databases route read-only transactions to replicas. Note that OrderView.from(...) runs inside the transaction. Because of that, any lazy associations can still be loaded, and spring.jpa.open-in-view=false is safe.

    5. Repository → Hibernate → SQL

    Java
    // ordering/infrastructure/JpaOrderRepository.java  (implements domain port OrderRepository)
public Optional<Order> findById(OrderId id) {
    return jpa.findById(id.getValue());   // Spring Data → EntityManager.find(Order.class, uuid)
}
    SQL
    -- what Hibernate actually executes (set logging.level.org.hibernate.SQL=DEBUG to see it)
select o.id, o.created_at, o.customer_email, o.placed_at, o.status, o.version
  from ordering_order o where o.id = ?;
select l.order_id, l.id, l.product_id, l.product_name, l.quantity,
       l.unit_price_amount, l.unit_price_currency
  from ordering_order_line l where l.order_id = ? order by l.product_name;

    6. Rows → aggregate

    Hibernate instantiates Order through its protected no-arg constructor and sets the private fields reflectively. It builds the Money embeddable from unit_price_amount and unit_price_currency. No setters run and no validation runs. Hibernate is reconstituting an object that was valid when it was saved.

    7. Aggregate → read model → JSON → screen

    Java
    // ordering/application/OrderView.java
static OrderView from(Order o) {
    return new OrderView(o.getId().getValue(), o.getCustomerEmail().getValue(), o.getStatus().name(),
            o.getLines().stream().map(LineView::from).collect(Collectors.toList()),
            o.total().getAmount(), o.total().getCurrency(),     // total() is computed by the domain
            o.getCreatedAt(), o.getPlacedAt(), o.getVersion());
}
    JSON
    {
  "id": "7f3c0b9e-…",
  "customerEmail": "ada@example.com",
  "status": "DRAFT",
  "lines": [{ "productId": "1111…0001", "productName": "Domain-Driven Design",
              "unitPrice": 54.99, "quantity": 2, "lineTotal": 109.98 }],
  "total": 109.98,
  "currency": "USD",
  "createdAt": "2026-11-17T22:41:07.512Z",
  "placedAt": null,
  "version": 1
}

    Vue assigns the JSON to order.value, and the template re-renders. Note that the backend calculated total. The frontend never repeats business calculations, because if it did, the two copies of the rule would eventually disagree.

    Write path: clicking "Place order"

    sequenceDiagram
  autonumber
  participant V as Vue (OrderDetailView)
  participant C as OrderController
  participant S as OrderApplicationService
  participant R as OrderRepository
  participant O as Order (aggregate)
  participant T as IntegrationEventTranslator
  participant H as Catalog StockReservationHandler
  participant DB as Database
  V->>C: POST /api/orders/{id}/place
  C->>S: place(id)
  Note over S: @Transactional begins
  S->>R: findById(id)
  R->>DB: SELECT order + lines
  S->>O: place(clock)
  O->>O: check DRAFT & non-empty<br/>status = PLACED<br/>register OrderPlaced
  S->>R: save(order)
  S->>T: publish OrderPlaced (sync)
  T->>H: publish OrderPlacedIntegrationEvent (sync)
  H->>DB: SELECT product, then product.reserve(qty)
  alt enough stock
    Note over S: commit → UPDATE order, UPDATE products
    S-->>C: OrderView (status PLACED)
    C-->>V: 200 JSON
  else insufficient stock
    H-->>S: DomainException
    Note over S: rollback — order stays DRAFT
    C-->>V: 409 application/problem+json
  end

    The important properties:

    • The rule lives in one place. Order.place() decides whether placing is legal. The Vue button is only a hint, and it can be shown or hidden based on status.
    • One transaction per command. Either everything (the order status and the stock of every product) commits, or nothing does.
    • No explicit UPDATE. Hibernate's dirty checking compares the loaded state to the current state when the transaction commits, and writes only the columns that changed. It also increments version for optimistic locking.
    • The response is the new state. The controller returns the updated OrderView, so Vue swaps its copy without making another GET request.

    How errors reach the screen

    Java
    // Domain throws a plain exception, knowing nothing about HTTP
throw new DomainException("Cannot place an empty order");
    Java
    // config/GlobalExceptionHandler.java maps it to RFC 7807/9457 problem+json (body class: ApiProblem)
@ExceptionHandler(DomainException.class)
ResponseEntity<Object> ruleViolated(DomainException ex, WebRequest request) {
    return ApiProblem.of(HttpStatus.CONFLICT, "business-rule", "Business rule violated",
            ex.getMessage(), path(request)).toResponse();
}
    HTTP
    HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{"type":"https://example.com/problems/business-rule","title":"Business rule violated",
 "status":409,"detail":"Cannot place an empty order","instance":"/api/orders/…/place"}
    TypeScript
    // frontend/src/api/http.ts turns it into ApiError; useAsync exposes error.value
if (!res.ok) throw new ApiError(await res.json())

    The message the user sees is the same one written in the domain class. That way the ubiquitous language reaches the UI too.

    Why not return the entity directly?

    Spring would happily serialize Order to JSON. Don't let it. Here's why:

    Returning entities

    • The API contract changes whenever the domain model changes.
    • Lazy collections throw LazyInitializationException during serialization, or trigger surprise queries.
    • Bidirectional relations cause infinite recursion.
    • Internal fields leak out (version, flags).
    • Tempts you to accept entities in @RequestBody, which is mass assignment.

    Returning read models

    • The domain can be refactored freely.
    • The shape is designed for the screen (computed totals, flattened names).
    • All loading happens inside the transaction, so there are no lazy surprises.
    • Easy to generate TypeScript types from them via OpenAPI.
    • Request DTOs whitelist exactly what clients may send.

    Where does the initial data come from?

    The products you see on first run are inserted by a Flyway migration, backend/src/main/resources/db/migration/V2__seed_catalog.sql. Flyway runs every migration the database hasn't seen yet when the app starts. Hibernate is set to ddl-auto: validate, so it only checks that the entity mappings match the schema that Flyway created. Data you create through the UI is written by the normal path described above. With H2 it disappears on restart. With the postgres profile it persists in the Docker volume.
