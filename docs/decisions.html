    Decisions

    Design decisions (ADR log)

    Every significant choice in the template, written as a lightweight Architecture Decision Record, with the alternatives and the signal that should make you revisit it.

    How to use this page

    An Architecture Decision Record captures one decision: the context, the options, the choice, and its consequences. When you start your own app, copy this page, keep the decisions you agree with, and rewrite the others. That gives your team a record of why things are the way they are, which is the first thing new joiners (and future you) will ask.

    ADR template:

    Text
    ## ADR-NNN: <title>
Status:       Proposed | Accepted | Superseded by ADR-MMM
Context:      What forces are at play? What problem are we solving?
Options:      A, B, C — with pros/cons
Decision:     We chose B.
Consequences: What gets easier, what gets harder, what we must now do.
Revisit when: The concrete signal that would change this decision.

    Platform

    ADR-001: Java 17 + Spring Boot 3.3 Accepted

    Context
    The project must be Java. We need a mature web/DI/transaction framework with strong JPA support and hiring familiarity.
    Options
    Spring Boot (ecosystem, docs, Spring Data, Security), Quarkus (fast startup, native images), Micronaut (compile-time DI), Jakarta EE server.
    Decision
    Spring Boot 3.x on Java 17 (LTS, records, sealed types, pattern matching for instanceof).
    Consequences
    Records for VOs, commands, and views. Jakarta namespaces (jakarta.persistence).
    Revisit when
    Java 21 is available in your runtime: upgrade for virtual threads (spring.threads.virtual.enabled=true), switch pattern matching, and sequenced collections. Changing java.version in the pom is all it takes.

    ADR-002: Maven (with wrapper) Accepted

    Options
    Maven: declarative, ubiquitous in enterprise Java. Gradle (Kotlin DSL): faster incremental builds, more flexible, steeper learning curve.
    Decision
    Maven with ./mvnw, so everyone uses the same Maven version.
    Revisit when
    You move to many modules with slow builds, or your organization standardizes on Gradle.

    ADR-003: Monorepo with backend/ and frontend/ Accepted

    Options
    One repo (atomic changes across API and UI, one PR) or two repos (independent release cycles and permissions).
    Decision
    One repo. Most features touch both sides, and reviewing them together catches contract drift.
    Revisit when
    Separate teams own the frontend and backend with separate release trains.

    Architecture

    ADR-004: Modular monolith, not microservices Accepted

    Context
    A new system with an unproven domain model. Boundaries will move as we learn.
    Options
    Microservices per context; modular monolith; unstructured monolith.
    Decision
    One deployable, with each bounded context as a top-level package that has strict, tested boundaries. Tables are prefixed per context, with no cross-context foreign keys.
    Consequences
    Cheap refactoring of boundaries, local transactions, simple ops. Contexts can't be scaled or deployed independently.
    Revisit when
    A context needs independent deployment cadence or scaling, or a separate team owns it.

    ADR-005: Hexagonal layers inside each context Accepted

    Options
    Classic layered; hexagonal (ports & adapters); full clean architecture with use-case classes and presenters.
    Decision
    domain / application / infrastructure / web per context, with dependencies pointing inward.
    Consequences
    The domain is unit-testable without Spring. There are a few more files than in a layered app (port + adapter per repository).
    Revisit when
    A context is pure CRUD: collapse it to a flat package (see Project structure).

    ADR-006: Enforce boundaries with ArchUnit (not Spring Modulith, not Maven modules) Accepted

    Options
    ArchUnit: explicit rules, any structure. Spring Modulith: convention-based module verification, plus an event registry, docs generation, and module tests. Maven modules: compiler-enforced.
    Decision
    ArchUnit. The rules are visible and teachable, and they cover layer rules inside a context, which Modulith doesn't do by default.
    Revisit when
    You need the outbox (Event Publication Registry) or generated module docs: add Spring Modulith (it can coexist with ArchUnit). Move to Maven modules when the team is too big to police by review.

    ADR-007: Application service per aggregate, no inbound port interfaces Accepted

    Options
    An interface plus an implementation per use case (strict hexagonal/clean), or one concrete service class per aggregate.
    Decision
    Concrete OrderApplicationService. Its public methods are the inbound port. An interface with exactly one implementation adds indirection without benefit.
    Revisit when
    A service exceeds about 15 methods, or several driving adapters need different subsets.

    ADR-008: Cross-context communication via ACL (queries) + integration events (reactions) Accepted

    Context
    Ordering needs Catalog data (price, name). Catalog must react to orders (stock). Direct calls both ways would create a cycle.
    Decision
    Ordering → Catalog: synchronous queries through Ordering's ProductCatalog port, implemented by the CatalogAdapter ACL. Catalog ← Ordering: integration events in a neutral integration package.
    Consequences
    No cycles. Catalog doesn't know Ordering exists. The seams are ready for a microservice split.

    Domain model

    ADR-009: JPA annotations directly on domain classes Accepted

    Options
    (A) Annotate domain classes. (B) Separate JPA entities plus mappers in infrastructure.
    Decision
    A, with discipline: field access, a protected no-arg constructor, no setters, embeddables for VOs, ID references across aggregates.
    Consequences
    Half the persistence code. The domain carries jakarta.persistence imports, which ArchUnit allows explicitly. Some constraints remain (non-final fields).
    Revisit when
    The schema is legacy or very different from the model, or you need multiple storage technologies. See Option B.

    ADR-010: UUIDs generated in the domain; typed ID records at the API Accepted

    Options
    DB sequences/identity (@GeneratedValue); UUID v4 assigned in the domain; UUID v7 (time-ordered); typed IDs as @EmbeddedId.
    Decision
    UUID v4 created by the factory method, stored as a UUID column, exposed as OrderId/ProductId records from accessors.
    Consequences
    Aggregates have identity before they're saved (good for events and tests). IDs are safe to expose in URLs (not guessable). Random UUIDs fragment B-tree indexes on very large tables.
    Revisit when
    Tables have tens of millions of rows: switch to UUID v7 (e.g. the uuid-creator library) for index locality.

    ADR-011: Domain repository interfaces + Spring Data adapters Accepted

    Options
    Domain interface extends JpaRepository directly (less code), or a narrow domain interface plus an adapter (more code, but a smaller API).
    Decision
    Narrow interface in domain, with a package-private Spring Data interface plus an adapter in infrastructure.
    Consequences
    The domain exposes only the operations it needs (no deleteAll), and in-memory fakes for tests are trivial. You write about 30 lines of adapter per aggregate.
    Revisit when
    The boilerplate annoys the team more than the leaky API worries it. Extending Repository<Order, UUID> (the empty marker interface) is a good middle ground.

    ADR-012: Synchronous in-transaction event handling for stock reservation Accepted

    Options
    Synchronous @EventListener (atomic); AFTER_COMMIT + outbox (eventual); direct call from Ordering to Catalog.
    Decision
    Synchronous. "Never oversell" is guaranteed by a single transaction, with no saga.
    Consequences
    Two aggregates are modified in one transaction (bending the "one aggregate per transaction" guideline). Both contexts must share a database.
    Revisit when
    Splitting contexts into services, or under high contention on popular products. Then move to an outbox plus a saga with PENDING_STOCK (see Events).

    ADR-013: Money as a BigDecimal + ISO currency value object Accepted

    Options
    double (never), long cents, BigDecimal + currency VO, JSR 354 (Moneta).
    Decision
    A custom Money record (scale 2, HALF_EVEN), stored as NUMERIC(19,2) plus a currency column.
    Revisit when
    You need currencies with 0 or 3 decimals (JPY, KWD) or currency conversion: use Currency.getDefaultFractionDigits() for the scale, or adopt Moneta.

    Data

    ADR-014: PostgreSQL in real environments; H2 for zero-setup local runs Accepted

    Decision
    H2 in PostgreSQL mode as the default profile, so ./mvnw spring-boot:run just works. A postgres profile plus Docker Compose for realistic development.
    Revisit when
    You start using Postgres-specific features (JSONB, SKIP LOCKED, partial indexes). Then drop H2 and use Testcontainers plus spring-boot-docker-compose.

    ADR-015: Flyway owns the schema; Hibernate validates Accepted

    Options
    Hibernate ddl-auto=update; Flyway; Liquibase.
    Decision
    Flyway with plain SQL and ddl-auto=validate.
    Revisit when
    You must support several database vendors from one changelog: Liquibase handles that better.

    API & frontend

    ADR-016: Task-based REST with ProblemDetail errors Accepted

    Options
    CRUD REST; task-based REST; GraphQL; gRPC.
    Decision
    REST with command sub-resources (/place, /cancel), read models as responses, and RFC 9457 errors. OpenAPI generated with springdoc.
    Revisit when
    Many different clients need very different shapes of the same data: consider GraphQL (Spring for GraphQL) for the read side.

    ADR-017: Vue 3 + TypeScript + Vite; feature folders per context; no global store yet Accepted

    Decision
    Composition API with <script setup>, vue-router with lazy routes, a fetch-based client, and local state with a useAsync composable.
    Revisit when
    State must be shared across routes (cart, user): add Pinia. Many screens cache the same server data: add TanStack Query. You need a component library: PrimeVue, Vuetify, or Quasar.

    ADR-018: Authentication deferred Proposed

    Context
    The template is for learning. Real apps need an IdP.
    Recommendation
    An OIDC provider (Keycloak/Entra/Okta), with Spring Boot as a backend-for-frontend using oauth2Login and a session cookie, or as a resource server with JWTs if the API serves multiple clients. See Security.

    Questions to answer for your app

    QuestionWhy it matters
    What is the core domain, the part worth modelling richly?Decides where to spend DDD effort and where CRUD is fine
    Which invariants must be immediately consistent?Decides aggregate boundaries and sync vs async events
    Will any context be owned by a different team?Decides module boundaries and whether a split is likely
    Is there an existing database or system you must integrate with?Calls for an ACL, and possibly a separate persistence model (Option B)
    Who are the users and what is the IdP?Decides the security setup (BFF vs JWT)
    Where will it run (Kubernetes, App Service, VM)?Decides packaging (JAR, image) and config strategy
    Audit or history requirements?Might call for event sourcing, Hibernate Envers, or an audit table fed by domain events
    Expected volume (rows per table, requests/s)?Decides ID type, read-model projections, and caching
