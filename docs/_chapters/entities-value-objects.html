--- title: Entities & value objects lede: Two kinds of domain object. An entity is defined by identity that lasts through change; a value object is defined entirely by its attributes. Getting this distinction right simplifies everything else. ---

The question to ask

For any concept, ask: "If two of these have identical attributes, are they the same thing?"

  • Two £45.00 amounts? Interchangeable, so it's a value object.
  • Two orders with identical lines? Still two different orders, so it's an entity.
  • Seat "Section B, Row 12, Seat F" at one venue? It depends on the context. In Planning, a seat's attributes are its identity (a value). In Sales, the seat's availability changes over time for a specific event, so availability is tracked by an entity.

Value objects

Value object
An immutable object with no identity, defined and compared only by its attributes. It validates itself on creation and carries the behaviour that belongs to the concept.

Properties

  • Immutable. You replace it rather than modify it: total = total.plus(fee).
  • Structural equality. Equal when all attributes are equal.
  • Self-validating. An invalid instance can't exist, so code that receives one never has to re-check it.
  • Behaviour-rich. Arithmetic, comparison, formatting and conversions live on the type, not in a MoneyUtils class.
  • Side-effect free. Methods return new values instead of changing state, so they're trivially safe to share and test.
```java public record Money(BigDecimal amount, Currency currency) { public Money { Objects.requireNonNull(amount); Objects.requireNonNull(currency); if (amount.scale() > currency.getDefaultFractionDigits()) throw new IllegalArgumentException("Too many decimal places for " + currency); if (amount.signum() < 0) throw new IllegalArgumentException("Money cannot be negative"); } public static Money of(String amount, String currency) { return new Money(new BigDecimal(amount), Currency.getInstance(currency)); } public Money plus(Money other) { requireSameCurrency(other); return new Money(amount.add(other.amount), currency); } public Money times(int quantity) { return new Money(amount.multiply(BigDecimal.valueOf(quantity)), currency); } private void requireSameCurrency(Money other) { if (!currency.equals(other.currency)) throw new CurrencyMismatch(this, other); } } ```

Curing primitive obsession

Using raw String, int and BigDecimal for domain concepts is called primitive obsession. It's the most common and cheapest thing to fix with DDD. Compare:

Primitives

```java void placeHold(String buyerId, String eventId, List seats, int limit) // which string is which? is limit validated? ```

Value objects

```java Hold placeHold(BuyerId buyer, EventId event, SeatSelection seats, PurchaseLimit limit) // can't swap arguments; each one is already valid ```

Good candidates in almost any domain: identifiers (OrderId), money, quantities with units, email addresses, date ranges, percentages, and codes with a format.

Value objects can hold rules

A value object can encapsulate a rule about a group of values. That turns scattered checks into one tested type:

```java public record SeatSelection(Set seats) { public SeatSelection { if (seats.isEmpty()) throw new IllegalArgumentException("Select at least one seat"); seats = Set.copyOf(seats); // defensive, immutable copy } public int count() { return seats.size(); } } public record PurchaseLimit(int max) { public PurchaseLimit { if (max < 1) throw new IllegalArgumentException("limit must be ≥ 1"); } public void check(int alreadyOwned, SeatSelection requested) { if (alreadyOwned + requested.count() > max) throw new PurchaseLimitExceeded(max, alreadyOwned, requested.count()); } } ```

Entities

Entity
An object with a distinct identity that stays the same through changes to its attributes and across its lifecycle. Equality is by identity only.

Properties

  • Identity: assigned once and never changed. Prefer generating it in the domain (UUIDs or ULIDs) over relying on database sequences, so an entity has its id before it is saved.
  • Lifecycle: entities are created, change state through meaningful operations, and are often archived rather than deleted.
  • Behaviour, not setters: state changes go through methods named in the ubiquitous language, and those methods enforce the rules.
  • Equality by id: equals/hashCode use only the identifier.
```java public class Hold { private final HoldId id; private final BuyerId buyer; private final SeatSelection seats; private final Instant expiresAt; private HoldStatus status = HoldStatus.ACTIVE; // ✗ no setStatus(), no setExpiresAt() public void convertToOrder(PaymentRef payment, Instant now) { if (status != HoldStatus.ACTIVE) throw new HoldNotActive(id, status); if (now.isAfter(expiresAt)) throw new HoldAlreadyExpired(id); status = HoldStatus.CONVERTED; // … record event } public void expire(Instant now) { if (status == HoldStatus.ACTIVE && !now.isBefore(expiresAt)) status = HoldStatus.EXPIRED; } @Override public boolean equals(Object o) { return o instanceof Hold h && h.id.equals(id); } @Override public int hashCode() { return id.hashCode(); } } ```

Prefer value objects

Value objects are simpler to reason about, test and share. When in doubt, model a concept as a value and promote it to an entity only when you need to track it through change. A healthy domain model usually has more value objects than entities, and entities tend to be thin shells that coordinate rich values.

Make illegal states unrepresentable

Push rules into types so invalid combinations can't be expressed at all. Sealed types are a good tool for state that carries different data in different stages:

```java public sealed interface HoldOutcome { record Converted(OrderId order, PaymentRef payment) implements HoldOutcome {} record Expired(Instant at) implements HoldOutcome {} record Cancelled(CancelReason reason) implements HoldOutcome {} } // No "status = CONVERTED but orderId == null" is possible. ```

A note on persistence

Some ORMs push you toward no-arg constructors and mutable fields. Common ways to keep the model clean anyway: map value objects as embedded or owned types, use field access with a protected constructor reserved for the ORM, or keep separate persistence models and map between them in the repository. Pick the least-invasive option your stack allows, and don't let the database schema dictate the domain design.
