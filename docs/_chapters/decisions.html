--- title: Design decisions (ADR log) lede: Every significant choice in the template, written as a lightweight Architecture Decision Record, with the alternatives and the signal that should make you revisit it. ---

How to use this page

An Architecture Decision Record captures one decision: the context, the options, the choice, and its consequences. When you start your own app, copy this page, keep the decisions you agree with, and rewrite the others. That gives your team a record of why things are the way they are, which is the first thing new joiners (and future you) will ask.

ADR template:

```text ## ADR-NNN: Status: Proposed | Accepted | Superseded by ADR-MMM Context: What forces are at play? What problem are we solving? Options: A, B, C — with pros/cons Decision: We chose B. Consequences: What gets easier, what gets harder, what we must now do. Revisit when: The concrete signal that would change this decision. ``` <h2 id="platform">Platform</h2> <div class="adr" id="adr-java"> <h3>ADR-001: Java 11 + Spring Boot 2.7 <span class="tag">Accepted</span></h3> <dl> <dt>Context</dt><dd>The project must be Java, and the target runtime is <strong>Java 11</strong>. We need a mature web/DI/transaction framework with strong JPA support and hiring familiarity.</dd> <dt>Options</dt><dd><strong>Spring Boot</strong> (ecosystem, docs, Spring Data, Security), <strong>Quarkus</strong> (fast startup, native images), <strong>Micronaut</strong> (compile-time DI), <strong>Jakarta EE</strong> server.</dd> <dt>Decision</dt><dd>Spring Boot <strong>2.7.18</strong>, the last release line that supports Java 11 (Spring Boot 3 requires Java 17). The pom sets <code>maven.compiler.release=11</code>, so the build rejects newer language features and APIs even when compiled on a newer JDK.</dd> <dt>Consequences</dt><dd> <ul> <li><code>javax.persistence</code> / <code>javax.validation</code> (not <code>jakarta.*</code>), Hibernate 5.6, Spring Framework 5.3, Spring Security 5.7, Flyway 8, springdoc 1.x.</li> <li>No records, switch expressions, text blocks or <code>Stream.toList()</code>. Immutable classes use Lombok <code>@Value</code> (<a href="#adr-lombok">ADR-019</a>); streams use <code>Collectors.toList()</code>.</li> <li>No built-in <code>ProblemDetail</code>: the template has its own <code>ApiProblem</code> with the same JSON.</li> <li><strong>Spring Boot 2.7's open-source support has ended</strong> (Nov 2023). No more free security patches; commercial support is available from Broadcom/VMware. Track this as technical debt.</li> </ul></dd> <dt>Revisit when</dt><dd>The runtime allows Java 17+ (do it as soon as possible). The upgrade path: <ol> <li>Set <code>java.version</code> to 17 and the Boot parent to 3.x.</li> <li>Rename <code>javax.persistence</code>/<code>javax.validation</code> → <code>jakarta.*</code>. OpenRewrite's <code>UpgradeSpringBoot_3_0</code> recipe automates most of it.</li> <li>Swap <code>springdoc-openapi-ui</code> for <code>springdoc-openapi-starter-webmvc-ui</code> 2.x; add <code>flyway-database-postgresql</code>.</li> <li>Optionally convert <code>@Value</code> classes to records, replace <code>ApiProblem</code> with Spring's <code>ProblemDetail</code>, and use <code>TIMESTAMPTZ</code> columns.</li> </ol></dd> </dl> </div> <div class="adr" id="adr-build"> <h3>ADR-002: Maven (with wrapper) <span class="tag">Accepted</span></h3> <dl> <dt>Options</dt><dd><strong>Maven</strong>: declarative, ubiquitous in enterprise Java. <strong>Gradle</strong> (Kotlin DSL): faster incremental builds, more flexible, steeper learning curve.</dd> <dt>Decision</dt><dd>Maven with <code>./mvnw</code>, so everyone uses the same Maven version.</dd> <dt>Revisit when</dt><dd>You move to many modules with slow builds, or your organization standardizes on Gradle.</dd> </dl> </div> <div class="adr" id="adr-monorepo"> <h3>ADR-003: Monorepo with backend/ and frontend/ <span class="tag">Accepted</span></h3> <dl> <dt>Options</dt><dd>One repo (atomic changes across API and UI, one PR) or two repos (independent release cycles and permissions).</dd> <dt>Decision</dt><dd>One repo. Most features touch both sides, and reviewing them together catches contract drift.</dd> <dt>Revisit when</dt><dd>Separate teams own the frontend and backend with separate release trains.</dd> </dl> </div> <h2 id="architecture">Architecture</h2> <div class="adr" id="adr-modular-monolith"> <h3>ADR-004: Modular monolith, not microservices <span class="tag">Accepted</span></h3> <dl> <dt>Context</dt><dd>A new system with an unproven domain model. Boundaries will move as we learn.</dd> <dt>Options</dt><dd>Microservices per context; modular monolith; unstructured monolith.</dd> <dt>Decision</dt><dd>One deployable, with each bounded context as a top-level package that has strict, tested boundaries. Tables are prefixed per context, with no cross-context foreign keys.</dd> <dt>Consequences</dt><dd>Cheap refactoring of boundaries, local transactions, simple ops. Contexts can't be scaled or deployed independently.</dd> <dt>Revisit when</dt><dd>A context needs independent deployment cadence or scaling, or a separate team owns it.</dd> </dl> </div> <div class="adr" id="adr-hexagonal"> <h3>ADR-005: Hexagonal layers inside each context <span class="tag">Accepted</span></h3> <dl> <dt>Options</dt><dd>Classic layered; hexagonal (ports & adapters); full clean architecture with use-case classes and presenters.</dd> <dt>Decision</dt><dd><code>domain</code> / <code>application</code> / <code>infrastructure</code> / <code>web</code> per context, with dependencies pointing inward.</dd> <dt>Consequences</dt><dd>The domain is unit-testable without Spring. There are a few more files than in a layered app (port + adapter per repository).</dd> <dt>Revisit when</dt><dd>A context is pure CRUD: collapse it to a flat package (see <a href="project-structure.html#flat-small">Project structure</a>).</dd> </dl> </div> <div class="adr" id="adr-boundaries"> <h3>ADR-006: Enforce boundaries with ArchUnit (not Spring Modulith, not Maven modules) <span class="tag">Accepted</span></h3> <dl> <dt>Options</dt><dd><strong>ArchUnit</strong>: explicit rules, any structure. <strong>Spring Modulith</strong>: convention-based module verification, plus an event registry, docs generation, and module tests. <strong>Maven modules</strong>: compiler-enforced.</dd> <dt>Decision</dt><dd>ArchUnit. The rules are visible and teachable, and they cover layer rules <em>inside</em> a context, which Modulith doesn't do by default.</dd> <dt>Revisit when</dt><dd>You need the outbox (Event Publication Registry) or generated module docs: add Spring Modulith (it can coexist with ArchUnit). Move to Maven modules when the team is too big to police by review.</dd> </dl> </div> <div class="adr" id="adr-use-case-interfaces"> <h3>ADR-007: Application service per aggregate, no inbound port interfaces <span class="tag">Accepted</span></h3> <dl> <dt>Options</dt><dd>An interface plus an implementation per use case (strict hexagonal/clean), or one concrete service class per aggregate.</dd> <dt>Decision</dt><dd>Concrete <code>OrderApplicationService</code>. Its public methods <em>are</em> the inbound port. An interface with exactly one implementation adds indirection without benefit.</dd> <dt>Revisit when</dt><dd>A service exceeds about 15 methods, or several driving adapters need different subsets.</dd> </dl> </div> <div class="adr" id="adr-cross-context"> <h3>ADR-008: Cross-context communication via ACL (queries) + integration events (reactions) <span class="tag">Accepted</span></h3> <dl> <dt>Context</dt><dd>Ordering needs Catalog data (price, name). Catalog must react to orders (stock). Direct calls both ways would create a cycle.</dd> <dt>Decision</dt><dd>Ordering → Catalog: synchronous queries through Ordering's <code>ProductCatalog</code> port, implemented by the <code>CatalogAdapter</code> ACL. Catalog ← Ordering: integration events in a neutral <code>integration</code> package.</dd> <dt>Consequences</dt><dd>No cycles. Catalog doesn't know Ordering exists. The seams are ready for a microservice split.</dd> </dl> </div> <h2 id="domain-model">Domain model</h2> <div class="adr" id="adr-persistence-model"> <h3>ADR-009: JPA annotations directly on domain classes <span class="tag">Accepted</span></h3> <dl> <dt>Options</dt><dd>(A) Annotate domain classes. (B) Separate JPA entities plus mappers in infrastructure.</dd> <dt>Decision</dt><dd>A, with discipline: field access, a protected no-arg constructor, no setters, embeddables for VOs, ID references across aggregates.</dd> <dt>Consequences</dt><dd>Half the persistence code. The domain carries <code>javax.persistence</code> imports, which ArchUnit allows explicitly. Some constraints remain (non-final fields).</dd> <dt>Revisit when</dt><dd>The schema is legacy or very different from the model, or you need multiple storage technologies. See <a href="persistence.html#option-b">Option B</a>.</dd> </dl> </div> <div class="adr" id="adr-ids"> <h3>ADR-010: UUIDs generated in the domain; typed ID classes at the API <span class="tag">Accepted</span></h3> <dl> <dt>Options</dt><dd>DB sequences/identity (<code>@GeneratedValue</code>); UUID v4 assigned in the domain; UUID v7 (time-ordered); typed IDs as <code>@EmbeddedId</code>.</dd> <dt>Decision</dt><dd>UUID v4 created by the factory method, stored as a <code>UUID</code> column, exposed as <code>OrderId</code>/<code>ProductId</code> value objects from getters.</dd> <dt>Consequences</dt><dd>Aggregates have identity before they're saved (good for events and tests). IDs are safe to expose in URLs (not guessable). Random UUIDs fragment B-tree indexes on very large tables.</dd> <dt>Revisit when</dt><dd>Tables have tens of millions of rows: switch to UUID v7 (e.g. the <code>uuid-creator</code> library) for index locality.</dd> </dl> </div> <div class="adr" id="adr-repositories"> <h3>ADR-011: Domain repository interfaces + Spring Data adapters <span class="tag">Accepted</span></h3> <dl> <dt>Options</dt><dd>Domain interface extends <code>JpaRepository</code> directly (less code), or a narrow domain interface plus an adapter (more code, but a smaller API).</dd> <dt>Decision</dt><dd>Narrow interface in <code>domain</code>, with a package-private Spring Data interface plus an adapter in <code>infrastructure</code>.</dd> <dt>Consequences</dt><dd>The domain exposes only the operations it needs (no <code>deleteAll</code>), and in-memory fakes for tests are trivial. You write about 30 lines of adapter per aggregate.</dd> <dt>Revisit when</dt><dd>The boilerplate annoys the team more than the leaky API worries it. Extending <code>Repository<Order, UUID></code> (the empty marker interface) is a good middle ground.</dd> </dl> </div> <div class="adr" id="adr-events"> <h3>ADR-012: Synchronous in-transaction event handling for stock reservation <span class="tag">Accepted</span></h3> <dl> <dt>Options</dt><dd>Synchronous <code>@EventListener</code> (atomic); <code>AFTER_COMMIT</code> + outbox (eventual); direct call from Ordering to Catalog.</dd> <dt>Decision</dt><dd>Synchronous. "Never oversell" is guaranteed by a single transaction, with no saga.</dd> <dt>Consequences</dt><dd>Two aggregates are modified in one transaction (bending the "one aggregate per transaction" guideline). Both contexts must share a database.</dd> <dt>Revisit when</dt><dd>Splitting contexts into services, or under high contention on popular products. Then move to an outbox plus a saga with <code>PENDING_STOCK</code> (see <a href="domain-events.html#eventual-consistency">Events</a>).</dd> </dl> </div> <div class="adr" id="adr-money"> <h3>ADR-013: Money as a BigDecimal + ISO currency value object <span class="tag">Accepted</span></h3> <dl> <dt>Options</dt><dd><code>double</code> (never), <code>long</code> cents, <code>BigDecimal</code> + currency VO, JSR 354 (Moneta).</dd> <dt>Decision</dt><dd>A custom <code>Money</code> embeddable value object (scale 2, HALF_EVEN), stored as <code>NUMERIC(19,2)</code> plus a currency column.</dd> <dt>Revisit when</dt><dd>You need currencies with 0 or 3 decimals (JPY, KWD) or currency conversion: use <code>Currency.getDefaultFractionDigits()</code> for the scale, or adopt Moneta.</dd> </dl> </div> <div class="adr" id="adr-lombok"> <h3>ADR-019: Lombok <code>@Value</code> for immutable value classes <span class="tag">Accepted</span></h3> <dl> <dt>Context</dt><dd>Java 11 has no records. The template has about 25 small immutable types: typed IDs, value objects, commands, views, events and request DTOs. Hand-writing constructors, getters, <code>equals</code>, <code>hashCode</code> and <code>toString</code> for each is about 40 lines of boilerplate apiece, and it's easy to get wrong when a field is added.</dd> <dt>Options</dt><dd>(A) Hand-written classes (IDE-generated). (B) Lombok <code>@Value</code>. (C) Immutables / AutoValue (annotation processors that generate separate implementation classes).</dd> <dt>Decision</dt><dd>Lombok <code>@Value</code>. Where validation is needed (IDs, <code>Sku</code>, <code>CustomerEmail</code>), write an explicit constructor and Lombok generates the rest. <code>backend/lombok.config</code> adds <code>@ConstructorProperties</code> so Jackson can deserialize request DTOs. JPA classes (<code>Money</code>, entities) stay hand-written, because Hibernate needs no-arg constructors and non-final fields.</dd> <dt>Consequences</dt><dd>It's compile-time only and absent from the runtime JAR and from bytecode references (ArchUnit's domain rule still passes). Accessors are JavaBean-style <code>getX()</code>. IDEs need the Lombok plugin (built into IntelliJ; VS Code's Java extension supports it).</dd> <dt>Revisit when</dt><dd>You move to Java 17: records replace almost all <code>@Value</code> classes.</dd> </dl> </div> <h2 id="data">Data</h2> <div class="adr" id="adr-db"> <h3>ADR-014: PostgreSQL in real environments; H2 for zero-setup local runs <span class="tag">Accepted</span></h3> <dl> <dt>Decision</dt><dd>H2 in PostgreSQL mode as the default profile, so <code>./mvnw spring-boot:run</code> just works. A <code>postgres</code> profile plus Docker Compose for realistic development.</dd> <dt>Revisit when</dt><dd>You start using Postgres-specific features (JSONB, <code>SKIP LOCKED</code>, partial indexes). Then drop H2 and use Testcontainers in tests and Docker Compose locally.</dd> </dl> </div> <div class="adr" id="adr-migrations"> <h3>ADR-015: Flyway owns the schema; Hibernate validates <span class="tag">Accepted</span></h3> <dl> <dt>Options</dt><dd>Hibernate <code>ddl-auto=update</code>; Flyway; Liquibase.</dd> <dt>Decision</dt><dd>Flyway with plain SQL and <code>ddl-auto=validate</code>.</dd> <dt>Revisit when</dt><dd>You must support several database vendors from one changelog: Liquibase handles that better.</dd> </dl> </div> <h2 id="api">API & frontend</h2> <div class="adr" id="adr-api-style"> <h3>ADR-016: Task-based REST with problem+json errors <span class="tag">Accepted</span></h3> <dl> <dt>Options</dt><dd>CRUD REST; task-based REST; GraphQL; gRPC.</dd> <dt>Decision</dt><dd>REST with command sub-resources (<code>/place</code>, <code>/cancel</code>), read models as responses, and RFC 7807/9457 problem+json errors (via <code>ApiProblem</code>). OpenAPI generated with springdoc 1.x.</dd> <dt>Revisit when</dt><dd>Many different clients need very different shapes of the same data: consider GraphQL (Spring for GraphQL) for the read side.</dd> </dl> </div> <div class="adr" id="adr-frontend"> <h3>ADR-017: Vue 3 + TypeScript + Vite; feature folders per context; no global store yet <span class="tag">Accepted</span></h3> <dl> <dt>Decision</dt><dd>Composition API with <code><script setup></code>, vue-router with lazy routes, a fetch-based client, and local state with a <code>useAsync</code> composable.</dd> <dt>Revisit when</dt><dd>State must be shared across routes (cart, user): add Pinia. Many screens cache the same server data: add TanStack Query. You need a component library: PrimeVue, Vuetify, or Quasar.</dd> </dl> </div> <div class="adr" id="adr-auth"> <h3>ADR-018: Authentication deferred <span class="tag">Proposed</span></h3> <dl> <dt>Context</dt><dd>The template is for learning. Real apps need an IdP.</dd> <dt>Recommendation</dt><dd>An OIDC provider (Keycloak/Entra/Okta), with Spring Boot as a backend-for-frontend using <code>oauth2Login</code> and a session cookie, or as a resource server with JWTs if the API serves multiple clients. See <a href="security-config-deploy.html">Security</a>.</dd> </dl> </div> <h2 id="open-questions">Questions to answer for <em>your</em> app</h2> <table> <thead><tr><th>Question</th><th>Why it matters</th></tr></thead> <tbody> <tr><td>What is the core domain, the part worth modelling richly?</td><td>Decides where to spend DDD effort and where CRUD is fine</td></tr> <tr><td>Which invariants must be <em>immediately</em> consistent?</td><td>Decides aggregate boundaries and sync vs async events</td></tr> <tr><td>Will any context be owned by a different team?</td><td>Decides module boundaries and whether a split is likely</td></tr> <tr><td>Is there an existing database or system you must integrate with?</td><td>Calls for an ACL, and possibly a separate persistence model (Option B)</td></tr> <tr><td>Who are the users and what is the IdP?</td><td>Decides the security setup (BFF vs JWT)</td></tr> <tr><td>Where will it run (Kubernetes, App Service, VM)?</td><td>Decides packaging (JAR, image) and config strategy</td></tr> <tr><td>Audit or history requirements?</td><td>Might call for event sourcing, Hibernate Envers, or an audit table fed by domain events</td></tr> <tr><td>Expected volume (rows per table, requests/s)?</td><td>Decides ID type, read-model projections, and caching</td></tr> </tbody> </table>
