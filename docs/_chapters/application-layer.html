What the application layer is for

An application service is a use-case script. It knows what to do in what order, but delegates how (the rules) to the domain. A good application service method is short enough that you can read it out loud to a domain expert:

```java public OrderView addLine(Commands.AddLine cmd) { Order order = load(cmd.getOrderId()); // 1. load OrderableProduct product = catalog.find(cmd.getProductId()) // 2. gather inputs .orElseThrow(() -> new NotFoundException("Product", cmd.getProductId())); if (!product.isAvailable()) throw new DomainException("… not available"); order.addLine(product.getProductId(), product.getName(), product.getPrice(), cmd.getQuantity()); // 3. one domain call return saveAndPublish(order); // 4. save, publish, return view } ```

The standard shape of a command method

```mermaid flowchart LR A[Command in] --> B[Load aggregate
or create via factory] B --> C[Call ONE behaviour method] C --> D[Save] D --> E[Publish pulled events] E --> F[Return read model] ```

The template factors steps D–F into one helper so they can't be forgotten:

```java private OrderView saveAndPublish(Order order) { Order saved = orders.save(order); order.pullDomainEvents().forEach(events::publishEvent); return OrderView.from(saved); } ```

Transactions

  • @Transactional on the class makes every public method a transaction. Override with @Transactional(readOnly = true) for queries.
  • One command = one transaction = (ideally) one aggregate.
  • Unchecked exceptions roll back. DomainException extends RuntimeException for this reason. Checked exceptions do not roll back by default.
  • Self-invocation bypasses the proxy. If place() calls this.reserve(), any @Transactional on reserve() is ignored, because Spring's proxy is never involved. Keep the transactional boundary at the public entry point.
  • No remote calls inside a transaction if you can avoid it. They hold a DB connection while waiting on the network. Gather remote data first, then open the transaction. Alternatively, call the remote system after commit, through events.
```java // Propagation cheat sheet @Transactional // REQUIRED (default): join existing or start new @Transactional(propagation = REQUIRES_NEW) // suspend caller's tx, run in a fresh one (audit logs) @Transactional(readOnly = true) // hint: no flush, can route to replica @Transactional(noRollbackFor = SomeException.class) @Transactional(timeout = 5) // seconds ```

Commands

A command is an immutable request to do something, named in the imperative. On Java 11, Lombok's @Value gives you an immutable class with a constructor, getters and equals in a few lines:

```java public final class Commands { @Value public static class StartOrder { String customerEmail; } @Value public static class AddLine { UUID orderId; UUID productId; int quantity; } @Value public static class ChangeQuantity { UUID orderId; UUID productId; int quantity; } @Value public static class RemoveLine { UUID orderId; UUID productId; } } // usage: new Commands.AddLine(orderId, productId, 2); cmd.getQuantity() ```

Why not pass the web request DTO straight through? Because the application layer may be called from places other than REST: a message listener, a scheduled job, a CLI, or a test. Commands belong to the application, while request DTOs belong to the HTTP contract. The two often look identical at first and drift apart later.

Commands carry primitive-ish types (UUID, String). The application service converts them into domain value objects (new CustomerEmail(cmd.getCustomerEmail())), and that is where format validation fires.

Read models (views)

```java @Value public class OrderView { UUID id; String customerEmail; String status; List lines; BigDecimal total; String currency; Instant createdAt; Instant placedAt; long version; static OrderView from(Order o) { … } } ```
  • Immutable (@Value), flat, with no behaviour. Jackson serializes the getters as-is (getCustomerEmail() → "customerEmail").
  • Shaped for consumers. For example, total is pre-computed and status is a string.
  • Built inside the transaction, so lazy associations can load.
  • The mapping is written by hand as a static factory. MapStruct is the alternative when there are dozens.

Outbound ports in the application layer

Where do interfaces like ProductCatalog go? A common rule is:

  • In domain, if the domain model itself needs it (repositories, or a domain service that needs an exchange rate source).
  • In application, if only orchestration needs it (other contexts, email senders, payment gateways).
```java // Typical outbound ports you'll add in a real app public interface PaymentGateway { PaymentResult authorize(OrderId order, Money amount, PaymentToken token); } public interface Notifier { void orderConfirmation(CustomerEmail to, OrderView order); } public interface CurrentUser { // wraps Spring Security so the app layer stays testable UserId id(); boolean hasRole(String role); } ```

One service per aggregate vs one class per use case

Service per aggregate (template)

```java @Service @Transactional public class OrderApplicationService { public OrderView startOrder(…) {} public OrderView addLine(…) {} public OrderView place(…) {} public OrderView cancel(…) {} } ```

Fewer files, and easy to find. It works well up to roughly 10–15 methods.

Class per use case

```java public interface PlaceOrder { OrderView handle(PlaceOrderCommand c); } @Service @Transactional class PlaceOrderHandler implements PlaceOrder { public OrderView handle(…) {} } ```

Each use case is isolated, with small constructors. It fits large contexts and command buses.

Start with service-per-aggregate. Split a service when it grows too large or when its constructor needs many collaborators that only some methods use.
