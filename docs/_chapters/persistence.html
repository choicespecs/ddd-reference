The big decision: JPA annotations on the domain model?

There are two schools of thought, and both are legitimate.

Option A: annotate the domain model directly (this template)

```java @Entity @Table(name = "ordering_order") public class Order extends AggregateRoot { @Id private UUID id; @Enumerated(EnumType.STRING) private OrderStatus status; @OneToMany(cascade = ALL, orphanRemoval = true) @JoinColumn(name = "order_id") private List lines = new ArrayList<>(); protected Order() {} // JPA needs it public void place(Clock clock) { … } // behaviour stays here } ```

Option B: separate persistence model + mapper

```java // ordering/domain/Order.java — pure Java, no annotations at all public final class Order { private final OrderId id; private OrderStatus status; private final List lines; public static Order reconstitute(OrderId id, OrderStatus s, List lines, long version) { … } public void place(Clock clock) { … } } // ordering/infrastructure/OrderEntity.java — JPA-only, anemic on purpose @Entity @Table(name = "ordering_order") class OrderEntity { @Id UUID id; String status; @OneToMany(cascade = ALL, orphanRemoval = true) @JoinColumn(name = "order_id") List lines; @Version long version; } // ordering/infrastructure/JpaOrderRepository.java public Order save(Order order) { OrderEntity entity = jpa.findById(order.id().value()).orElseGet(OrderEntity::new); mapper.copyInto(order, entity); // domain → entity return mapper.toDomain(jpa.save(entity)); } ```

Why the template picks A

JPA annotations are metadata: they don't change how the class behaves when you call it, and unit tests run without a database. The real danger with JPA isn't the annotations. It's public setters, bidirectional relationships, and lazy-loading surprises, and the rules below handle those. Option B is described in detail so you can switch if your project needs it. See ADR.

Mapping rules for DDD-friendly entities

  1. Field access, not property access. Put @Id on a field, and Hibernate will read and write fields directly, ignoring getters and setters. That means you don't need setters.
  2. Protected no-arg constructor for Hibernate, and a private or package-private "real" constructor called from a factory.
  3. Assign IDs in the domain. Use UUID.randomUUID() in the constructor, with no @GeneratedValue. The entity is complete before it's saved, and save() does a merge that first SELECTs to check whether the row exists. If that extra SELECT matters, implement Persistable<UUID> with an isNew() flag.
  4. Enums as STRING. @Enumerated(EnumType.STRING). Never use ORDINAL: reordering the enum would silently corrupt your data.
  5. Value objects as @Embeddable (records work in Hibernate 6.2+), or as an AttributeConverter for single-column VOs.
  6. Cross-aggregate references by ID: a plain UUID productId column, not @ManyToOne Product.
  7. Aggregate-internal collections: unidirectional @OneToMany with cascade = ALL, orphanRemoval = true, owned by the root.
  8. Optimistic locking on every root: a @Version field (in AggregateRoot here).

Value objects: @Embeddable vs AttributeConverter

```java // Multi-column VO → @Embeddable; rename columns per use with @AttributeOverride @Embeddable public record Money(@Column(name = "amount") BigDecimal amount, @Column(name = "currency") String currency) { … } @Embedded @AttributeOverrides({ @AttributeOverride(name = "amount", column = @Column(name = "unit_price_amount")), @AttributeOverride(name = "currency", column = @Column(name = "unit_price_currency")) }) private Money unitPrice; ``` ```java // Single-column VO → AttributeConverter; the entity field can then be the VO type itself @Converter(autoApply = true) public class SkuConverter implements AttributeConverter { public String convertToDatabaseColumn(Sku sku) { return sku == null ? null : sku.value(); } public Sku convertToEntityAttribute(String raw) { return raw == null ? null : new Sku(raw); } } @Column(nullable = false, unique = true) private Sku sku; // instead of String sku + conversion in the getter ```

The template stores String sku and converts in the accessor, which is simple and explicit. A converter is cleaner once you have many such fields. Note that Spring Data derived queries then take the VO: findBySku(Sku sku).

Typed IDs and JPA

Mapping OrderId as the @Id type is possible (@EmbeddedId with an @Embeddable record, or Hibernate's @JavaType), but it adds friction with Spring Data's generic JpaRepository<Order, OrderId> and with JPQL. The template stores a raw UUID and exposes OrderId from the accessor. You get type safety at the API, and the plumbing stays simple.

The N+1 problem

Loading 20 orders, then touching each order's lines, gives 1 query for the orders plus 20 queries for the lines. Three ways to fix it:

```yaml # 1. Batch fetching (set globally in application.yml — the template does this) spring.jpa.properties.hibernate.default_batch_fetch_size: 50 # → 1 query for orders + 1 query "where order_id in (?, ?, … 20 ids)" ``` ```java // 2. Fetch join for a specific query @Query("select distinct o from Order o left join fetch o.lines where o.status = :status") List findWithLinesByStatus(OrderStatus status); // 3. Entity graph @EntityGraph(attributePaths = "lines") List findAllByCustomerEmail(String email); ```
Fetch join + pagination

Combining join fetch on a collection with Pageable makes Hibernate paginate in memory, and it logs warning HHH90003004. For paged lists, prefer batch fetching (option 1) or a projection query that doesn't load aggregates at all (see CQRS).

Dirty checking: why there's no "update" call

```java public ProductView changePrice(UUID productId, BigDecimal amount, String currency) { Product product = load(productId); // managed entity, snapshot taken product.changePrice(new Money(amount, currency)); return ProductView.from(product); // no save() call! } // ← @Transactional commit: Hibernate diffs the snapshot → UPDATE catalog_product SET price_amount=?, version=? WHERE id=? AND version=? ```

Every entity loaded inside a transaction is managed, and changes are flushed automatically at commit. The template still calls repository.save() in OrderApplicationService. That is redundant for loaded entities, but it makes the intent explicit, and it is required for new ones and if you ever switch to Option B. Pick one convention and stick to it.

Optimistic locking

Two users open the same draft order. User A adds a line, and so does user B. Without locking, the last write wins and A's change silently disappears.

```java @MappedSuperclass public abstract class AggregateRoot { @Version private long version; // UPDATE … SET version = 6 WHERE id = ? AND version = 5 } ```

If the WHERE … version = 5 matches 0 rows, Hibernate throws OptimisticLockException. Spring wraps it as ObjectOptimisticLockingFailureException, and GlobalExceptionHandler maps that to 409 Conflict with "reload and try again". The version is also returned in OrderView. To catch conflicts across separate HTTP requests (where the user edited stale data), have the client send the version back, either in an If-Match header or in the body, and compare it before applying the command:

```java public OrderView addLine(AddLine cmd) { Order order = load(cmd.orderId()); if (cmd.expectedVersion() != null && cmd.expectedVersion() != order.version()) throw new ConcurrentModificationException("Order was changed by someone else"); … } ```

Schema management with Flyway

ddl-auto: update

  • Hibernate guesses the schema from the entities
  • Never drops or renames columns, and can't migrate data
  • Different databases end up with different schemas
  • No review, no history, no rollback plan

Flyway + ddl-auto: validate

  • The schema is versioned SQL, reviewed in PRs
  • Every environment runs the identical scripts
  • Data migrations sit next to schema changes
  • Hibernate validates the mapping at startup and fails fast
```text backend/src/main/resources/db/migration/ ├── V1__create_schema.sql ← applied once, then immutable ├── V2__seed_catalog.sql └── V3__add_order_notes.sql ← your next change goes here ``` ```sql -- V3__add_order_notes.sql — example of evolving the schema ALTER TABLE ordering_order ADD COLUMN notes VARCHAR(1000); ```

Rules: never edit an applied migration (Flyway checksums them and will refuse to start). Name files V<n>__description.sql with two underscores. For zero-downtime deploys, use expand/contract: add the new column, deploy code that writes both columns, backfill, deploy code that reads the new one, then drop the old one in a later migration.

Schema conventions in the template

  • Table prefix per context (catalog_, ordering_) so ownership is obvious and splitting is easy.
  • No foreign keys across contexts. ordering_order_line.product_id has no FK to catalog_product. Contexts must be able to live in separate databases one day.
  • FKs and CHECK constraints within a context as a second line of defence (stock_on_hand >= 0).
  • Money stored as NUMERIC(19,2) plus a currency code, never as FLOAT/DOUBLE.
  • Timestamps as TIMESTAMP WITH TIME ZONE, mapped to Instant.

Turn off open-in-view

Spring Boot enables spring.jpa.open-in-view by default. It keeps the Hibernate session open during view rendering and JSON serialization, so lazy loading "just works" in controllers. That hides N+1 queries and holds a DB connection for the whole request. The template sets it to false and builds read models inside the transactional application service.
