--- title: Rendering the UI lede: A generic renderer turns metadata plus an instance into forms, tables and buttons. You write it once, and it renders every domain object you'll ever add. ---

The pieces

PieceJob
Widget registryMaps a property's kind (and value type) to a widget component
ObjectViewOne page for any object: title, property form, collection tables, action bar
ListViewA table of objects of one type, with columns derived from the spec

Generic routes/objects/:type/:id and /list/:type, so new types need no new routes

Client-side types

These mirror the server's metamodel:

```ts export type ValueKind = 'STRING' | 'NUMBER' | 'BOOLEAN' | 'ENUM' | 'DATE' | 'DATETIME' | 'VALUE' | 'REFERENCE' export interface PropertySpec { id: string; label: string; kind: ValueKind; valueType?: string order: number; required: boolean; editable: boolean constraints: { minLength?: number; maxLength?: number; min?: number; max?: number; pattern?: string; enumValues?: string[] } } export interface ActionSpec { id: string; label: string; order: number; confirm?: string semantics: 'SAFE' | 'IDEMPOTENT' | 'NON_IDEMPOTENT'; parameters: PropertySpec[] } export interface ObjectSpec { type: string; label: string; plural: string; titleProperty: string properties: PropertySpec[]; collections: { id: string; label: string; elementType: string }[] actions: ActionSpec[] } export interface ObjectRep { type: string; id: string; title: string values: Record members: Record } ```

The widget registry

This is the one place where "type → UI" is decided. Value objects register their own widgets, and everything else falls back to a default by kind:

```ts import TextInput from './widgets/TextInput.vue' import NumberInput from './widgets/NumberInput.vue' // … Checkbox, Select, DateInput, DateTimeInput, RefLookup, MoneyInput const byValueType: Record = { Money: MoneyInput, // registered once; every Money everywhere uses it EmailAddress: EmailInput, } const byKind: Record = { STRING: TextInput, NUMBER: NumberInput, BOOLEAN: Checkbox, ENUM: Select, DATE: DateInput, DATETIME: DateTimeInput, REFERENCE: RefLookup, VALUE: TextInput, } export function widgetFor(p: PropertySpec): Component { return (p.valueType && byValueType[p.valueType]) || byKind[p.kind] } ```

ActionDialog

Action parameters are just PropertySpecs, so the dialog reuses the same widgets. If the action has no parameters, the dialog is skipped and the action is invoked straight away (after a confirm prompt, if the spec has one).

Generic routes

```ts const routes = [ { path: '/', component: Home }, // menu from GET /api/meta { path: '/list/:type', component: ListView, props: true }, { path: '/objects/:type/:id', component: ObjectView, props: true }, ] ```

When you add the Promotion class on the server, it appears in the menu, /list/Promotion works, and each promotion opens at /objects/Promotion/:id. No frontend change is needed.

Client-side validation from constraints

Widgets read spec.constraints to give instant feedback (maxlength, min, pattern, required markers). This is a convenience only. The server re-checks everything (see Rules). If you use the JSON Schema path, a standard validator such as Ajv can check a whole form against the schema in one call.

Off-the-shelf renderers

If you emit JSON Schema, you don't have to write the form renderer yourself. JSON Forms (React, Angular, Vue), react-jsonschema-form and Formily render schema-driven forms. You'd still build the object page, collection tables and action bar around them.
