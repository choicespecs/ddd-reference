Then update groupId/artifactId in pom.xml, rename ShopApplication, and change spring.application.name. Option 2: generate a fresh project at start.spring.io (Web, Validation, Data JPA, Flyway, PostgreSQL, H2, Actuator), then copy over sharedkernel, config, the ArchUnit test, and the package conventions.

Step 1: Learn the domain before writing code

  1. Talk to the domain experts. Ask them to walk you through a real case from start to finish. Write down every noun and verb they use.
  2. Run a mini Event Storming session (even one hour helps): list the domain events in time order, then add the commands, actors, and rules. See Event Storming.
  3. Start the glossary. Copy the glossary and replace the shop terms with yours.
  4. Mark hotspots, the places where people disagree or say "it depends". Those are where the complexity, and the value, sits.

Step 2: Draw the context map

Group the events and commands into 2–4 candidate bounded contexts. For each one, write a single sentence of responsibility and classify it (core, supporting, or generic). Then draw the arrows: who needs what from whom?

```mermaid flowchart LR subgraph Example["Example: an insurance claims app"] Policy["Policy
(supporting)"] Claims["Claims
(core)"] Payments["Payments
(generic → Stripe/bank API)"] Docs["Documents
(generic → S3/Blob)"] end Claims -- "ACL: is policy active? coverage limits" --> Policy Claims -- "ClaimApproved event" --> Payments Claims -- "port: store evidence" --> Docs ```

Turn each context into a top-level package with the four layer sub-packages, delete catalog/ordering, and update the ArchUnit rules to name your contexts.

Step 3: Model the core aggregate

Pick the most important command in the core context, then answer these questions on paper:

QuestionShop exampleYour answer
Which command?Place order
Which aggregate handles it?Order
What must be true before?Status DRAFT, at least one line
What changes?Status → PLACED, placedAt set
What event results?OrderPlaced
Who reacts to the event?Catalog reserves stock
What other data does the command need?Product price and name (from Catalog via the ACL)

Then write the aggregate test-first, as plain Java:

```java // 1. Write the rule as a test @Test void claim_cannot_be_approved_above_policy_limit() { Claim claim = Claim.submit(policyId, Money.of("12000", "USD"), "Water damage", clock); assertThatThrownBy(() -> claim.approve(Money.of("10000", "USD") /* limit */, adjuster, clock)) .isInstanceOf(DomainException.class) .hasMessageContaining("exceeds policy limit"); } // 2. Make it pass in the aggregate public void approve(Money policyLimit, AdjusterId by, Clock clock) { requireStatus(ClaimStatus.UNDER_REVIEW, "approve"); if (claimedAmount.isGreaterThan(policyLimit)) throw new DomainException("Claimed amount " + claimedAmount + " exceeds policy limit " + policyLimit); this.status = ClaimStatus.APPROVED; this.approvedBy = by.getValue(); registerEvent(new ClaimApproved(id(), claimedAmount, clock.instant())); } ```

Step 5: Record decisions as you go

Every time you choose between options (sync vs async events, a new library, an aggregate boundary), add an ADR to the decision log. Add your own pages to this guide (docs/_chapters + build.py), for example a "Claims domain" page with your context map and glossary.

Common pitfalls (and the fix)

SmellFix
Entities with public setters and services full of ifsMove each rule into an intention-revealing method on the aggregate
@ManyToOne from one aggregate to anotherStore the ID; load the other aggregate through its repository if needed
One giant aggregate (e.g. Customer with all orders)Find the real invariants, then split and reference by ID
Controllers calling repositoriesGo through an application service
Entities returned from controllersReturn view classes (read models)
The frontend recomputing totals or eligibilityHave the backend return it in the view (total, allowedActions)
Instant.now() in domain codePass a Clock
A "Utils" or "Helper" class with business logicUsually a missing value object or domain service. Name it.
Generic names: Manager, Processor, DataUse a word from the ubiquitous language
Shared "common" module growing every sprintKeep the shared kernel tiny. Duplicate small things instead of sharing them.

Day-one checklist

  • ☐ Glossary started with at least 10 terms from domain experts
  • ☐ Context map drawn (even on a whiteboard photo committed to docs/)
  • ☐ ArchUnit rules updated with your context names
  • ☐ First aggregate with unit tests for every invariant
  • ☐ First Flyway migration
  • ☐ One vertical slice visible in the Vue UI
  • ☐ ADRs written for anything you changed from this template
  • ☐ CI running ./mvnw verify and npm run build
