--- title: Architecture for a domain model lede: DDD doesn't require a particular architecture, but it needs one that keeps the domain model independent of frameworks, databases and delivery mechanisms. Layered, hexagonal, onion and clean architecture are variations on the same rule. ---

The one rule

Dependency rule

Source code dependencies point toward the domain. The domain model depends on nothing outside itself: no ORM annotations required, no HTTP, no message broker. Everything else depends on the domain.

Why it matters: the domain is the part you'll refactor most and test most. If it imports the web framework, every framework upgrade becomes a domain change, and every domain test needs a running container.

Classic layered architecture

Evans' original book described four layers:

LayerResponsibility
User interface / presentationShow information, interpret user commands (controllers, views)
ApplicationCoordinate use cases; thin; no business rules
DomainBusiness concepts, state and rules. The heart of the system
InfrastructurePersistence, messaging, external APIs, technical plumbing

In the naive version, Domain depends on Infrastructure because it calls the database. Apply dependency inversion instead: the domain defines interfaces (repositories, gateways) and infrastructure implements them. With that change, layered architecture becomes the same thing as the styles below.

Hexagonal (ports & adapters)

Alistair Cockburn's formulation. The application core is surrounded by ports, interfaces the core owns, and adapters that plug technology into those ports.

  • Driving (primary) adapters call into the core: REST controllers, CLI commands, message consumers, tests.
  • Driven (secondary) adapters are called by the core: database repositories, payment gateways, email senders.

(use-case ports)"] DOM["Domain model"] APP --> DOM end subgraph Driven["Driven adapters"] DB["SQL repository"] PSP["Payment provider client"] MAIL["Email sender"] end REST & MQ & T --> APP APP -- "HoldRepository «port»" --> DB APP -- "PaymentGateway «port»" --> PSP APP -- "Notifier «port»" --> MAIL ```

Onion and Clean Architecture

Jeffrey Palermo's onion architecture and Robert C. Martin's Clean Architecture draw the same idea as concentric rings: the domain at the centre, then application/use cases, then interface adapters, then frameworks and drivers on the outside. The vocabulary differs (Clean Architecture's "entities" means enterprise-wide business rules, not DDD entities), but the dependency rule is identical.

A typical package layout per context

sales/ ├── domain/ ← pure: aggregates, values, events, repository ports, domain services │ ├── hold/ ← group by concept, not by pattern type │ ├── seating/ │ └── limits/ ├── application/ ← use-case handlers, commands, query services, ports for gateways ├── infrastructure/ ← SQL repositories, broker publisher, payment ACL, mappers └── interfaces/ ← REST controllers, message listeners, request/response DTOs
Group by concept

Inside the domain, prefer hold/, seating/, limits/ over entities/, repositories/, services/. Modules should tell the story of the domain, which is what Evans meant by the Modules pattern. A folder named after a pattern type hides which concepts belong together.

Enforcing the rules

Architecture that isn't enforced decays. Options, from lightest to strongest:

  • Architecture tests in the build: ArchUnit (JVM), NetArchTest (.NET), dependency-cruiser (JS/TS), import-linter (Python). Example rule: "classes in ..domain.. must not depend on ..infrastructure.. or on framework packages."
  • Build modules: put the domain in its own module with no framework dependencies. The compiler then enforces the rule.
  • Language module systems: JPMS, Go internal packages, Rust crates/visibility.
```java @ArchTest static final ArchRule domain_is_pure = noClasses() .that().resideInAPackage("..domain..") .should().dependOnClassesThat() .resideInAnyPackage("..infrastructure..", "..interfaces..", "org.springframework..", "jakarta.persistence.."); ```

Pragmatism

  • Supporting and generic contexts don't need this. A CRUD context can be a controller talking to a table. Use the full architecture where the domain is complex.
  • Mapping costs something. Separate persistence models plus mappers keep the domain pure but add code. Many teams accept ORM annotations on domain classes as a pragmatic compromise. That's fine as long as the annotations never drive design decisions.
  • Don't create an interface for everything. Ports are worth it where you'd plausibly swap or fake the implementation: persistence, external systems, time. They aren't worth it for every class.
