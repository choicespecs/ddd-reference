Value objects

A value object has no identity. Two Money(10.00, USD) instances are interchangeable, just like two copies of the number 10. Value objects are:

  • Immutable. You never change one; you replace it. price = price.plus(tax).
  • Equal by value. Override equals/hashCode on every field, or let Lombok's @Value generate them. Java 11 has no records; on Java 16+ a record gives you this for free.
  • Self-validating. An invalid one can't exist, so code that receives a Sku never has to re-check the format.
  • Behaviour-rich. Arithmetic, formatting, and comparisons live on the type, not in utility classes.
```java // sharedkernel/Money.java (simplified) — hand-written because JPA embeddables need a // no-arg constructor and non-final fields. Still immutable from the outside: no setters. @Embeddable public class Money { private BigDecimal amount; private String currency; protected Money() {} // JPA only public Money(BigDecimal amount, String currency) { // constructor = validation Objects.requireNonNull(amount, "amount"); Currency.getInstance(currency); // rejects "XYZ" if (amount.signum() < 0) throw new DomainException("Money cannot be negative"); this.amount = amount.setScale(2, RoundingMode.HALF_EVEN); // normalize this.currency = currency; } public Money plus(Money other) { requireSameCurrency(other); return new Money(amount.add(other.amount), currency); // new instance } public Money times(int quantity) { return new Money(amount.multiply(BigDecimal.valueOf(quantity)), currency); } public BigDecimal getAmount() { return amount; } public String getCurrency() { return currency; } @Override public boolean equals(Object o) { … amount and currency … } @Override public int hashCode() { return Objects.hash(amount, currency); } } ```

Value objects that aren't JPA embeddables are simpler. Lombok's @Value makes the class final and the fields private and final, and generates getters, equals, hashCode and toString. You write only the validating constructor:

```java // catalog/domain/Sku.java @Value public class Sku { private static final Pattern FORMAT = Pattern.compile("^[A-Z]{2,10}-\\d{4,8}$"); String value; // @Value makes it private final + getValue() public Sku(String value) { // explicit constructor replaces Lombok's if (value == null || !FORMAT.matcher(value).matches()) throw new DomainException("Invalid SKU '" + value + "'"); this.value = value; } } ```
Without Lombok

Plain Java 11 needs the same class with private final String value;, a getValue(), and hand-written equals/hashCode/toString. IDEs generate these, but they're easy to forget to update when a field is added. That's the main reason the template uses Lombok (see the ADR).

Fixing primitive obsession

Primitive obsession means passing String, UUID, and BigDecimal around for concepts that have rules. It leads to bugs like this one, which compiles happily:

```java // Which UUID is which? The compiler can't help. void addLine(UUID orderId, UUID productId, int qty); service.addLine(productId, orderId, 2); // swapped — runtime bug ``` ```java // Typed IDs make the swap a compile error @Value public class OrderId { UUID value; … } @Value public class ProductId { UUID value; … } void addLine(OrderId orderId, ProductId productId, int qty); ```

Good candidates for value objects: identifiers, money, quantities with units, email/phone, date ranges, addresses, percentages, codes with formats (SKU, IBAN, postal code).

```java // A date range VO — note the behaviour that would otherwise be duplicated everywhere @Value public class DateRange { LocalDate start; LocalDate end; public DateRange(LocalDate start, LocalDate end) { if (end.isBefore(start)) throw new DomainException("end before start"); this.start = start; this.end = end; } public boolean contains(LocalDate d) { return !d.isBefore(start) && !d.isAfter(end); } public boolean overlaps(DateRange o) { return !end.isBefore(o.start) && !o.end.isBefore(start); } public long days() { return ChronoUnit.DAYS.between(start, end) + 1; } } ```

Entities

An entity has a thread of identity. An order is still the same order after its lines change. Rules for entities:

  • Equality is based on the ID, not on the attributes.
  • Generate IDs in the domain (UUID.randomUUID()), not in the database, so an entity has its identity before it is saved. This makes events, tests, and equality simpler.
  • Don't expose public setters. Expose intention-revealing methods instead.
  • A no-arg constructor is needed for JPA. Make it protected so application code can't use it.
```java @Entity public class OrderLine { @Id private UUID id; private UUID productId; private String productName; @Embedded private Money unitPrice; private int quantity; protected OrderLine() {} // JPA only OrderLine(UUID productId, String name, Money unitPrice, int quantity) { // package-private: this.id = UUID.randomUUID(); // only Order (same package) can create lines … changeQuantity(quantity); // reuse the validation } void changeQuantity(int q) { // package-private: only via Order if (q < 1 || q > 99) throw new DomainException("Quantity must be between 1 and 99"); this.quantity = q; } } ```
equals/hashCode on JPA entities

The template doesn't override equals on entities, because aggregates are compared by ID explicitly (order.getId().equals(otherId)). If you do put entities in Sets, base equals on the ID. Because IDs are assigned in the constructor rather than by the database, this works without the usual "null ID before persist" problem.

Aggregates

An aggregate is a group of objects that must stay consistent together, with one entity as its root. It is the most important tactical pattern and the one most often misused.

The rules

  1. Protect invariants inside the boundary. All rules that must be immediately true ("the total equals the sum of the lines", "lines share one currency") are enforced by the root.
  2. Outside code holds references to the root only. Nobody outside Order keeps a reference to an OrderLine. getLines() returns an unmodifiable list.
  3. Reference other aggregates by ID. OrderLine stores productId, not a @ManyToOne Product. This keeps aggregates independent, avoids loading huge graphs, and lets contexts split later.
  4. One aggregate per transaction (as a guideline). Changes to other aggregates should happen via domain events, ideally with eventual consistency.
  5. Keep them small. A large aggregate is slow to load and causes lock conflicts.
This template bends rule 4, on purpose

Placing an order changes the Order and every Product involved in the same transaction (the event handler runs synchronously). That's a pragmatic choice for a monolith: it gives you "never oversell" without sagas. The Events chapter shows how to switch to eventual consistency when you need to.

Sizing aggregates: an example

Should Customer contain a List<Order>? Ask: is there an invariant that spans a customer and all their orders and must be true at every moment? Usually not. "Customers have orders" is a relationship, not an invariant. So Order is its own aggregate and holds a customerId. Otherwise, a customer with 5,000 orders would load all of them every time they change their email, and two orders placed at the same moment would conflict on the customer's version column.

CandidateInvariant that spans it?Verdict

Bank account + TransactionsBalance never below overdraft limit⚠️ Together, but don't load all transactions: store a running balance on the account

Repositories

A repository gives the illusion of an in-memory collection of aggregates. In DDD:

  • There is one repository per aggregate root, and none for inner entities. There is no OrderLineRepository.
  • The interface lives in the domain, uses domain types, and has only the methods the domain needs.
  • The implementation lives in infrastructure.
```java // ordering/domain/OrderRepository.java — the port public interface OrderRepository { Optional findById(OrderId id); List findRecent(int limit); Order save(Order order); } ``` ```java // ordering/infrastructure — the adapter, backed by Spring Data interface SpringDataOrderRepository extends JpaRepository { // package-private List findAllByOrderByCreatedAtDesc(Pageable pageable); } @Repository class JpaOrderRepository implements OrderRepository { private final SpringDataOrderRepository jpa; public Optional findById(OrderId id) { return jpa.findById(id.getValue()); } … } ```

Why not let the domain interface extend JpaRepository directly? You can, and it's a common pragmatic shortcut (see the decision log). The cost is that JpaRepository exposes about 20 methods, including deleteAll() and findAll() on a table that might hold millions of rows. Every one of those becomes part of your domain's API.

Factories

When creating an aggregate involves rules, generating an ID, or setting an initial state, put that logic in a static factory method on the root, or in a separate factory class if creation needs other collaborators.

```java public static Product create(Sku sku, String name, String description, Money price, int initialStock) { return new Product(ProductId.newId(), sku, name, description, price, initialStock); } // The constructor is private. "new Product(...)" from outside isn't possible. ```

Factory names should come from the ubiquitous language: Order.startDraft() says more than new Order().

Domain services

Use a domain service when a piece of domain logic doesn't naturally belong to a single entity, usually because it involves several aggregates or a policy. A domain service is stateless, is named in the ubiquitous language, and lives in the domain package.

```java // Example (not in the template): pricing that depends on customer tier and promotions public class PricingPolicy { public Money priceFor(Product product, CustomerTier tier, List active) { Money base = product.getPrice(); Money discounted = active.stream() .filter(p -> p.appliesTo(product.getId(), tier)) .map(p -> p.apply(base)) .min(Comparator.comparing(Money::amount)) .orElse(base); return tier == CustomerTier.GOLD ? discounted.percentOff(5) : discounted; } } ```

Don't overuse them

If every rule ends up in a "service" and the entities are just getters, you've rebuilt the anemic model. Try putting logic on an entity or value object first.

Domain events

A domain event records something meaningful that happened. Name it in the past tense, make it immutable, and include enough data for listeners to act on it.

```java @Value public class OrderPlaced implements DomainEvent { OrderId orderId; List lines; Money total; Instant occurredAt; @Value public static class Line { UUID productId; int quantity; } } ```

Aggregates register events, and the application layer publishes them after saving. Events decouple side effects (reserving stock, sending email, updating a search index) from the aggregate that caused them. The full story is in Domain & integration events.

Bonus: specifications and policies

When a business rule is a reusable yes/no check, a specification object names it:

```java public final class EligibleForFreeShipping { private static final Money THRESHOLD = Money.of("50.00", "USD"); public boolean isSatisfiedBy(Order order) { return order.total().amount().compareTo(THRESHOLD.getAmount()) >= 0 && order.getLines().stream().noneMatch(l -> l.getProductName().contains("Oversize")); } } ```

Quick checklist for a new aggregate

  • ☐ The name comes from the ubiquitous language
  • ☐ Invariants are listed in the class Javadoc
  • ☐ The constructor is private or protected; a factory method exists
  • ☐ There are no public setters; methods are named after business actions
  • ☐ Collections are exposed unmodifiable
  • ☐ Other aggregates are referenced by ID
  • ☐ Value objects are used for anything with rules or units
  • ☐ Domain events are registered for things others care about
  • ☐ It has unit tests for every invariant, with no Spring
  • ☐ It has a repository interface in domain and an adapter in infrastructure
