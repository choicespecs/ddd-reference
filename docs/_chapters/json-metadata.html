--- title: JSON metadata lede: The JSON path. Objects are described in JSON (a data schema plus UI hints) and a generic frontend renders forms from it. The JSON can be written by hand, stored as configuration, or generated from your POJOs. ---

Two documents: data schema and UI schema

Most JSON-driven UI libraries separate what the data is from how to lay it out:

DocumentStandardSays
Data schemaJSON Schema (current draft 2020-12)Fields, types, required, min/max, formats, enums
UI schemaLibrary-specific (JSON Forms, react-jsonschema-form, …)Order, grouping, widgets, labels, read-only, conditional visibility
ActionsYour own convention (JSON Schema doesn't cover behaviour)Buttons, their parameters (as a schema), confirmation, semantics

The data schema for Event

```json { "$schema": "https://json-schema.org/draft/2020-12/schema", "$id": "https://fieldhouse.example/schemas/Event.json", "title": "Event", "type": "object", "required": ["name", "venue", "onSaleAt"], "properties": { "name": { "type": "string", "title": "Name", "minLength": 1, "maxLength": 120 }, "venue": { "type": "string", "title": "Venue", "format": "ref:Venue" }, "onSaleAt": { "type": "string", "title": "On-sale opens", "format": "date-time" }, "status": { "type": "string", "title": "Status", "enum": ["DRAFT", "ON_SALE", "CANCELLED"], "readOnly": true }, "tiers": { "type": "array", "title": "Price tiers", "items": { "$ref": "#/$defs/PriceTier" }, "readOnly": true } }, "$defs": { "Money": { "type": "object", "x-widget": "money", "required": ["amount", "currency"], "properties": { "amount": { "type": "string", "pattern": "^\\d+(\\.\\d{1,2})?$" }, "currency": { "type": "string", "pattern": "^[A-Z]{3}$" } } }, "PriceTier": { "type": "object", "properties": { "name": { "type": "string" }, "price": { "$ref": "#/$defs/Money" }, "capacity": { "type": "integer", "minimum": 1 } } } } } ```

Custom formats (ref:Venue) and x- keywords (x-widget) are allowed: JSON Schema ignores keywords it doesn't know. Use them for things the standard doesn't cover, and keep a list of the ones you use.

The UI schema

For example, in the JSON Forms style (jsonforms.io), the UI schema arranges controls that point into the data schema:

```json { "type": "VerticalLayout", "elements": [ { "type": "Group", "label": "Details", "elements": [ { "type": "Control", "scope": "#/properties/name" }, { "type": "Control", "scope": "#/properties/venue" }, { "type": "Control", "scope": "#/properties/onSaleAt" }, { "type": "Control", "scope": "#/properties/status" } ]}, { "type": "Control", "scope": "#/properties/tiers", "options": { "detail": "READONLY" } } ] } ```

Describing actions

JSON Schema describes data, not behaviour, so actions need a small convention of your own. Describe each action's parameters as a schema, and the same form renderer can draw the dialog:

```json "actions": [ { "id": "publish", "label": "Publish", "semantics": "IDEMPOTENT" }, { "id": "addTier", "label": "Add price tier", "semantics": "NON_IDEMPOTENT", "parameters": { "type": "object", "required": ["name", "price", "capacity"], "properties": { "name": { "type": "string", "minLength": 1, "maxLength": 40 }, "price": { "$ref": "#/$defs/Money" }, "capacity": { "type": "integer", "minimum": 1, "default": 100 } } } }, { "id": "cancel", "label": "Cancel", "confirm": "Cancel this event? Buyers will be refunded.", "parameters": { "type": "object", "required": ["reason"], "properties": { "reason": { "type": "string", "minLength": 1, "maxLength": 500 } } } } ] ```

Per-instance state, such as "publish is disabled because…", can't go in a static JSON file. It still comes from the server with each object (see type vs. instance).

Where the JSON comes from

1. Written by handJSON files checked into the repo next to the code. Simple, but they drift from the Java classes unless tests compare them.
2. Stored as configurationSchemas kept in a database and edited by admins at runtime. Useful for user-defined forms; the server must still validate against them.
3. Generated from POJOsThe POJO stays the single source of truth and the JSON is a build or runtime artifact. Usually the best option.

Generating JSON Schema from a POJO

The victools jsonschema-generator library generates JSON Schema from Java classes, and its Jakarta Validation module turns @NotBlank, @Size and the rest into schema constraints:

```java var config = new SchemaGeneratorConfigBuilder(SchemaVersion.DRAFT_2020_12, OptionPreset.PLAIN_JSON) .with(new JakartaValidationModule(JakartaValidationOption.INCLUDE_PATTERN_EXPRESSIONS)) .with(new JacksonModule()); // respect @JsonProperty names config.forFields().withTitleResolver(f -> { // labels from @Property or the name Property p = f.getAnnotationConsideringFieldAndGetter(Property.class); return p != null && !p.label().isEmpty() ? p.label() : Labels.humanise(f.getName()); }); config.forFields().withReadOnlyCheck(f -> { Property p = f.getAnnotationConsideringFieldAndGetter(Property.class); return p != null && !p.editable(); }); JsonNode schema = new SchemaGenerator(config.build()).generateSchema(Event.class); ```

Alternatively, if you already have the annotation metamodel, serialise ObjectSpec to JSON directly. That's the hybrid covered in the next chapter.

The server still validates

A JSON schema in the browser gives fast feedback, but users can bypass it. Validate every request on the server, either with Bean Validation on the POJO or with a JSON Schema validator (networknt json-schema-validator, everit) against the same schema. See Rules once, enforced everywhere.
