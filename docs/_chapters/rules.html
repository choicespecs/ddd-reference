--- title: Rules once, enforced everywhere lede: The biggest payoff of a model-driven UI is that each business rule is written once, on the domain object, and then shows up in the UI and is enforced by the API automatically. ---

The problem it solves

In a hand-built application, "an event needs at least one price tier before it can be published" typically appears in three places: a disabled button in the frontend, a check in the controller, and maybe a database constraint. Sooner or later the three disagree.

In a model-driven application, the rule is written once, on Event, and everything else reads it:

```mermaid flowchart LR R["Event.disablePublish()
'Add at least one price tier first'"] R --> UI["UI: Publish button greyed out
with the reason as tooltip"] R --> API["API: POST …/publish/invoke
rejected with the same reason"] R --> T["Unit test: asserts the reason"] ```

The order of checks

Both the renderer and the API apply the same sequence. The UI uses it to decide what to draw, and the API uses it to decide what to allow. In Naked Objects terminology: see it, use it, do it.

  1. Can you see it? Permissions, then hideX(). If not, it doesn't exist for this user, so the API returns 404.
  2. Can you use it? disableX(). If not, the reason is shown, and the API returns an error with the same text.
  3. Can you do it with these values? Bean Validation on the parameters, then validateX(…), then value-object constructors.
  4. Do it, then check the object's invariants before saving.

Testing rules

Because the rules are plain methods on plain objects, they're trivial to unit test, with no UI or HTTP involved:

```java @Test void cannot_publish_an_event_without_price_tiers() { var event = anEvent().withNoTiers().build(); assertEquals("Add at least one price tier first", event.disablePublish()); } @Test void can_publish_once_a_tier_exists() { var event = anEvent().build(); event.addTier("General", Money.of("45.00", "GBP"), 500); assertNull(event.disablePublish()); } @Test void cancel_is_hidden_after_cancelling() { var event = anEvent().build(); event.cancel("Artist illness"); assertTrue(event.hideCancel()); } ```

Add one generic API test that proves the invoker enforces disableX for any action. Then you don't need a separate API test per rule.

Never rely on the UI alone

A greyed-out button is a hint, not a guard. Anyone can call the API directly. Every check the UI performs must also run on the server. The generic invoker in The generic REST API does this for every action automatically, which is exactly why one code path is safer than many.
