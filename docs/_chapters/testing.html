Aggregate tests that read like rules

Name tests after the business rules from Example Mapping. Use builders so each test shows only what matters to it.

```java class EventSeatingTest { Instant onSale = Instant.parse("2026-06-01T10:00:00Z"); @Test void a_seat_cannot_be_held_by_two_buyers() { var seating = aSeating().onSaleAt(onSale).withSeats("12F", "12G").build(); seating.hold(buyer("alice"), seats("12F"), onSale.plusSeconds(1)); assertThrows(SeatUnavailable.class, () -> seating.hold(buyer("bob"), seats("12F"), onSale.plusSeconds(2))); } @Test void seats_cannot_be_held_before_the_on_sale_opens() { var seating = aSeating().onSaleAt(onSale).withSeats("12F").build(); assertThrows(OnSaleNotOpen.class, () -> seating.hold(buyer("alice"), seats("12F"), onSale.minusSeconds(1))); } @Test void releasing_a_hold_makes_its_seats_available_again() { var seating = aSeating().onSaleAt(onSale).withSeats("12F").build(); var hold = seating.hold(buyer("alice"), seats("12F"), onSale); seating.release(hold); assertThat(seating.isAvailable(seat("12F"))).isTrue(); assertThat(seating.pullEvents()).last().isInstanceOf(SeatsReleased.class); } } ```

Assert on events, not just state

Events are part of the aggregate's public behaviour. Asserting "this command produced SeatsHeld with these seats" tests the business outcome without coupling to internal fields. For event-sourced aggregates this is the natural style: given past events, when a command, then new events (or an error).

Value objects and properties

Value objects are pure functions, which makes them ideal for property-based testing (jqwik, QuickCheck, Hypothesis, fast-check): state a rule and let the tool search for counter-examples.

```java @Property void adding_money_is_commutative(@ForAll("gbp") Money a, @ForAll("gbp") Money b) { assertThat(a.plus(b)).isEqualTo(b.plus(a)); } @Property void limit_never_allows_more_than_max(@ForAll @IntRange(min=0, max=10) int owned, @ForAll @IntRange(min=1, max=10) int requested) { var limit = new PurchaseLimit(6); if (owned + requested > 6) assertThrows(PurchaseLimitExceeded.class, () -> limit.check(owned, n(requested))); else assertDoesNotThrow(() -> limit.check(owned, n(requested))); } ```

Control time

Holds expire and on-sales open, so time is a domain input. Never call Instant.now() inside the domain. Pass now into methods, or inject a Clock into application services and use a fixed or mutable clock in tests. This one habit removes a whole class of flaky tests.

Fakes over mocks

  • Use in-memory fake repositories rather than mocking repository.get(...) calls. Fakes behave like the real thing, and the tests survive refactoring.
  • Run one contract test suite against both the fake and the real adapter so they can't drift.
  • Don't mock domain objects. They're cheap to create for real, and mocking them tests your mocks, not your rules.
```java abstract class HoldRepositoryContract { abstract HoldRepository repository(); @Test void finds_holds_expiring_before_a_cutoff() { … } } class InMemoryHoldRepositoryTest extends HoldRepositoryContract { … } class SqlHoldRepositoryIT extends HoldRepositoryContract { … } // Testcontainers ```

Architecture tests

Add a handful of automated rules (see Architecture › Enforcing): the domain doesn't depend on infrastructure, contexts only use each other's public API, and so on. They're cheap and they stop slow erosion.
