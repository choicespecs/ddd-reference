--- title: Domain events lede: A domain event records something that happened that domain experts care about. Events decouple aggregates and contexts, make side effects explicit, and give you a vocabulary for time. ---

Definition

Domain event
An immutable record of a business-significant fact, named in the past tense in the ubiquitous language: SeatsHeld, HoldExpired, OrderConfirmed. It happened, so it can't be rejected, only reacted to.

A useful test: would a domain expert say "when that happens, we need to…"? If yes, it's an event. "Row updated" is not a domain event. "Order confirmed" is.

Commands vs. events

CommandEvent
TenseImperative: PlaceHoldPast: SeatsHeld
IntentA request that may be rejectedA fact that already occurred
RecipientsExactly one handlerZero or more subscribers
CouplingThe sender knows who handles itThe publisher doesn't know who listens

Shape of an event

```java public sealed interface SalesEvent extends DomainEvent permits SeatsHeld, SeatsReleased, HoldConverted, OrderConfirmed {} public record OrderConfirmed( EventId eventId, OrderId orderId, BuyerId buyer, Set seats, Money total, Instant occurredAt // always include when it happened ) implements SalesEvent {} ```
  • Immutable and named in the past tense.
  • Carries what subscribers need to react: usually identifiers plus the key facts. Avoid putting whole aggregates in it.
  • Records when it occurred, from an injected clock rather than Instant.now(), so it's testable.

Raising events from aggregates

The cleanest approach is for the aggregate to record events as part of its state change, and for the application layer to dispatch them after saving. The domain then never needs to know about message buses.

```java public abstract class AggregateRoot { private final List pending = new ArrayList<>(); protected void record(DomainEvent e) { pending.add(e); } public List pullEvents() { var out = List.copyOf(pending); pending.clear(); return out; } } // application service: one aggregate per transaction @Transactional public void payForHold(HoldId holdId, PaymentRef payment) { Hold hold = holds.get(holdId); hold.convertToOrder(payment, clock.instant()); // records HoldConverted holds.save(hold); publisher.publish(hold.pullEvents()); // or: write to an outbox in the same tx } // reactions, each in its own transaction @On(HoldConverted.class) void markSeatsSold(HoldConverted e) { /* EventSeating.markSold(e.hold()) */ } @On(HoldConverted.class) void createOrder(HoldConverted e) { /* Order.confirmFrom(e) → records OrderConfirmed */ } ```

What events decouple

  • Aggregate to aggregate (same context): HoldExpired leads to EventSeating.release(hold), and HoldConverted leads to a new Order, each in its own transaction, following the one-aggregate-per-transaction rule.
  • Context to context: OrderConfirmed triggers Admission to issue tickets and Notifications to send a receipt. Sales doesn't know either of them exists.
  • Core logic and side effects: auditing, analytics and emails become subscribers instead of lines tangled into the use case.
```mermaid sequenceDiagram participant H as Hold (aggregate) participant App as Application service participant Bus as Event dispatch participant ES as EventSeating participant Adm as Admission ctx participant O as Order (aggregate) App->>H: convertToOrder(payment) H-->>App: records HoldConverted App->>Bus: publish after commit Bus->>ES: markSold(hold) [own tx] Bus->>O: confirmFrom(hold) [own tx] O-->>Bus: records OrderConfirmed Bus->>Adm: OrderConfirmed (integration event) ```

Domain events vs. integration events

An important distinction once events cross a context boundary:

Domain eventIntegration event
AudienceInside the same bounded contextOther bounded contexts
ShapeUses internal model types; free to changePrimitive, versioned, documented: a published language
TransportOften in-processMessage broker, via an outbox
CompatibilityRefactor freelyAdditive changes only; version breaking changes

Translate domain events into integration events at the boundary. Don't publish your internal model to the world, because every consumer would then be coupled to your refactorings.

Pitfalls

  • CRUD events (HoldUpdated) carry no business meaning. Name what actually happened.
  • Publishing before commit: subscribers react to something that was then rolled back. Dispatch after commit, or use the transactional outbox.
  • Hidden control flow: long chains of event handlers are hard to follow. If a process has steps and deadlines, make it explicit with a process manager.
  • Assuming exactly-once delivery: make handlers idempotent, because the same event can arrive twice.
