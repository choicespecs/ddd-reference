The event flow in this template

```mermaid sequenceDiagram participant App as OrderApplicationService participant O as Order participant Bus as Spring event bus participant Tr as IntegrationEventTranslator (ordering) participant H as StockReservationHandler (catalog) App->>O: place(clock) O-->>O: registerEvent(OrderPlaced) App->>App: orders.save(order) App->>O: pullDomainEvents() App->>Bus: publishEvent(OrderPlaced) Bus->>Tr: on(OrderPlaced) Tr->>Bus: publishEvent(OrderPlacedIntegrationEvent) Bus->>H: on(OrderPlacedIntegrationEvent) H->>H: catalog.reserveStock(...) per line Note over App,H: all synchronous, same thread, same transaction ```

1. The aggregate registers

```java public void place(Clock clock) { … this.status = OrderStatus.PLACED; registerEvent(new OrderPlaced(id(), snapshotLines(), total(), placedAt)); } ```

The aggregate doesn't publish anything itself. It has no reference to a publisher, which keeps it pure and easy to unit test (order.peekDomainEvents()).

2. The application service publishes

```java Order saved = orders.save(order); order.pullDomainEvents().forEach(events::publishEvent); ```
Alternative: Spring Data @DomainEvents

Spring Data can publish events automatically on save() if the aggregate extends AbstractAggregateRoot (or has a @DomainEvents method). That takes less code, but it couples the domain to Spring Data, and it only fires when you call save() explicitly, not on dirty-checked updates. The template publishes explicitly so the behaviour is visible.

3. Translate to the published language

```java @Component class IntegrationEventTranslator { @EventListener void on(OrderPlaced e) { publisher.publishEvent(new OrderPlacedIntegrationEvent(e.orderId().value(), toLines(e.lines()))); } } ```

4. Another context reacts

```java @Component class StockReservationHandler { // in catalog.application — depends only on integration.* @EventListener void on(OrderPlacedIntegrationEvent event) { event.lines().forEach(l -> catalog.reserveStock(l.productId(), l.quantity())); } } ```

The critical choice: when does the listener run?

AnnotationRunsFailure in listenerConsistency

@TransactionalEventListener (default AFTER_COMMIT)After a successful commitOriginal change is already committed; the listener's work is lost unless you retryEventual (and fragile without an outbox)

Why the template uses synchronous listeners for stock

The business rule is "never oversell". With a synchronous listener, a failed reservation throws DomainException and the order stays DRAFT, with no partial state and no compensation logic. The integration test overselling_rolls_back_the_whole_placement proves it. The cost is that the two aggregates are locked together for the length of one transaction, which is fine in a monolith with moderate load.

When to use AFTER_COMMIT

Use it for side effects that shouldn't happen if the transaction rolls back, and whose failure shouldn't undo the business action:

```java @Component class OrderConfirmationEmailer { @TransactionalEventListener // AFTER_COMMIT: never email about an order that rolled back @Async // don't make the user wait for SMTP void on(OrderPlaced e) { mailer.sendConfirmation(e.orderId()); } } ```
Gotcha

Inside an AFTER_COMMIT listener, the original transaction is finished. If the listener writes to the database, annotate its service method with @Transactional(propagation = REQUIRES_NEW). Otherwise the writes are silently never committed.

The transactional outbox

When events must leave the process (Kafka, RabbitMQ, a webhook), this naive code is broken:

```java @Transactional public void place(UUID id) { order.place(clock); orders.save(order); kafka.send("orders", event); // ❌ sent, then DB commit fails → consumers see a phantom order } // ❌ or: DB commits, then the app crashes before send → event lost ```

The outbox pattern writes the event to an outbox table in the same transaction as the business change. A separate relay process reads the table and publishes, retrying until it succeeds. That gives at-least-once delivery, so consumers must be idempotent.

```mermaid flowchart LR A[Application service] -- "same TX" --> T1[(ordering_order)] A -- "same TX" --> T2[(outbox)] R[Relay / poller
or Debezium CDC] -- reads --> T2 R -- publishes --> K[[Kafka topic]] K --> C[Consumer
idempotent] ``` ```sql CREATE TABLE outbox ( id UUID PRIMARY KEY, aggregate_id UUID NOT NULL, type VARCHAR(200) NOT NULL, payload JSONB NOT NULL, created_at TIMESTAMPTZ NOT NULL, published_at TIMESTAMPTZ ); ```

Options for implementing it:

  • Spring Modulith's Event Publication Registry records @ApplicationModuleListener events in a table and republishes incomplete ones on restart. It's the least effort if you adopt Modulith, and it also externalizes events to Kafka/AMQP with @Externalized.
  • Hand-rolled: an OutboxWriter listener with BEFORE_COMMIT that inserts rows, plus a @Scheduled poller that publishes and marks them sent.
  • Debezium CDC: tails the database's write-ahead log and publishes outbox rows. This scales best, but it's another piece of infrastructure.

Going eventually consistent: what changes

If stock reservation became asynchronous, the model would need new states, because "placed" no longer means "stock guaranteed":

```mermaid stateDiagram-v2 [*] --> DRAFT DRAFT --> PENDING_STOCK: place() PENDING_STOCK --> CONFIRMED: StockReserved PENDING_STOCK --> REJECTED: StockReservationFailed CONFIRMED --> SHIPPED: ship() CONFIRMED --> CANCELLED: cancel() → StockReleased DRAFT --> CANCELLED: cancel() ```

This is a small saga (a process manager): a sequence of local transactions linked by events, with compensating actions on failure. It's more robust at scale and across services, but it is noticeably more complex for both the code and the UI (which now shows "pending" states). Make that trade-off deliberately.

Designing good events

  • Past tense, business language: OrderPlaced, not OrderStatusChangedToTwo.
  • Immutable records with an occurredAt timestamp.
  • Enough data to act without calling back (the lines and quantities here). It shouldn't be the whole aggregate, though.
  • Integration events: add fields, never remove or rename them. If you must break the contract, publish OrderPlacedV2 alongside the old event for a while.
  • Consumers are idempotent. Store processed event IDs, or make the operation naturally idempotent.
