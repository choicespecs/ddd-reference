--- title: Domain objects drive the UI lede: Write plain domain objects once (POJOs carrying their own data, rules and behaviour) and let the user interface and the REST API be generated from them, described either by Java annotations or by JSON metadata. ---

The idea in one picture

In most applications, one concept such as an Event is written four times: a database entity, a DTO, a REST controller, and a hand-built form and table in the frontend. Every new field means editing all four, and the business rules end up copied in several places.

This guide is about the alternative. The domain object is the single source of truth. You create a POJO for Event, and from that one class the system derives:

  • a form for its properties, with the right widget for each type,
  • a table for each of its collections,
  • a button for each of its business operations (actions),
  • the validation, shown in the UI and enforced on the server,
  • and a REST API to read and invoke all of it.

Add a field to the class and it appears in the form, the API and the validation. Add a method marked as an action and a button appears. Add a new class and it gets its own screens. Nothing else needs to be written by hand.

Where this comes from

This approach is called the Naked Objects pattern, also known as model-driven or metadata-driven UI. Richard Pawson introduced it around 2000, and it was built on the same insight as domain-driven design: the domain model should be the heart of the system. Naked Objects takes that one step further: the user interacts with the domain objects directly. The next chapter covers its history and principles, and how it relates to classic DDD.

Two ways to describe the objects

Java annotations

The POJO is annotated (@Property, @Action, @NotBlank…). The server uses reflection at runtime to read the class and build the metamodel. Frameworks: Apache Causeway, or a small home-grown introspector.

JSON metadata

The object is described in JSON (JSON Schema plus a UI schema). A generic frontend renders forms from the JSON. The JSON can be written by hand, stored in a database, or generated from the POJO.

Both paths end at the same place: a metamodel that a generic renderer turns into UI. Every chapter shows the same object both ways so you can compare them directly, and Annotations vs. JSON helps you choose.

About the code

Server examples are plain Java (records, Jakarta Bean Validation). Client examples are TypeScript with a small Vue component. Where a snippet uses a home-grown annotation such as @Action, the chapter shows its definition. Where it borrows from a real framework, the chapter says which one.
