--- title: DDD in legacy systems lede: Most DDD happens in existing systems rather than new ones. These patterns let you introduce a clean model gradually, without a rewrite. ---

Don't start with a rewrite

Big-bang rewrites of business systems fail often. The old system encodes years of rules nobody wrote down, and the business won't stop for you. The patterns below instead grow a well-modelled area alongside the legacy code and expand it over time.

Map what exists first

  • Draw a context map of the current landscape as it is, including the big ball of mud. Be honest about it.
  • Run a Big Picture Event Storming to find where the business pain is.
  • Identify the core subdomain. That's where a clean model pays off first. Leave stable, boring legacy alone.

Bubble context

From Eric Evans' essay Getting Started with DDD When Surrounded by Legacy Systems. Build a small new bounded context with a clean model for one specific need, and protect it from the legacy model with an anti-corruption layer. The bubble reads and writes legacy data through the ACL, so it doesn't need its own database at first.

```mermaid flowchart LR subgraph Bubble["Bubble context (new, clean model)"] M["Hold / EventSeating
rich domain model"] end ACL["Anti-corruption layer
translate legacy ⇄ model"] subgraph Legacy["Legacy ticketing system"] DB[("TBL_RSV, TBL_SEAT_STAT …")] end M <--> ACL <--> DB ```

It's cheap to start and shows value quickly. The downside is that the bubble depends on the legacy schema through the ACL, so it's fragile if that schema changes.

Autonomous bubble

A later stage: the new context gets its own data store, kept in sync with legacy by a synchronising ACL (batch jobs, change data capture, or events). It can now run independently, which makes it a stepping stone to replacing that part of the legacy system.

Strangler fig

Martin Fowler's pattern. Put a routing layer (proxy, gateway or façade) in front of the legacy system. Move capabilities one at a time into new contexts and redirect their traffic. Over time the new system grows around the old one until the old one can be switched off.

```mermaid flowchart LR U["Clients"] --> R["Routing façade"] R -- "/holds, /on-sales" --> N["New Sales context"] R -- "everything else" --> L["Legacy system"] N -. "events / ACL sync" .- L ```

A practical sequence

  1. Pick one painful, valuable capability in the core domain.
  2. Model it with domain experts. Write the glossary and the invariants.
  3. Build it as a bubble context behind an ACL. Ship it.
  4. Make it autonomous: its own storage, synchronised with legacy.
  5. Route traffic to it via a strangler façade. Retire the legacy path.
  6. Repeat for the next capability.
Refactoring inside the mud

Not every improvement needs a new context. Inside legacy code you can still introduce value objects for primitives, rename toward the ubiquitous language, and extract rules from scattered services into the objects they belong to. Each small step makes the eventual boundary easier to draw.
