Domain services

Use a domain service when an operation is a meaningful domain concept but doesn't naturally belong to any single entity or value object. Often it needs information from several aggregates, or it's a calculation the experts talk about as a thing in its own right.

```java // "Dynamic pricing" is something experts discuss by name. It needs the // event's demand and the tier, but it isn't the responsibility of either. public class DynamicPricingPolicy { public Money priceFor(PriceTier tier, DemandSnapshot demand, Instant now) { Money base = tier.basePrice(); if (demand.sellThroughRate().isAbove(Percent.of(80))) return base.times(tier.surgeMultiplier()); // capped by tier return base; } } ```
Don't overuse them

Reaching for a domain service by default leads straight to an anemic model: entities become data bags and all logic moves into XxxService classes. First ask whether the behaviour belongs on an entity or value object. Use a service only when it really doesn't.

Application services

An application service implements one use case from start to finish. It is a thin coordinator: a good one reads like a recipe and contains no if statements about business rules.

  1. Accept a command (input DTO) and authorise the caller.
  2. Load the aggregate(s) via repositories.
  3. Call domain methods. All decisions happen here, inside the domain.
  4. Save the aggregate in one transaction.
  5. Dispatch recorded events (or write them to an outbox).
  6. Return an id or a result DTO, never a domain object.
```java public record PlaceHold(BuyerId buyer, EventId event, Set seats) {} // command public class PlaceHoldHandler { private final EventSeatingRepository seatings; private final HoldRepository holds; private final PurchaseLimits limits; private final Clock clock; private final EventPublisher events; @Transactional public HoldId handle(PlaceHold cmd) { var selection = new SeatSelection(cmd.seats()); // reads across aggregates, so it's eventually consistent; see Aggregates › Sizing trade-offs limits.forEvent(cmd.event()) .check(holds.seatsHeldOrOwnedBy(cmd.buyer(), cmd.event()), selection); EventSeating seating = seatings.get(cmd.event()); HoldId holdId = seating.hold(cmd.buyer(), selection, clock.instant()); seatings.save(seating); events.publish(seating.pullEvents()); // SeatsHeld → creates the Hold aggregate return holdId; } } ```
Spot the smell

If an application service has if (hold.getStatus() == ACTIVE && hold.getExpiresAt().isAfter(now)), a business rule has leaked out of the domain. Move it into Hold as a method with a domain name.

Commands, queries and DTOs

  • Commands are input records named for intent (PlaceHold, CancelOrder), not UpdateHoldRequest.
  • Queries don't need the domain model at all. They can read straight from a read-optimised view. See CQRS.
  • Never return entities across the application boundary. Return ids or purpose-built views, so callers can't bypass the aggregate's methods and the API can evolve independently of the model.

Infrastructure services

A third kind: sending email, calling a payment provider, generating a PDF. The domain or application layer defines an interface (a port such as PaymentGateway) and infrastructure implements it. The domain says what it needs, and infrastructure decides how.
