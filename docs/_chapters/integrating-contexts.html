Integration styles

StyleExampleStrengthsCosts

Shared databaseSales reads Planning's tablesQuick to buildDestroys the boundary. Avoid it

A sensible default: events between contexts, synchronous calls only when the user is waiting for an answer that must be current.

Living with eventual consistency

Across contexts, there's no shared transaction. After OrderConfirmed, there will be a short window where Sales knows about the order and Admission doesn't yet. Design for it:

  • Ask the business how long a delay is acceptable. Usually seconds or even minutes are fine.
  • Show pending states in the UI: "Your tickets are being issued…"
  • Make every step retryable and every handler idempotent.
  • Model compensations for failures, such as refunding when tickets can't be issued, rather than pretending failures don't happen.

The transactional outbox

The dual-write problem: saving the aggregate and publishing to a broker are two separate systems. If you commit and then crash before publishing, the event is lost. If you publish and then the commit fails, you've announced something that never happened.

The outbox fixes this. Write the event to an outbox table in the same database transaction as the aggregate. A separate relay reads the outbox and publishes to the broker, marking rows as sent.

```mermaid sequenceDiagram participant App as Application service participant DB as Sales database participant Relay as Outbox relay participant Broker as Message broker participant Adm as Admission App->>DB: one transaction - update order + insert outbox row loop every few hundred ms (or via CDC) Relay->>DB: fetch unsent rows Relay->>Broker: publish OrderConfirmed Relay->>DB: mark sent end Broker->>Adm: deliver (at-least-once) Adm->>Adm: dedupe by event id, then handle ```

The relay can poll, or it can use change data capture (for example Debezium reading the database log). Either way, delivery is at-least-once, so consumers must handle duplicates.

Idempotent consumers

```java @Transactional public void on(OrderConfirmedV1 msg) { if (processed.alreadyHandled(msg.eventId())) return; // inbox / dedupe table tickets.issueFor(new OrderRef(msg.orderId()), msg.seatIds()); processed.markHandled(msg.eventId()); // same transaction } ```

Other options: natural idempotency (setting a state that's already set is harmless), or unique constraints on a business key such as "one ticket per seat per event".

Sagas and process managers

A business process that spans contexts and takes time ("hold, then pay, then issue tickets, then notify, compensating if any step fails") needs coordination. Two styles:

Choreography

Each context reacts to others' events, with no central coordinator. It's simple for short flows, but the overall process is implicit and spread across services.

Orchestration (process manager)

A dedicated object holds the process state, sends commands and reacts to events, including timeouts. The process is explicit and testable. It's better for flows with many steps, deadlines or compensations.

```java // Process manager for checkout: itself a small aggregate with state. public class CheckoutProcess { private CheckoutState state; // AWAITING_PAYMENT → PAID → TICKETS_ISSUED | REFUNDING public List on(PaymentCaptured e) { if (holdExpired) { // the hotspot from Event Storming state = REFUNDING; return List.of(new RefundPayment(e.payment(), "hold expired before payment")); } state = PAID; return List.of(new ConfirmOrder(holdId, e.payment())); } public List on(TicketIssuanceFailed e) { state = REFUNDING; return List.of(new RefundPayment(paymentRef, e.reason())); } } ```

Contracts between contexts

  • Publish integration events, not internal domain events (see Domain events).
  • Version schemas (OrderConfirmedV1) and evolve additively. Add optional fields; never repurpose existing ones.
  • Consumer-driven contract tests (Pact, Spring Cloud Contract) catch breaking changes before deploy.
  • Translate on the way in: the consumer maps the message into its own model in an ACL instead of letting the publisher's shape leak inward.
