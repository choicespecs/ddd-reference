Subdomains: what the business does

A subdomain is an area of the business. You discover subdomains, you don't design them. Classify each one, because the classification tells you how much effort to put in:

TypeMeaningStrategyExample (a shop)
CoreWhat makes this business different from competitors. Complex and valuable.Build in-house, with your best people, a rich domain model, and full DDD.Ordering & fulfilment rules, pricing/promotions
SupportingNeeded and somewhat specific to you, but not a differentiator.Build simply (CRUD is often fine) or outsource.Catalog management, inventory
GenericEvery business has it, and it's a solved problem.Buy or use off-the-shelf.Authentication (Keycloak/Okta), payments (Stripe), email

Bounded contexts: where a model applies

A bounded context is a boundary inside which every term has exactly one meaning and one model. It's a solution-space boundary: a chunk of software with its own model, its own code, and usually its own tables.

The classic example is the word "Product":

ContextWhat "Product" means thereAttributes it cares about
CatalogSomething we sellSKU, name, description, price, stock on hand, active
OrderingA line on an order (not even called Product: it's an OrderLine)productId, name at the time of ordering, unit price at the time of ordering, quantity
Shipping (future)A parcel to packWeight, dimensions, hazardous flag

Trying to build one Product class with every attribute for every context creates the "big ball of mud": every change risks breaking an unrelated feature, and nobody can reason about the whole thing. Bounded contexts let each model stay small and focused.

Heuristics for finding boundaries

  • Language changes. When the same word means something different, or different words mean the same thing, you've probably crossed a boundary.
  • Different experts. The warehouse manager and the marketing manager each own different contexts.
  • Different rates of change. Pricing rules change weekly and customer addresses almost never. Keep them apart.
  • Business capabilities, not data. "Place orders" is a capability; the "orders table" is not a boundary.
  • Transactional needs. Things that must be consistent immediately usually belong together. Things that can be consistent eventually can be split.
Bounded context ≠ microservice

A bounded context is a logical boundary. You can deploy several contexts in one Spring Boot app (a modular monolith, which is what this template does) and split them out later if you need to. Going the other way, from a microservice per entity to sensible contexts, is far more painful. See Monolith vs microservices.

ACL in code

Ordering states what it needs, in its own words:

```java // ordering/application/ProductCatalog.java — a port owned by Ordering public interface ProductCatalog { Optional find(UUID productId); record OrderableProduct(UUID productId, String name, Money price, boolean available) {} } ```

The adapter is the only place where Catalog's vocabulary appears:

```java // ordering/infrastructure/CatalogAdapter.java @Component class CatalogAdapter implements ProductCatalog { private final CatalogService catalog; public Optional find(UUID productId) { return catalog.findProduct(productId).map(CatalogAdapter::translate); } private static OrderableProduct translate(ProductView p) { // Ordering's idea of "available" combines two Catalog facts boolean available = p.active() && p.stockOnHand() > 0; return new OrderableProduct(p.id(), p.name(), new Money(p.price(), p.currency()), available); } } ```

If Catalog becomes a separate microservice tomorrow, only this class changes: it would use a RestClient call instead of a method call. Order, OrderApplicationService, and every test of them stay exactly as they are.

Event Storming: discovering it all

Event Storming (Alberto Brandolini) is a workshop format for discovering the domain with experts. You need a long wall (or Miro), sticky notes in a few colours, and the right people.

StickyColourExample
Domain event (past tense)OrangeOrder placed, Stock reserved, Payment captured
Command (imperative)BluePlace order, Cancel order
Actor / personSmall yellowCustomer, Warehouse clerk
Aggregate (handles commands, emits events)Large yellowOrder, Product
Policy ("whenever X, then Y")LilacWhenever an order is placed, reserve stock
Read model (what the user looks at to decide)GreenProduct list with stock
External systemPinkPayment provider
Hotspot / questionRed"What if stock runs out between add-to-cart and place?"

Clusters of stickies that share language and rules become your bounded contexts.

How big should a context be?

  • Too big: the same word starts meaning two things inside it, or two teams keep stepping on each other.
  • Too small: every use case needs calls across three contexts, or you keep needing distributed transactions.
  • Rule of thumb: one team can own several contexts, but one context should not be owned by several teams.
  • Start coarse. It is much cheaper to split a well-modularized context later than to merge two that were split too early.
