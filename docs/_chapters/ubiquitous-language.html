--- title: Names become the UI lede: When the UI is generated from your classes, every class, field and method name is something a user will read. DDD's ubiquitous language stops being good advice and becomes a requirement. ---

Ubiquitous language, briefly

Ubiquitous language
A precise vocabulary that developers and business experts build together and use everywhere: in conversation, in documents, and in code. The term comes from domain-driven design.

In a hand-built UI, a developer can name a field stsCd and label it "Status" in the form. The names in the code and on the screen are separate. In a generated UI they're the same name: whatever is in the code is what the user sees.

How names become labels

A metamodel builder derives labels from names using a simple convention, and annotations override it where needed:

CodeDerived labelShown as
class PriceTier"Price Tier" / plural "Price Tiers"Page title, menu entry
field onSaleAt"On Sale At"Form label (override: "On-sale opens")
method addTier(…)"Add Tier"Button (override: "Add price tier")
parameter capacity"Capacity"Dialog field
enum ON_SALE"On Sale"Dropdown option / badge
```java static String humanise(String identifier) { // "onSaleAt" → "On Sale At", "ON_SALE" → "On Sale" String spaced = identifier.contains("_") ? identifier.toLowerCase().replace('_', ' ') : identifier.replaceAll("([a-z0-9])([A-Z])", "$1 $2"); return Arrays.stream(spaced.split(" ")) .map(w -> Character.toUpperCase(w.charAt(0)) + w.substring(1).toLowerCase()) .collect(Collectors.joining(" ")); } ```

Note that humanise() needs parameter names at runtime, so compile Java with -parameters. Otherwise you get arg0, arg1.

Technical names make an unusable UI

Technical names

```java class EvtRec { String nm; int stsCd; void updStatus(int c) { … } void process() { … } } ```

The UI shows "Evt Rec", "Nm", "Sts Cd", and buttons labelled "Upd Status" and "Process".

Domain names

```java class Event { String name; EventStatus status; void publish() { … } void cancel(String reason) { … } } ```

The UI shows "Event", "Name", "Status", and buttons labelled "Publish" and "Cancel". It reads the way staff talk.

Name behaviour after business operations

Generic verbs such as update, process, handle and setStatus become meaningless buttons. Name each action after what the business calls it: publish, release hold, refund order, add price tier. If nobody can name an action in business terms, the model is probably missing a concept.

Practical rules

  • Agree on terms with the people who use the screens. Show them the generated UI early. It's the fastest way to check the language, because they react to the words directly.
  • Resolve synonyms. If "hold", "reservation" and "block" all appear, pick one, rename the class, and the UI follows.
  • Override labels sparingly. If you need a label override everywhere, the code name is wrong, so rename it. Keep overrides for punctuation and casing ("On-sale opens").
  • Treat renames as UI changes. Renaming a field changes the screen, and possibly the API and JSON metadata. Review renames the way you'd review copy changes.
  • Localise through keys, not code. For multiple languages, derive a key from the name (Event.onSaleAt) and look up translations. The code name stays the canonical term.
