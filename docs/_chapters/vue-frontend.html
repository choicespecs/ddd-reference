--- title: Vue frontend lede: Structuring a Vue 3 + TypeScript app to sit cleanly on top of a domain-driven backend, without re-implementing the domain in the browser. ---

Principles

  1. The backend owns the rules. The UI may hint (hide the Place button on a placed order), but it never decides. It sends commands and displays the resulting state or error.
  2. Mirror the bounded contexts. features/catalog and features/ordering match the backend packages, so the language is the same on both sides.
  3. One API module per context, with functions named after the use cases (orderingApi.place(id)).
  4. Typed contracts. TS interfaces mirror the Java read models, and are ideally generated from OpenAPI.

The API client

```ts // src/api/http.ts export class ApiError extends Error { constructor(public readonly problem: ProblemDetail) { super(problem.detail ?? problem.title) // the domain's own message } } export async function http(path: string, init: RequestInit = {}): Promise { const res = await fetch(path, { ...init, headers: { 'Content-Type': 'application/json', ...init.headers } }) if (!res.ok) throw new ApiError(await res.json().catch(() => ({ title: res.statusText, status: res.status }))) return res.status === 204 ? (undefined as T) : res.json() } ``` ```ts // src/api/ordering.ts — reads like the application service export const orderingApi = { get: (id: string) => get(`/api/orders/${id}`), start: (customerEmail: string) => post('/api/orders', { customerEmail }), addLine: (id: string, productId: string, quantity: number) => post(`/api/orders/${id}/lines`, { productId, quantity }), place: (id: string) => post(`/api/orders/${id}/place`), cancel: (id: string) => post(`/api/orders/${id}/cancel`), } ```

Why fetch and not axios? Fewer dependencies, and the wrapper is 20 lines. Axios is a fine choice if you want interceptors (auth token refresh) out of the box.

State: composables vs Pinia

The template keeps state local to views with a small composable:

```ts // src/composables/useAsync.ts export function useAsync(fn: (...args: A) => Promise) { const data = shallowRef(null) const loading = ref(false) const error = ref(null) async function run(...args: A) { loading.value = true; error.value = null try { return (data.value = await fn(...args)) } catch (e) { error.value = e instanceof ApiError ? e.message : String(e); return null } finally { loading.value = false } } return { data, loading, error, run } } ``` ```vue ```

Don't mirror the aggregate in the store

A store that recomputes totals or checks "can this be placed?" duplicates the domain, and the two copies will drift. Store the server's OrderView as-is and replace it with whatever the next command returns.

Better: let the server say which actions are allowed

The v-if="order.status === 'DRAFT'" check repeats a small piece of domain knowledge in the UI. For complex state machines, have the read model include the allowed actions:

```java // backend @Value public class OrderView { …; Set allowedActions; } // built from the aggregate: order.canPlace(), order.canCancel() … ``` ```vue ```

Forms and validation

  • Use HTML attributes (required, min, type="email") for instant feedback.
  • Show the server's problem+json detail messages for everything else. They come from the domain and are already user-readable.
  • For field-level server errors, read the errors: { field: message } map that GlobalExceptionHandler already adds to 400 validation responses, and show each message next to its input.
  • For complex forms, libraries such as VeeValidate + Zod give schema-driven client validation.

Keeping TypeScript types in sync

```bash npm i -D openapi-typescript npx openapi-typescript http://localhost:8080/v3/api-docs -o src/api/schema.d.ts ``` ```ts import type { components } from './schema' export type Order = components['schemas']['OrderView'] export type Product = components['schemas']['ProductView'] ```

Add this as an npm script ("gen:api") and run it in CI. That way a backend change that breaks the frontend fails the build instead of failing in production.

Dev server and the proxy

```ts // vite.config.ts server: { port: 5173, proxy: { '/api': 'http://localhost:8080' } } ```

In the browser everything is same-origin (:5173), so there are no CORS preflights and no cookie headaches. The backend also has a CORS config (WebConfig) for when you point the frontend at the API by absolute URL.

Testing the frontend

  • Vitest + @vue/test-utils for components and composables. Mock the API modules, not fetch.
  • Playwright for a handful of end-to-end flows against the real backend ("create order → add line → place").
```ts // Example Vitest test for useAsync import { useAsync } from '@/composables/useAsync' import { ApiError } from '@/api/http' it('exposes the ProblemDetail message', async () => { const { error, run } = useAsync(() => Promise.reject(new ApiError({ title: 'x', status: 409, detail: 'Cannot place an empty order' }))) await run() expect(error.value).toBe('Cannot place an empty order') }) ```
