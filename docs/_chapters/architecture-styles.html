--- title: Architecture styles lede: Layered, hexagonal, onion, clean, modular monolith, microservices. What each one means, how they differ (less than you'd think), and what this template picks. ---

The one rule they all share

Hexagonal, onion, and clean architecture are three ways of drawing the same idea: source code dependencies point inward, toward the domain. The domain doesn't import Spring MVC, JPA repositories, Kafka clients, or Vue. The outer layers depend on the domain, and the domain depends on nothing (except the JDK and, pragmatically, JPA annotations; see Persistence).

Classic layered (n-tier)

```mermaid flowchart TB P[Presentation / Controllers] --> B[Business / Services] --> D[Data access / DAOs] --> DB[(DB)] ```

This is what most Spring tutorials show: controller → service → repository, often packaged by layer (com.app.controller, com.app.service, com.app.repository).

  • Problem 1: the business layer depends on the data layer, so business code ends up shaped by tables.
  • Problem 2: packaging by layer scatters a single feature across the whole codebase, and nothing stops OrderService from calling InvoiceRepository directly.
  • Fine for: simple CRUD apps and supporting subdomains.

Hexagonal (ports & adapters)

Alistair Cockburn, 2005. The application sits in the middle, and the outside world connects through ports (interfaces the application owns) and adapters (implementations of those interfaces for specific technologies).

```mermaid flowchart LR subgraph Driving["Driving (primary) adapters"] REST[REST controller] CLI[CLI / scheduler] TEST[Tests] end subgraph Core["Application core"] IN(["Inbound port
(use case API)"]) APP[Application services] DOM[Domain model] OUT1(["Outbound port
OrderRepository"]) OUT2(["Outbound port
ProductCatalog"]) IN --> APP --> DOM APP --> OUT1 & OUT2 end subgraph Driven["Driven (secondary) adapters"] JPA[JPA repository] ACL[Catalog adapter / HTTP client] end REST & CLI & TEST --> IN JPA -. implements .-> OUT1 ACL -. implements .-> OUT2 ```
  • Driving adapters call into the application: REST controllers, message listeners, schedulers, and tests.
  • Driven adapters are called by the application through outbound ports: databases, other services, email, clocks.
  • The payoff is that you can test the core with in-memory fakes for every outbound port, and you can swap technologies without touching the core.

Onion architecture

Jeffrey Palermo, 2008. It uses concentric rings: Domain model → Domain services → Application services → (UI, Infrastructure, Tests). It's the same dependency rule as hexagonal, drawn as circles, with a more explicit split between the domain model and domain services.

Clean architecture

Robert C. Martin, 2012. Its rings are Entities → Use cases → Interface adapters → Frameworks & drivers. It tends to be more prescriptive: one class per use case, with input and output ports and presenters for each. That's great for very large codebases, and heavy for small ones.

```java // A strictly "clean" use case — one class, one public method public interface PlaceOrderUseCase { OrderView place(PlaceOrderCommand command); } @Service @Transactional class PlaceOrderService implements PlaceOrderUseCase { private final LoadOrderPort loadOrder; private final SaveOrderPort saveOrder; public OrderView place(PlaceOrderCommand cmd) { … } } ```

Don't get stuck on the labels

In interviews and design reviews, "we use hexagonal/clean architecture with DDD" usually means: domain in the middle with no framework dependencies, ports for persistence and external systems, thin controllers, and package-by-feature. That is exactly this template.

Package by layer vs package by feature

By layer

com.example.shop ├── controller/ │ ├── OrderController │ └── ProductController ├── service/ │ ├── OrderService │ └── ProductService ├── repository/ ├── entity/ └── dto/

A single feature is spread across 5 folders, and every class must be public, so anything can call anything.

By feature/context, then layer

com.example.shop ├── catalog/ │ ├── domain/ │ ├── application/ │ ├── infrastructure/ │ └── web/ └── ordering/ ├── domain/ ├── application/ ├── infrastructure/ └── web/

A context is one folder, and package-private classes (SpringDataOrderRepository, controllers) can't leak out of it.

Modular monolith vs microservices

This template is a modular monolith: one Spring Boot app and one database, with strict module (bounded context) boundaries enforced by tests.

Modular monolithMicroservices
Deployables1One per context (or more)
Cross-context callMethod call (nanoseconds, transactional)HTTP/gRPC/messaging (ms, can fail, no shared transaction)
ConsistencyCan be immediate (one DB transaction)Eventual; needs sagas/outbox
Refactoring a boundaryAn IDE refactorCoordinated API versioning across teams
Independent scaling/deploysNoYes
Operational costLowHigh (service discovery, tracing, many pipelines)
WhenDefault for new systems; one or a few teamsMany teams that need independent deploys, or very different scaling needs

Split the monolith when a context needs independent deployment or independent scaling, not before. When you do, the seams are already in place:

  1. The ACL adapter (CatalogAdapter) switches from a method call to an HTTP client.
  2. Integration events go onto Kafka/RabbitMQ instead of the Spring event bus, with an outbox.
  3. The context's tables (already prefixed catalog_ / ordering_, with no cross-context foreign keys) move to their own database.

Spring Modulith

Spring Modulith is an official Spring project for exactly this style. It treats each top-level package under the application class as a module, verifies the boundaries, documents them (generating C4/PlantUML diagrams), offers an event publication registry (a built-in outbox), and supports per-module integration tests. This template enforces boundaries with ArchUnit instead, so the rules are visible and explicit. Adopting Modulith later is straightforward because the package layout already matches what it expects. CQRS: where it fits

Command Query Responsibility Segregation means using different models for writing (commands → aggregates) and reading (queries → read models). The template uses a light form of it: commands go through aggregates, and queries return OrderView/ProductView read models. Today those views are built from the aggregates. When read performance matters, you can build them directly with JPQL projections or SQL, skipping the aggregate:

```java // A query-side repository — no aggregate loading, no dirty checking, exactly the columns needed public interface OrderSummaryQueries { @Query(""" select new com.example.shop.ordering.application.OrderSummary( o.id, o.customerEmail, o.status, o.createdAt, count(l), coalesce(sum(l.unitPrice.amount * l.quantity), 0)) from Order o left join o.lines l group by o.id, o.customerEmail, o.status, o.createdAt order by o.createdAt desc""") List recentSummaries(Pageable page); } ```

Full CQRS, with separate read databases updated from events, is a large step. Only take it when the read and write workloads really diverge.
