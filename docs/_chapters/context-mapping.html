--- title: Context mapping lede: A context map shows how bounded contexts relate to each other: who depends on whom, how models are translated, and the team dynamics behind each connection. ---

Why map relationships

Bounded contexts still have to work together. Every connection between two contexts is also a connection between two teams, with a direction of influence. Who must adapt when the other changes? A context map makes those relationships explicit, so integration problems and organisational problems become visible before they turn into outages.

Upstream and downstream

When context A's model affects context B, A is upstream (U) and B is downstream (D), like a river: what happens upstream flows down. The downstream team depends on the upstream team's decisions. The patterns below differ in how much power each side has and how the downstream side protects itself.

The patterns

Partnership

Two teams succeed or fail together, so they coordinate releases and evolve the interface jointly. It works best between two teams with high trust and similar schedules. It's expensive in communication, so reserve it for tightly coupled core work.

Shared kernel

Two contexts share a small, explicitly defined part of the model, usually a library. Changes need agreement from both teams. Keep it tiny (types like Money, EventId) because everything in it is coupled.

Customer–supplier

The upstream (supplier) team takes the downstream (customer) team's needs into its planning. The customer can negotiate, and the supplier commits. Event Planning → Sales works like this: Sales needs seating plans in a particular shape, and Planning agrees to provide them.

Conformist

The downstream team simply adopts the upstream model as is, because it has no leverage, or because the upstream model is good enough and translating isn't worth it. This is a common relationship with big external platforms. It's fine for supporting contexts, but dangerous for core ones because a foreign model ends up shaping your differentiator.

Anti-corruption layer (ACL)

The downstream team builds a translation layer that converts the upstream model into its own, so foreign concepts never leak into its domain. This is the defensive pattern to use when the upstream is a legacy system or an external vendor, and essential when protecting a core context.

```java // Sales defines what it needs, in its own language (a port): public interface PaymentGateway { PaymentResult charge(HoldId hold, Money amount, PaymentMethodToken token); } // The ACL adapter translates to/from the provider's model. // Provider concepts (PaymentIntent, cents, status strings) stop here. class ProviderPaymentGateway implements PaymentGateway { private final ProviderClient client; public PaymentResult charge(HoldId hold, Money amount, PaymentMethodToken token) { var intent = client.createPaymentIntent(Map.of( "amount", amount.minorUnits(), "currency", amount.currency().getCurrencyCode().toLowerCase(), "payment_method", token.value(), "idempotency_key", "hold-" + hold.value())); return switch (intent.status()) { case "succeeded" -> PaymentResult.captured(new PaymentRef(intent.id())); case "requires_action" -> PaymentResult.needsBuyerAction(intent.clientSecret()); default -> PaymentResult.declined(intent.lastError()); }; } } ```

Open host service (OHS) and published language (PL)

The upstream team offers a well-designed, stable, documented protocol for everyone to use, instead of custom integrations per consumer. The published language is the shared schema used on that protocol: versioned event schemas, an OpenAPI spec, or an industry standard. Sales publishing OrderConfirmed v2 events with a documented JSON schema is an OHS with a PL.

Separate ways

Sometimes the best integration is none. If the cost of integrating outweighs the benefit, let the contexts solve their problems independently, even if that means a little duplication.

Big ball of mud

Not a recommendation, just an honest label. Mark the parts of the landscape where models are tangled and boundaries don't exist. Draw a boundary around the mess, and keep its model from spreading with an ACL.

Conway's law

Systems end up mirroring the communication structure of the organisations that build them. A context map is partly an org chart. If the map and the team structure disagree, one of them will eventually change to match the other. Design them together; this is sometimes called the inverse Conway manoeuvre.
