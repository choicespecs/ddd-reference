--- title: Bounded contexts lede: A bounded context is an explicit boundary inside which one model, and one meaning for every term, applies consistently. It is the central pattern of strategic DDD. ---

The "one model" trap

The natural instinct is to build a single, unified model of the business, with one Ticket class and one Customer table that every part of the system shares. For any non-trivial business this fails. Different parts of the business genuinely need different models of the "same" thing:

ContextWhat "ticket" meansWhat it needs
SalesA line on an orderseat, price tier, price paid, order id
AdmissionA pass that admits one person oncebarcode, gate, scanned-at, revoked flag
Event PlanningA unit of venue capacitysection, row, accessibility, sellable flag
FinanceA revenue itemgross, fees, tax, payout batch

Merge all of those into one Ticket and you get a class with 40 nullable fields where every change risks breaking a department you've never met. Each team then has to understand everyone else's concerns to change anything. That is the big ball of mud.

Definition

Bounded context
An explicit boundary (linguistic, and usually also in code, data and team ownership) within which a particular domain model is defined and applicable. Inside it, every term has exactly one meaning. Outside it, the same word may mean something else, and that's fine.

barcode · scannedAt"] G["Gate"] --> T2 end Sales -- "OrderConfirmed
(orderId, seatIds)" --> Admission ```

The two Ticket classes share a name, but they are different concepts and different code. They're connected only by an explicit translation, here an event carrying identifiers.

What a boundary usually contains

  • A model and its language: the defining feature.
  • Code: a module, package, or service. Code from other contexts doesn't reach into its internals.
  • Data: its own schema or tables. Other contexts don't query them directly.
  • A team: ideally one team owns a context end to end. One team may own several contexts, but a context shared by several teams tends to rot.

How big should a context be?

There's no formula. Some heuristics:

  • Language heuristic: if a term starts needing a qualifier ("the sales ticket" vs. "the door ticket"), you're probably crossing a boundary.
  • Team heuristic: a context should be small enough for one team to own and understand completely.
  • Change heuristic: things that change together for the same business reason belong together.
  • Autonomy heuristic: a good boundary lets a team ship most changes without coordinating with other teams.
  • Start larger. Splitting a context later is easier than merging two that grew apart. Early on you know the least about where the real seams are.

Bounded contexts and microservices

A bounded context is a model boundary. A microservice is a deployment boundary. They fit together well, but:

  • One context can be deployed as several services (for example, Sales' on-sale API scaled separately from its back-office API).
  • Several contexts can live in one deployable as modules of a monolith, often called a modular monolith. This is often the best place to start: boundaries are enforced by module rules, and you can pull a context out into its own service later if scaling or team autonomy calls for it.
  • A service that spans several contexts is usually a smell: it mixes models.

What it looks like in code

In a modular monolith, each context gets a top-level module with a small public API. Its internals are hidden.

fieldhouse/ ├── sales/ ← bounded context (core) │ ├── api/ ← the only package other contexts may use │ │ ├── SalesFacade.java │ │ └── events/OrderConfirmed.java │ ├── domain/ ← Hold, Order, EventSeating, PurchaseLimit … │ ├── application/ │ └── infrastructure/ ├── admission/ ← bounded context │ ├── domain/ ← its own Ticket, Gate, Scan … │ └── … ├── planning/ └── shared/ ← tiny shared kernel (if any): Money, EventId

Enforce the rule with a module system (Java's JPMS, Gradle/Maven modules, .NET assemblies), a build-time architecture test (ArchUnit, NetArchTest, dependency-cruiser), or with tools like Spring Modulith.

Watch for

A context that's split in the code but shares a database schema with another context isn't really bounded. Shared tables are a shared model, and changing a column couples the two teams again.
