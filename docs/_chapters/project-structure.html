What goes in each layer

LayerContainsMay depend onMust NOT contain
domainAggregates, entities, value objects, domain services, domain events, repository interfacesJDK, sharedkernel, JPA annotations (pragmatic)Spring annotations, HTTP, SQL, DTOs, logging frameworks, @Transactional

Use Java visibility as a design tool

Package-private (no modifier) is your best friend in a package-by-feature layout:

ClassVisibilityWhy
SpringDataOrderRepositorypackage-privateNobody can bypass the domain port and call deleteAll()
JpaOrderRepository, CatalogAdapterpackage-privateSpring finds them by component scan; nobody needs to reference them by type
OrderControllerpackage-privateControllers are entry points, never called from Java code
OrderLine constructor, changeQuantitypackage-privateOnly Order may create or modify lines
StockReservationHandler, IntegrationEventTranslatorpackage-privateInvoked by the event bus only
OrderApplicationService, OrderViewpublicThe context's API

Enforcing the rules with ArchUnit

Documentation goes stale, but tests don't. backend/src/test/java/com/example/shop/architecture/ArchitectureTest.java fails the build if the structure is violated:

```java @AnalyzeClasses(packages = "com.example.shop", importOptions = ImportOption.DoNotIncludeTests.class) class ArchitectureTest { @ArchTest static final ArchRule domain_is_independent = noClasses() .that().resideInAPackage("..domain..") .should().dependOnClassesThat().resideInAnyPackage( "..application..", "..infrastructure..", "..web..", "org.springframework.."); @ArchTest static final ArchRule application_does_not_depend_on_adapters = noClasses() .that().resideInAPackage("..application..") .should().dependOnClassesThat().resideInAnyPackage("..infrastructure..", "..web.."); @ArchTest static final ArchRule contexts_are_free_of_cycles = slices() .matching("com.example.shop.(*)..") .should().beFreeOfCycles(); @ArchTest static final ArchRule catalog_does_not_know_ordering = noClasses() .that().resideInAPackage("com.example.shop.catalog..") .should().dependOnClassesThat().resideInAPackage("com.example.shop.ordering.."); @ArchTest // only the ACL in ordering.infrastructure may touch Catalog static final ArchRule only_acl_touches_catalog = classes() .that().resideInAPackage("com.example.shop.catalog..") .should().onlyHaveDependentClassesThat().resideOutsideOfPackages( "com.example.shop.ordering.domain..", "com.example.shop.ordering.application..", "com.example.shop.ordering.web.."); } ```

Try it: add import com.example.shop.ordering.domain.Order; to any Catalog class and run ./mvnw test. The build fails, and the error message names the offending class and line.

Other useful rules to add as you grow

```java // Controllers live only in web packages and are named *Controller classes().that().areAnnotatedWith(RestController.class) .should().resideInAPackage("..web..").andShould().haveSimpleNameEndingWith("Controller"); // @Transactional only in the application layer noClasses().that().resideOutsideOfPackage("..application..") .should().beAnnotatedWith(Transactional.class); // No field injection anywhere noFields().should().beAnnotatedWith(Autowired.class); // Domain events live in the domain layer classes().that().implement(DomainEvent.class).should().resideInAPackage("..domain.."); ```

Alternative layouts

Multi-module Maven/Gradle

For larger systems, each context (or even each layer) becomes its own Maven module. The compiler then enforces dependencies: if catalog-domain doesn't declare a dependency on Spring, it can't import Spring.

shop/ ├── pom.xml (parent, <modules>) ├── shared-kernel/ ├── catalog/ │ ├── catalog-domain/ depends on: shared-kernel (NO Spring) │ ├── catalog-app/ depends on: catalog-domain, spring-context, spring-tx │ └── catalog-infra/ depends on: catalog-app, spring-data-jpa ├── ordering/ … └── app/ depends on everything; contains ShopApplication + config

This gives strong guarantees, but it slows down builds and adds a lot of pom.xml plumbing. A good path is to start with packages plus ArchUnit (like this template) and move to modules when the team grows past what reviews can police.

Flat, for small contexts

A small supporting context doesn't need four sub-packages. This is fine:

referencedata/ ├── Country.java @Entity, simple ├── CountryRepository.java extends JpaRepository └── CountryController.java
