--- title: The metamodel lede: The metamodel is an explicit, serialisable description of your domain classes. It's the hinge of the whole approach, because annotations and JSON both produce it, and the UI and API both consume it. ---

What it is

Metamodel
Data that describes your model: for each domain type, its properties (with types and constraints), its collections, and its actions (with parameters). It's a model of the model.

Without a metamodel, the frontend would need to know about Event specifically. With one, the frontend only needs to know about properties, collections and actions in general, so the same rendering code works for every type you'll ever add.

(one ObjectSpec per type)"] MM --> R["Renderer"] MM --> API["REST API"] MM --> VAL["Validator"] MM --> DOCS["Docs / OpenAPI"] ```

Its shape

A minimal metamodel needs only a handful of types. This is enough to drive everything in this guide:

```java public record ObjectSpec( String type, // "Event" String label, String plural, // "Event", "Events" String titleProperty, // "name" List properties, List collections, List actions) {} public record PropertySpec( String id, // "onSaleAt" String label, // "On-sale opens" ValueKind kind, // STRING, NUMBER, BOOLEAN, ENUM, DATE, DATETIME, VALUE, REFERENCE String valueType, // "Money" for VALUE, "Venue" for REFERENCE, enum name for ENUM int order, boolean required, boolean editable, Map constraints) {} // maxLength, min, max, pattern, enumValues… public record CollectionSpec(String id, String label, String elementType, int order, boolean editable) {} public record ActionSpec( String id, String label, int order, Semantics semantics, // SAFE, IDEMPOTENT, NON_IDEMPOTENT String confirm, // null = no confirmation List parameters) {} ```

Type metadata vs. instance state

This is the most important distinction to get right. Some information is the same for every Event, and some depends on this event right now:

Examples"Event has a required name, max 120 chars"; "Event has a publish action""This event's name is Summer Jam"; "publish is disabled because there are no tiers"

```json // GET /api/objects/Event/42: the instance representation { "type": "Event", "id": "42", "title": "Summer Jam 2026", "values": { "name": "Summer Jam 2026", "venue": { "type": "Venue", "id": "7", "title": "Riverside Arena (Leeds)" }, "onSaleAt": "2026-06-01T10:00:00", "status": "DRAFT", "tiers": [] }, "members": { "publish": { "disabledReason": "Add at least one price tier first" }, "cancel": { "hidden": false }, "name": { "disabledReason": null } } } ```

The renderer combines the two: the spec says what to draw, and the instance says what values to put in it and which members are hidden or disabled right now. The dynamic state comes from the hideX / disableX methods described in Behaviour as actions.

Build it once, at startup

Building the metamodel uses reflection (or JSON parsing), and neither is free. Do it once per type at startup, keep the results in a registry, and fail fast on mistakes. Startup is the best time to discover that disablePublish() returns the wrong type.

```java public class SpecRegistry { private final Map specs = new ConcurrentHashMap<>(); public SpecRegistry(List> domainTypes, SpecBuilder builder) { for (Class c : domainTypes) { ObjectSpec spec = builder.build(c); // reflection or JSON; see next chapters specs.put(spec.type(), spec); } } public ObjectSpec get(String type) { var s = specs.get(type); if (s == null) throw new UnknownType(type); // also an allowlist: unknown = not exposed return s; } public List all() { return List.copyOf(specs.values()); } // drives the menu } ```
The registry is also your allowlist

Only types in the registry can be reached through the generic API. Only members in a spec can be read, edited or invoked. That's how you avoid accidentally exposing every class and every method on the classpath. See Security.
