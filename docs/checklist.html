    Design checklist

    Questions to ask at each stage of a DDD effort. Use this as a review aid in design discussions and pull requests.

    Before you start

    • Is the domain complex enough to justify DDD, or is this mostly CRUD? (Why DDD?)
    • Do we have regular access to people who really understand the business?
    • Can we state in one paragraph what makes this business different? That's the core domain.

    Strategic design

    • Have we run a collaborative modelling session (Event Storming, Domain Storytelling) with experts in the room?
    • Is there a written glossary per context, and does the code use exactly those terms?
    • Have we classified subdomains as core, supporting or generic, and does our investment match?
    • Are generic subdomains bought or integrated rather than built?
    • Does every bounded context have one owning team?
    • Is every term used with one meaning inside each context?
    • Is there a context map, and does it show upstream/downstream and the relationship pattern for each connection?
    • Is the core domain protected from external models by anti-corruption layers?
    • Does each context own its data, with no shared tables across contexts?

    Tactical design (in complex contexts)

    • Are domain concepts expressed as value objects instead of primitives?
    • Do entities change state only through methods named in the ubiquitous language (no public setters)?
    • Can you name the invariant(s) each aggregate protects?
    • Are aggregates small, and do they reference other aggregates by id?
    • Does each transaction modify exactly one aggregate?
    • Are cross-aggregate reactions handled through domain events?
    • Are events named in the past tense, and do they carry business meaning (not XUpdated)?
    • Is there one repository per aggregate root, with its interface in the domain?
    • Are application services thin, with no business ifs?
    • Is time passed in or injected rather than read from the system clock in the domain?

    Architecture & integration

    • Does the domain layer compile without any framework or infrastructure dependency?
    • Are dependency rules enforced automatically in the build?
    • Are queries served without loading aggregates (at least CQRS level 1)?
    • Are cross-context messages versioned integration events rather than internal domain events?
    • Are events published reliably (outbox) and consumed idempotently?
    • Are long-running cross-context processes explicit (process manager) with compensations?
    • Has the business agreed on acceptable consistency delays?

    Ongoing

    • When a requirement felt awkward to implement, did we revisit the model rather than bolt on a flag?
    • Do domain experts still recognise the language in the code (and in tests)?
    • Have subdomain classifications changed with the business strategy?
    • Are context boundaries still aligned with team boundaries?
