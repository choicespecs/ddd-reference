    Modelling the objects

    Behaviour as actions

    Business methods on a domain object become the buttons on its page. Method parameters become the fields of a dialog. This is what makes a generated UI more than a database editor.

    Why actions, not setters

    If a POJO has only getters and setters (an anemic model), the generated UI can only edit fields one at a time. Users can set status = CANCELLED without giving a reason, triggering refunds, or checking any rule. That isn't a business application; it's a table editor.

    When behaviour is modelled as methods with business names, the UI shows the operations the business actually performs, each with its own rules:

    Setters → field editing

    Java
    public void setStatus(EventStatus s) { status = s; }
public void setCancelReason(String r) { … }

    UI: a "Status" dropdown anyone can change.

    Actions → operations

    Java
    @Action
public void cancel(@NotBlank String reason) {
    status = CANCELLED;
    refunds.requestFor(this, reason);
}

    UI: a "Cancel" button that asks for a reason.

    Anatomy of an action

    In the methodIn the UI
    Method name / labelButton label
    No parametersButton invokes immediately (or after a confirm prompt)
    ParametersA dialog with one field per parameter, using the same type → widget mapping as properties
    Parameter annotations (@NotBlank, @Min)Validation in the dialog, re-checked on the server
    Return valueWhat to show next: void refreshes the page; an object navigates to that object; a list shows a table
    ExceptionAn error message in the dialog

    Supporting methods (the naming convention)

    Naked Objects frameworks use a naming convention to attach rules to an action without extra annotations. Apache Causeway uses this style. The renderer asks these methods about the current object before drawing the button:

    MethodReturnsEffect in the UI
    hideCancel()booleanButton not shown at all
    disablePublish()String reason or nullButton greyed out, with the reason as a tooltip
    validateAddTier(name, price, capacity)String reason or nullDialog shows the error and won't submit; checks the parameters together
    validate0AddTier(name)String or nullError shown next to parameter 0
    default2AddTier()parameter typePre-filled value for parameter 2
    choices0RemoveTier()ListParameter 0 becomes a dropdown of these options
    autoComplete0Transfer(String search)ListParameter 0 becomes a search-as-you-type lookup
    Java
    @Action(label = "Add price tier")
public PriceTier addTier(String name, Money price, int capacity) { … }

public String validate0AddTier(String name) {                     // per-parameter check
    return name.length() > 40 ? "Keep tier names under 40 characters" : null;
}
public String validateAddTier(String name, Money price, int capacity) {   // cross-parameter check
    return capacity > venue.capacity() ? "Capacity exceeds the venue's " + venue.capacity() : null;
}
public int default2AddTier() { return 100; }                      // pre-fill capacity
    Why a convention?

    The rule lives right next to the action it governs, in plain Java, and it's easy to unit test: assertEquals("Add at least one price tier first", event.disablePublish()). The same method drives the greyed-out button and the server-side check (see Rules).

    Action semantics

    Describe what kind of effect an action has, so the UI and API can treat it correctly:

    • Safe (query-only, e.g. findHoldsExpiringSoon()): can be a GET, no confirmation needed, and the result can be cached.
    • Idempotent (e.g. publish()): repeating it is harmless, so it maps to PUT.
    • Non-idempotent (e.g. addTier()): every call changes state, so it maps to POST and may need confirmation.

    Causeway expresses this as @Action(semantics = SemanticsOf.IDEMPOTENT). In a home-grown framework it's one enum field on @Action.

    Actions not tied to one object

    Creating and finding objects (createEvent(...), findEventsByVenue(...)) don't belong to an existing instance. Put them on a domain service or repository class annotated as a menu, and the renderer shows them in the app's main menu:

    Java
    @DomainMenu(label = "Events")
public class EventMenu {
    @Action public Event createEvent(@NotBlank String name, Venue venue, LocalDateTime onSaleAt) { … }
    @Action(semantics = SAFE) public List<Event> findOnSaleEvents() { … }
    @Action(semantics = SAFE) public List<Event> findEventsAtVenue(Venue venue) { … }
}
