    Glossary

    Every DDD term used in this guide, with a short definition and a link to where it's explained.

    A – C

    Aggregate
    A cluster of entities and value objects treated as one unit for data changes, with a single root and a consistency boundary. →
    Aggregate root
    The one entity in an aggregate that outside code may reference and call; it enforces the aggregate's invariants.
    Anemic domain model
    An anti-pattern where domain objects hold data but no behaviour, with the logic in services. →
    Anti-corruption layer (ACL)
    A translation layer that protects a context's model from an upstream model. →
    Application service
    Coordinates a use case: loads aggregates, calls domain methods, saves, publishes events. No business rules. →
    Big ball of mud
    A system without discernible boundaries, where models are tangled together. →
    Bounded context
    An explicit boundary inside which one model and one meaning for each term applies. →
    Bubble context
    A small, clean new context inside a legacy landscape, protected by an ACL. →
    Command
    A request to change state, named in the imperative (PlaceHold); it may be rejected.
    Conformist
    A downstream context that adopts the upstream model without translation. →
    Context map
    A diagram and description of the relationships between bounded contexts and their teams. →
    Core domain / subdomain
    The part of the business that provides competitive advantage, where modelling effort pays off most. →
    CQRS
    Command Query Responsibility Segregation: separate models for writing and reading. →
    Customer–supplier
    An upstream/downstream relationship where the upstream team plans around the downstream team's needs. →

    D – G

    Distillation
    Separating the core domain from supporting and generic concerns so it stays small and clear. →
    Domain
    The area of knowledge or activity the software serves, such as live-event ticketing.
    Domain event
    An immutable record of a business-significant fact, named in the past tense. →
    Domain expert
    Someone with deep knowledge of the business: organisers, box-office staff, finance, operations.
    Domain model
    The system of abstractions (expressed in language and code) that captures the parts of the domain relevant to the problem.
    Domain service
    A stateless operation that expresses domain logic not belonging to any single entity or value object. →
    Domain Storytelling
    A workshop technique where experts tell concrete stories that are drawn as pictographic sentences. →
    Entity
    An object defined by a lasting identity rather than its attributes. →
    Event sourcing
    Persisting an aggregate as its sequence of events rather than its current state. →
    Event Storming
    A collaborative workshop that models a domain as a timeline of domain events on sticky notes. →
    Eventual consistency
    Data across boundaries becomes consistent after a short delay rather than instantly. →
    Example Mapping
    A technique that breaks a story into rules, concrete examples and open questions. →
    Factory
    Something that encapsulates creating a valid aggregate or complex value. →
    Generic subdomain
    A solved problem common to many businesses (payments, email, identity); usually bought rather than built.

    I – P

    Idempotency
    Handling the same message more than once has the same effect as handling it once. →
    Integration event
    A versioned, public event meant for other bounded contexts, as opposed to an internal domain event. →
    Invariant
    A business rule that must always hold true for an aggregate when it's saved.
    Modular monolith
    One deployable whose code is split into modules with enforced boundaries, often one per bounded context.
    Module
    A grouping of model elements by domain concept (e.g. hold/), named in the ubiquitous language.
    Open host service (OHS)
    A well-defined protocol that an upstream context offers to all consumers. →
    Outbox (transactional)
    Writing events to a table in the same transaction as the state change, then relaying them to a broker. →
    Partnership
    Two teams that coordinate closely and evolve their interface together. →
    Policy
    A reactive business rule: "whenever X happens, do Y". Shown as lilac stickies in Event Storming.
    Port / adapter
    An interface owned by the core (port) and a technology-specific implementation (adapter). →
    Process manager
    A stateful coordinator for a long-running process across aggregates or contexts. →
    Projection / read model
    A query-optimised view built from events or state, used on the read side of CQRS.
    Published language (PL)
    A documented, shared schema used for integration between contexts. →

    R – Z

    Reconstitution
    Rebuilding an existing aggregate from storage, without re-running creation rules or raising events.
    Repository
    A collection-like abstraction for retrieving and storing aggregates. →
    Saga
    A long-running business transaction made of local steps with compensations; often implemented by a process manager or by choreography.
    Separate ways
    Choosing not to integrate two contexts at all. →
    Shared kernel
    A small part of the model explicitly shared by two contexts and changed only by agreement. →
    Strangler fig
    Gradually replacing a legacy system by routing capabilities to new code one at a time. →
    Strategic design
    The part of DDD concerned with subdomains, bounded contexts and their relationships.
    Subdomain
    A coherent part of the business problem: core, supporting or generic. →
    Supporting subdomain
    A business-specific area that's necessary but not a differentiator.
    Tactical design
    The building-block patterns used to implement a model inside one bounded context.
    Ubiquitous language
    The shared, rigorous language of a bounded context, used by experts and developers in conversation and code. →
    Upstream / downstream
    The direction of influence between two contexts; downstream depends on upstream. →
    Value object
    An immutable object defined only by its attributes, with no identity. →
