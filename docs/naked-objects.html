    Naked Objects & DDD

    The pattern behind "domain objects drive the UI": where it came from, its three principles, and how it relates to domain-driven design.

    A short history

    • 2001–2002: Richard Pawson and Robert Matthews describe Naked Objects and publish a book of the same name (Wiley, 2002). Pawson's 2004 PhD thesis at Trinity College Dublin formalises the pattern.
    • The Naked Objects Framework (Java, later also .NET) implements it. The Irish government's Department of Social Protection is one well-known large system built with it.
    • 2010: the Java framework enters the Apache incubator as Apache Isis. Dan Haywood also writes the Restful Objects specification, a standard REST API for exposing domain objects.
    • 2023: Apache Isis is renamed Apache Causeway. It's still the most complete Java implementation and runs on Spring Boot.

    The same idea shows up under other names: metadata-driven UI, model-driven UI, schema-driven forms, server-driven UI, and the admin generators of Django, Rails and JHipster.

    The three principles

    1. All business logic lives on the domain objects. Rules and behaviour aren't spread across controllers and services. An Event knows how to publish itself and when it may not.
    2. The UI is a direct representation of the domain objects. Users see Events and Holds, inspect their properties, and invoke their actions. Nobody hand-writes screens for them.
    3. The UI is generated 100% automatically from the domain objects. In practice most frameworks allow some customisation (see Customisation), but generation is the default.
    What "naked" means

    The objects are shown to the user naked, without a hand-built façade of screens and controllers. If an object is well designed, its generated UI is usable. If the generated UI is confusing, the object is usually confusing too. The UI becomes a mirror of the model's quality.

    How it relates to domain-driven design

    Domain-driven design (Eric Evans, 2003) is the broader discipline. Its main concerns are building a shared language with domain experts and designing a rich domain model whose objects hold both data and behaviour. Classic DDD doesn't say anything about how the UI is built. Teams usually write screens by hand.

    Naked Objects is a DDD-friendly implementation strategy that pushes the model all the way to the screen:

    DDD ideaWhat it becomes with Naked Objects
    Ubiquitous languageClass, field and method names are the labels users read
    EntitiesObjects with their own page, reachable by id
    Value objectsWidgets inside a form (money, date range, email)
    AggregatesA root page with nested child tables; links to other aggregates
    Rich behaviour on the modelActions: buttons and dialogs
    InvariantsRules shown in the UI and enforced on the server

    The two fit together well. Naked Objects actually forces good DDD practice. An anemic object with getters and setters produces a UI that is just a database editor. An object with well-named behaviour produces a UI that reads like the business.

    The pipeline every implementation shares

    flowchart LR
  A["1. Domain classes<br/>(POJOs)"] --> B["2. Introspect<br/>reflection or JSON"]
  B --> C["3. Metamodel<br/>types · members · rules"]
  C --> D["4. Generic renderer<br/>widgets per type"]
  C --> E["5. Generic REST API<br/>read · edit · invoke"]
  D <--> E

    Every chapter in this guide fits one of these five steps. The key design artifact is the metamodel (step 3): an explicit, serialisable description of your classes. Once you have it, the UI and the API are generic code you write once.
