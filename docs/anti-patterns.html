    Anti-patterns

    The common ways DDD efforts go wrong, how to recognise each one, and what to do instead.

    Anemic domain model

    Symptom: entities are bags of getters and setters, and all the logic lives in XxxService classes. Martin Fowler named this anti-pattern in 2003.

    Anemic

    Java
    // HoldService.java
if (hold.getStatus() == ACTIVE
    && hold.getExpiresAt().isAfter(now)) {
  hold.setStatus(CONVERTED);
  hold.setPaymentRef(ref);
}

    Rich

    Java
    // HoldService.java
hold.convertToOrder(ref, now);

// Hold.java owns the rule, in one place

    Why it hurts: rules get duplicated across services, any code can put an object into an invalid state, and the model teaches you nothing about the business. Fix: move each rule onto the object whose data it uses, remove setters, and name methods after domain operations.

    But…

    An anemic model is fine for a simple CRUD supporting context. It only becomes an anti-pattern where real business rules exist.

    DDD-lite (patterns without strategy)

    Symptom: folders named entities/, valueobjects/ and repositories/, but no one has talked to a domain expert, there's no context map, and one giant model spans everything. Fix: start with the strategic work: language, subdomains, boundaries. The tactical patterns are the least important part of DDD.

    God aggregate

    Symptom: an Event aggregate containing seats, holds, orders, tickets, reviews and payouts, constant optimistic-locking failures, and slow loads. Fix: list the invariants that truly need immediate consistency and draw the aggregate around only those. Everything else becomes a separate aggregate that references by id and is coordinated by events. See Aggregates.

    One model to rule them all

    Symptom: a canonical Customer or Ticket class shared across the company, usually in a "common" library that everyone depends on and nobody can change. Fix: bounded contexts. Let each context model what it needs, translate at the boundaries, and keep any shared kernel tiny.

    Integration through the database

    Symptom: context A reads or writes context B's tables directly. It's fast to build and then impossible to change, because B can't rename a column without breaking A. Fix: each context owns its data. Integrate through APIs or events. If A needs B's data locally, keep a replica updated from B's events.

    Leaking internal events

    Symptom: internal domain events are serialised straight onto the company message bus, so every refactor of the model breaks consumers. Fix: translate to versioned integration events at the boundary.

    Infrastructure in the domain

    Symptom: aggregates call HTTP clients, read config, send emails, or use Instant.now(). Tests need containers and mocks for everything. Fix: the domain decides and records events. Application services and adapters do the I/O. Pass time in.

    Technical language in the model

    Symptom: HoldManager, SeatProcessor, OrderDataHelper, updateStatus(int). Fix: rename to the ubiquitous language. If nobody can name the thing in business terms, the concept may be missing or wrong. Go back to the experts.

    Premature microservices

    Symptom: fifteen services on day one, with boundaries guessed before anyone understood the domain. Changes need coordinated deploys, which makes it a distributed monolith. Fix: start with a modular monolith that enforces context boundaries in code. Extract services once the boundaries have proven stable and there's a concrete reason to deploy separately (scaling, team autonomy, technology).

    Everything is core

    Symptom: the full tactical toolkit (aggregates, events, CQRS, hexagonal) applied to the venue-address form and the email templates. Delivery slows down everywhere. Fix: classify subdomains and match effort to value. Simple things should stay simple.

    Big design up front

    Symptom: months of modelling before any code, then a model that resists every new requirement. Fix: model a little, code it, learn, and refactor. The model improves through use, and the code is where you find out whether it works.
