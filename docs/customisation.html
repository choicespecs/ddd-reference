    Customisation

    A fully generated UI is the starting point, not a ceiling. These are the escape hatches, ordered from lightest to heaviest. Always reach for the lightest one that works.

    The customisation ladder

    1. Hints on the domain object: order, labels, grouping
    2. Layout files: arrangement kept outside the class
    3. Custom widgets for a value type
    4. View models: purpose-built objects that are rendered the same way
    5. Hand-built pages for the few screens that need them

    1. Hints on the domain object

    Ordering, labels, groups and multi-line text fit naturally on the class and cover most needs. This extends the @Property annotation with group and multiline attributes, which the introspector copies into PropertySpec:

    Java
    @Property(order = 1, group = "Details")                       private String name;
@Property(order = 2, group = "Details")                       private Venue venue;
@Property(order = 1, group = "Schedule", label = "On-sale opens") private LocalDateTime onSaleAt;
@Property(order = 1, group = "Notes", multiline = 6)           private String internalNotes;

    2. Layout files

    When presentation detail starts crowding the domain class, move the arrangement into a layout file per type. The class keeps the meaning and the layout file keeps the arrangement. Apache Causeway uses Event.layout.xml files for this. The JSON equivalent is a UI schema:

    JSON
    // Event.layout.json
{
  "columns": [
    { "span": 8, "groups": [ { "label": "Details",  "members": ["name", "venue"] },
                             { "label": "Schedule", "members": ["onSaleAt", "status"] } ] },
    { "span": 4, "groups": [ { "label": "Notes",    "members": ["internalNotes"] } ] }
  ],
  "collections": ["tiers"],
  "actionsPanel": ["publish", "addTier", "cancel"]
}

    Load layouts into the metamodel at startup. If no layout exists, fall back to the defaults derived from the class.

    3. Custom widgets

    Register a component for a value type or kind in the widget registry. Every property of that type, on every object, picks it up:

    TypeScript
    registerWidget({ valueType: 'SeatMap', component: SeatMapPicker })   // visual seat picker
registerWidget({ valueType: 'GeoPoint', component: MapPin })

    This is usually the best customisation per line of code, because one widget improves many screens.

    4. View models

    Sometimes the screen users need doesn't match a single domain object: a dashboard, a wizard, or a summary across aggregates. Don't distort the domain model to fit. Create a view model, which is also a POJO with properties, collections and actions, rendered by the same machinery:

    Java
    @DomainObject(viewModel = true, title = "eventName")   // add viewModel() to @DomainObject
public class OnSaleDashboard {
    @Property private String eventName;
    @Property private int seatsHeld;
    @Property private int seatsSold;
    @Property private Money revenue;
    @Collection private List<Hold> holdsExpiringSoon;

    @Action public void releaseAllExpiredHolds() { … }   // delegates to the Hold aggregates
}

    View models aren't persisted. They're rebuilt from domain objects (or a read-optimised query) on each request, and their state can be encoded in the URL. They let the generated UI handle task-oriented screens while the domain model stays clean.

    5. Hand-built pages

    For the handful of screens where user experience is critical, such as a public checkout flow or a seat-selection map, build the page by hand. Keep it on the same API: it can still call GET /api/meta for labels and constraints, and invoke actions through the generic endpoints, so the rules stay in one place.

    A healthy ratio

    In a typical back-office application, the vast majority of screens can stay generated, with a small number of hand-built pages for the critical moments. If you find yourself hand-building most screens, the domain objects may not match how users work, or this approach may not suit the application (see Trade-offs).
