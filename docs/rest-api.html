    REST API design

    Thin controllers, task-based endpoints that speak the ubiquitous language, validation at the edge, and consistent problem+json errors.

    Task-based vs CRUD endpoints

    CRUD-style

    HTTP
    PATCH /api/orders/42
{ "status": "PLACED" }

    The client decides the new state, and the server has to reverse-engineer the intent ("is going from DRAFT to PLACED allowed? Which side effects should run?"). This is usually a sign that the domain model is anemic.

    Task-based

    HTTP
    POST /api/orders/42/place

    The client states its intent, and the domain decides the outcome. It maps 1:1 to order.place(), and the URL is in the ubiquitous language.

    Use plain resource-style CRUD for simple fields with no rules (renaming a product, for example). Use task endpoints for state transitions and anything with business rules or side effects.

    Thin controllers

    Java
    @RestController
@RequestMapping("/api/orders")
class OrderController {
    private final OrderApplicationService orders;

    @PostMapping("/{id}/lines")
    OrderView addLine(@PathVariable UUID id, @Valid @RequestBody AddLineRequest req) {
        return orders.addLine(new Commands.AddLine(id, req.getProductId(), req.getQuantity()));
    }

    @Value
    static class AddLineRequest {
        @NotNull UUID productId;
        @Min(1) @Max(99) int quantity;
    }
}

    A controller does four things: bind the HTTP input, validate its shape, build a command, and return the view. If you find an if that encodes business logic in a controller, move it into the domain.

    Request DTOs are nested immutable classes, so the HTTP contract sits next to the endpoint that uses it, and nothing else can depend on it.

    How Jackson builds immutable DTOs on Java 11

    A @Value class has no setters and no no-arg constructor. backend/lombok.config sets lombok.anyConstructor.addConstructorProperties = true, so Lombok puts @ConstructorProperties on the generated constructor and Jackson passes the JSON fields to it by name. Without that setting you'd need @JsonCreator plus @JsonProperty on every constructor parameter.

    Bean Validation at the edge

    Java
    @Value
static class CreateProductRequest {
    @NotBlank @Size(max = 32) String sku;
    @NotBlank @Size(max = 200) String name;
    @Size(max = 2000) String description;
    @NotNull @DecimalMin("0.00") BigDecimal price;
    @NotBlank @Pattern(regexp = "[A-Z]{3}") String currency;
    @Min(0) int initialStock;
}

    @Valid on the parameter triggers validation. Failures become MethodArgumentNotValidException, and because GlobalExceptionHandler extends ResponseEntityExceptionHandler, they come back as a 400 problem+json response with per-field messages:

    JSON
    {"type":"https://example.com/problems/validation","title":"Invalid request","status":400,
 "detail":"One or more fields are invalid","instance":"/api/orders",
 "errors":{"customerEmail":"must be a well-formed email address"}}

    Errors: RFC 7807/9457 problem details

    Every error from the API has the same shape (Content-Type: application/problem+json):

    JSON
    {
  "type": "https://example.com/problems/business-rule",
  "title": "Business rule violated",
  "status": 409,
  "detail": "Insufficient stock for STKR-0001: requested 5, available 2",
  "instance": "/api/orders/0b6e…/place"
}

    Spring Framework 6 (Boot 3) has a built-in ProblemDetail class for this. Spring 5 (Boot 2.7) doesn't, so the template defines config/ApiProblem with the same fields and returns it as application/problem+json:

    Java
    @ExceptionHandler(DomainException.class)
ResponseEntity<Object> ruleViolated(DomainException ex, WebRequest request) {
    return ApiProblem.of(HttpStatus.CONFLICT, "business-rule", "Business rule violated",
            ex.getMessage(), path(request)).toResponse();
}

// Spring's own MVC errors (malformed JSON, 405, 415…) get the same shape:
@Override
protected ResponseEntity<Object> handleExceptionInternal(Exception ex, Object body, HttpHeaders headers,
                                                         HttpStatus status, WebRequest request) {
    return ApiProblem.of(status, "http-" + status.value(), status.getReasonPhrase(),
            ex.getMessage(), path(request)).toResponse();
}

    When you upgrade to Boot 3, delete ApiProblem and return Spring's ProblemDetail. The JSON stays identical, so the frontend doesn't notice.

    ExceptionStatusMeaning
    MethodArgumentNotValidException400Malformed request (Bean Validation)
    IllegalArgumentException400Bad input, e.g. an unparseable UUID
    NotFoundException404Aggregate ID doesn't exist
    DomainException409Business rule violated
    ObjectOptimisticLockingFailureException409Concurrent modification
    409 or 422 for rule violations?

    Both are common. 409 Conflict says "conflicts with the current state of the resource", which fits state-machine rules ("cannot place when PLACED"). 422 Unprocessable Content says "well-formed, but semantically wrong". Pick one and document it. A more advanced approach is to give DomainException subclasses (InvariantViolation, IllegalStateTransition) and map each to a status and a type URI that the frontend can switch on.

    Status codes and responses

    • 201 Created for creation, ideally with a Location header: ResponseEntity.created(URI.create("/api/orders/" + view.getId())).body(view).
    • Return the new state from commands (the template does). That saves the client a round trip and keeps the UI in sync with the server's view.
    • 204 No Content if you prefer commands to return nothing (a stricter CQS style).
    • 202 Accepted for asynchronous commands (see eventual consistency).

    Pagination and filtering

    Java
    @GetMapping
Page<OrderSummary> search(@RequestParam(required = false) OrderStatus status,
                          @PageableDefault(size = 20, sort = "createdAt", direction = DESC) Pageable page) {
    return orderQueries.search(status, page);
}

    Serializing Spring Data's Page directly works, but it exposes a large, implementation-specific JSON shape (pageable, sort, first…), and newer Spring Data versions warn about it. Wrap it in your own PageResponse<T> class with items, page, size and total so the contract is yours.

    Versioning

    • Additive changes need no new version. Adding a field to a view is safe, because Jackson clients ignore unknown fields by default (configure the TS side the same way).
    • Breaking changes: use a URL prefix (/api/v2/orders) or a media type. If the Vue app is the only client and is deployed together with the backend, you can often avoid versioning altogether.

    Idempotency for unsafe commands

    A user double-clicks "Place order", or a mobile client retries after a timeout. place() is naturally safe here: the second call fails with "Cannot place the order when order is PLACED". "Start order", however, would create two drafts. Common fixes:

    • Disable the button while the request is in flight (the Vue views do this with loading).
    • Accept an Idempotency-Key header, store keys with their responses for 24 hours, and replay the stored response on a repeat.
    • Let the client generate the ID (PUT /api/orders/{clientGeneratedUuid}).
