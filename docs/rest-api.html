    From metadata to UI

    The generic REST API

    Instead of one controller per class, a handful of generic endpoints serve every domain object. They read metadata, fetch instances, edit properties and invoke actions, using the metamodel as the allowlist.

    The endpoints

    Method & pathPurpose
    GET /api/metaAll registered types and menus (builds the app menu)
    GET /api/meta/{type}The ObjectSpec for one type (cacheable)
    GET /api/objects/{type}?page=&q=List or search instances
    GET /api/objects/{type}/{id}One instance: values plus member state
    PUT /api/objects/{type}/{id}/properties/{prop}Edit one editable property
    GET /api/objects/{type}/{id}/actions/{action}/invokeInvoke a safe action
    POST /api/objects/{type}/{id}/actions/{action}/invokeInvoke a state-changing action
    GET /api/objects/{type}/{id}/actions/{action}/choices/{param}?q=Dropdown/autocomplete options for a parameter
    POST /api/menus/{menu}/actions/{action}/invokeMenu actions such as createEvent

    This layout follows the Restful Objects specification (Dan Haywood), a standard for exposing domain objects over REST. Apache Causeway implements it, so you can read that spec for a complete, battle-tested version including links (HATEOAS) and media types.

    Invoking an action safely

    This is the most important endpoint, and it must never trust the client. The server re-runs every check that the UI showed:

    Java
    @PostMapping("/api/objects/{type}/{id}/actions/{action}/invoke")
public ObjectRep invoke(@PathVariable String type, @PathVariable String id,
                        @PathVariable String action, @RequestBody Map<String, JsonNode> body) {
    ObjectSpec spec = registry.get(type);                  // 404 unless registered
    ActionSpec a = spec.action(action);                    // 404 unless an @Action on this type
    ActionHandles h = handles.of(type, action);
    authz.checkCanInvoke(currentUser(), type, action);     // 403

    Object target = repositories.load(type, id);           // 404 if missing

    if (h.isHidden(target))                 throw new NotFound(action);           // hidden = doesn't exist
    String disabled = h.disabledReason(target);
    if (disabled != null)                   throw new ActionDisabled(disabled);    // 409/422
    Object[] args = binder.bind(a.parameters(), body);      // JSON → Money, Venue, LocalDateTime…
    validator.validateParameters(target, h.invoke(), args); // Bean Validation on parameters → 422
    String invalid = h.validate(target, args);
    if (invalid != null)                    throw new ActionInvalid(invalid);      // 422

    Object result = transactions.execute(() -> {
        Object r = h.invoke().invoke(target, args);         // the domain method runs here
        validator.validateObject(target);                   // invariants still hold?
        repositories.save(target);
        return r;
    });
    return representations.of(result == null ? target : result);   // what the UI shows next
}

    Errors the UI can show

    Return errors as problem+json (RFC 9457) with field-level detail, so the generic dialog can attach each message to the right field without knowing anything about the type:

    JSON
    {
  "type": "https://fieldhouse.example/problems/validation",
  "title": "Invalid parameters",
  "status": 422,
  "detail": "Capacity exceeds the venue's 8000",
  "errors": [ { "member": "capacity", "message": "must be greater than or equal to 1" } ]
}

    Binding values

    The binder turns JSON into the parameter types declared in the spec. It's driven by the same ValueKind as the widgets:

    • Primitives, enums, dates: Jackson conversion.
    • Value objects: a registered parser per type (Money.parse) or Jackson deserialisation of the record. Constructor validation runs, so an invalid value can't be created.
    • References: the client sends {"type": "Venue", "id": "7"}, and the binder loads the entity from its repository. Never deserialise an entity from client JSON.

    Representations

    An ObjectRep is built from the spec, not by serialising the POJO directly with Jackson. That guarantees only spec'd members leave the server, references become {type, id, title} links, and each member's dynamic state (hidden, disabledReason) is computed for the current user and object.

    Java
    public ObjectRep of(Object target) {
    ObjectSpec spec = registry.get(typeName(target));
    var values = new LinkedHashMap<String, Object>();
    var members = new LinkedHashMap<String, MemberState>();
    for (PropertySpec p : spec.properties()) {
        if (handles.isHidden(target, p.id()) || !authz.canView(currentUser(), spec, p)) continue;
        values.put(p.id(), toJsonValue(read(target, p)));         // references → {type,id,title}
        members.put(p.id(), new MemberState(false, handles.disabledReason(target, p.id())));
    }
    for (ActionSpec a : spec.actions())
        members.put(a.id(), new MemberState(handles.isHidden(target, a.id()),
                                            handles.disabledReason(target, a.id())));
    return new ObjectRep(spec.type(), idOf(target), titleOf(target, spec), values, members);
}
