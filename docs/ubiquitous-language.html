    Strategic design

    Ubiquitous language

    A single, precise vocabulary that domain experts and developers share. You use it in conversation, in documents, and in the code itself.

    Definition

    Ubiquitous language
    The language the team builds around the domain model, used by everyone on the team in every activity. "Ubiquitous" means everywhere: whiteboards, tickets, tests, class names, method names, database tables and API fields.

    Without one, every conversation goes through a translation step. An expert says "release the hold", a developer hears "set status = 3", and somewhere in that translation a rule gets lost. With one, the expert could read the method name hold.release() and nod.

    From conversation to code

    Listen for the nouns (candidate entities and value objects), the verbs (commands and behaviour), the past-tense phrases (domain events) and the rules (invariants and policies).

    "When a buyer places a hold on seats, those seats are unavailable to anyone else until the hold expires or is converted into an order. A buyer can't hold more than the event's purchase limit."

    Translated (lossy)

    Java
    seatService.updateStatus(seatIds, 2, userId);
if (count(userId) > cfg.getMax()) throw new Ex("too many");
reservationRepo.save(new Reservation(userId, seatIds, now + 600_000));

    Ubiquitous

    Java
    Hold hold = event.placeHold(buyer, seats, clock);
// throws PurchaseLimitExceeded
...
hold.convertToOrder(payment);
hold.expire();

    Building the language

    • Work from concrete scenarios, not abstractions. "Walk me through what happens when someone's card is declined during an on-sale" gets better language than "describe your entities."
    • Push back on vague words. When someone says "process", "handle", "manage" or "data", ask what actually happens.
    • Resolve synonyms. If "reservation", "hold" and "block" mean the same thing, agree on one and retire the others. If they mean different things, you've just found a concept.
    • Notice homonyms. If "ticket" means two different things to two groups, that's usually a context boundary, not a naming problem.
    • Write a glossary per context, keep it short, and put it next to the code (a GLOSSARY.md in the module). Prune it actively.
    • Rename code when the language changes. A stale name in code makes the old misunderstanding permanent. IDE refactorings make renaming cheap, so do it.

    Example: Sales context glossary

    TermMeaning in SalesNot to be confused with
    On-saleThe moment from which an event's tickets may be held and bought"Sale" as a discount
    HoldA time-limited claim by one buyer on specific seats; expires after 10 minutesAn order (a hold has no payment yet)
    Purchase limitMax seats one buyer may hold or own for an event, across all ordersVenue capacity
    OrderA paid, confirmed purchase created from exactly one holdA cart (not a Sales concept at all)
    TicketA line on an order: one seat at one price tierAdmission's "ticket", a scannable pass

    Pitfalls

    • Developer jargon leaking in: SeatDTO, HoldManager, processReservationData(). Technical names belong in the infrastructure layer, not in the domain model.
    • Forcing one language on the whole company: the language is ubiquitous within a bounded context, not across the organisation. Marketing and Admission are allowed to mean different things by "ticket".
    • Treating it as documentation: the language lives in conversations and code. A glossary that nobody updates is a museum.
