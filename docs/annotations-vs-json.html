    Describing the objects

    Annotations vs. JSON

    Both paths produce a metamodel. They differ in where the truth lives, who can change it, and how much behaviour they can express. Most teams end up with a hybrid that uses Java as the source and JSON on the wire.

    The same property, both ways

    Java annotations

    Java
    @Property(order = 3, label = "On-sale opens")
@NotNull @Future
private LocalDateTime onSaleAt;

    JSON metadata

    JSON
    "onSaleAt": {
  "type": "string",
  "format": "date-time",
  "title": "On-sale opens",
  "x-order": 3,
  "x-future": true
}

    Comparison

    Java annotationsJSON metadata
    Source of truthThe POJO itselfA separate document (unless generated)
    Behaviour (actions, rules)Natural: methods and disableX() are codeLimited: actions are described, but logic must live on the server
    Drift riskNone; the metadata is the classHigh if hand-written; none if generated
    Type safety & refactoringCompiler and IDE renames cover everythingStrings; renames need searching
    Change without deployingNoYes, if stored as configuration
    Who can editDevelopersDevelopers, or admins via a form builder
    Frontend independenceNeeds an API that serves the metamodelStandard format; many off-the-shelf renderers
    Language independenceJVM onlyAny backend, any frontend
    Best forRich domain behaviour, back-office appsDynamic / user-defined forms, polyglot systems

    The hybrid: Java as the source, JSON on the wire

    In practice, the strongest setup combines both:

    flowchart LR
  P["POJO<br/>annotations + Bean Validation<br/>+ supporting methods"] -- "reflection at startup" --> M["ObjectSpec registry"]
  M -- "serialise" --> J["JSON metadata<br/>GET /api/meta/{type}"]
  J --> F["Generic frontend<br/>(any framework)"]
  M --> S["Server-side validation<br/>& action invocation"]
  F -- "edit / invoke" --> S
    • Java is the single source of truth. You write the POJO and nothing else.
    • JSON is how the frontend learns about it. The frontend never imports Java types. It just renders whatever metadata the server sends.
    • Behaviour stays on the server. Rules run in Java, and their results (disabled reasons, validation messages) travel as JSON.
    • JSON Schema is still available. Emit it from the same spec for off-the-shelf form libraries, OpenAPI docs, or other consumers.
    Java
    @GetMapping("/api/meta/{type}")
public ResponseEntity<ObjectSpec> meta(@PathVariable String type) {
    return ResponseEntity.ok()
        .cacheControl(CacheControl.maxAge(Duration.ofHours(1)))   // type metadata is per-deployment
        .eTag(buildVersion)
        .body(registry.get(type));                              // Jackson serialises the records
}

    Choosing

    If…Choose
    The domain has real behaviour and rules, built by developersAnnotations (or the hybrid)
    Your frontend is a separate SPA (Vue, React)Hybrid: annotations on the server, JSON to the client
    Business users must define new forms without a deployJSON stored as configuration, validated on the server
    The backend isn't Java, or there are several backendsJSON (generated by each backend in a shared format)
    You want a complete generated app with minimal custom frontendA framework such as Apache Causeway
