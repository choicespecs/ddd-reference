    Concepts

    DDD fundamentals

    Domain-Driven Design is a way of organizing software around the business problem instead of around the database or the framework.

    What DDD actually is

    Eric Evans introduced DDD in Domain-Driven Design: Tackling Complexity in the Heart of Software (2003). It has two halves:

    Strategic designTactical design
    QuestionHow do we split a large problem into parts, and how do the parts relate?How do we write the code inside one part so the business rules are explicit and protected?
    ToolsSubdomains, bounded contexts, context maps, ubiquitous languageEntities, value objects, aggregates, repositories, domain services, domain events, factories
    Who's involvedDevelopers + domain experts + architectsMostly developers (with domain experts validating)
    In this repoStrategic designTactical patterns
    Common mistake

    Teams often adopt only the tactical patterns (put an Aggregate suffix on things, add repositories) and skip the strategic part. That gives you all the ceremony and almost none of the benefit. The biggest payoff comes from drawing the right boundaries and using the right words.

    The core idea in one paragraph

    Business software is hard because the business is complicated, not because Java or SQL is. So put the business rules at the center of the code, in plain objects named the way the business talks. Keep them free of HTTP, SQL, and framework concerns, so they can be read, tested, and changed on their own. Everything else (controllers, ORM, messaging, UI) is a plug-in around that core.

    Ubiquitous language

    The ubiquitous language is the shared vocabulary that developers and domain experts use in conversation, in tickets, in the UI, and in the code. When a domain expert says "a customer places an order", the code should say order.place().

    Database/CRUD language

    Java
    orderDto.setStatus(2);
orderDto.setPlacedTs(new Date());
orderService.update(orderDto);
inventoryService.decrement(itemId, qty);

    Ubiquitous language

    Java
    order.place(clock);
// raises OrderPlaced → Catalog reserves stock

    Practical rules for building the language:

    • Keep a glossary (this guide has one: Glossary). When a new word comes up in a meeting, add it.
    • Watch out for synonyms. If people say "client", "customer", and "account holder" for the same thing, pick one. If they mean different things, that's a sign of separate concepts, or even separate bounded contexts.
    • Rename code when the language changes. A class still called Ticket after the business switched to saying "Case" will confuse every new developer.
    • Name methods after business actions, not data changes: cancel(), approve(), reserve(), not setStatus().
    • Error messages are part of the language. "Cannot place an empty order" is better than "Validation failed: lines.size > 0".

    The domain model

    A domain model is a simplified picture of the business that is good enough for the problems this software solves. It does not try to mirror reality completely. The Catalog's Product knows its price and stock. It knows nothing about the product's weight, supplier, or marketing copy, because nobody here needs that yet.

    In code, the model consists of classes that hold both data and behaviour. Compare:

    Anemic model + transaction script

    Java
    // Data bag
public class Order {
  private String status;
  private List<OrderLine> lines;
  // getters + setters for everything
}

// Rules scattered in services
public void place(UUID id) {
  Order o = repo.findById(id).get();
  if (!o.getStatus().equals("DRAFT"))
    throw new RuntimeException("bad");
  if (o.getLines().isEmpty())
    throw new RuntimeException("empty");
  o.setStatus("PLACED");
  repo.save(o);
}
// …and another service forgets the
// empty check and calls setStatus too.

    Rich model

    Java
    public class Order {
  public void place(Clock clock) {
    requireStatus(DRAFT, "place the order");
    if (lines.isEmpty())
      throw new DomainException(
        "Cannot place an empty order");
    status = PLACED;
    placedAt = clock.instant();
    registerEvent(new OrderPlaced(…));
  }
  // no setStatus() exists — the only way
  // to reach PLACED is through place().
}

    The anemic version isn't wrong, and for simple CRUD it's fine. The problem is that the rule "only DRAFT, non-empty orders can be placed" can be bypassed by any code that holds an Order. In the rich model it cannot be bypassed. The class protects its own invariants.

    When DDD pays off and when it doesn't

    Use DDD (fully) when…Skip or go light when…
    The business rules are complex and change often (pricing, eligibility, workflows, scheduling, claims).The app is mostly forms over tables (admin screens, reference data).
    Several teams or departments use the same words with different meanings.One small team, one clear meaning for every term.
    The software is a competitive differentiator (core domain).It's a commodity you could buy off the shelf (generic subdomain).
    The system will live for years and be maintained by people who didn't write it.It's a prototype or a one-off script.
    Mix and match

    You don't have to choose one style for the whole app. A common, healthy setup is a rich DDD model for the core context (here, Ordering) and plain CRUD with Spring Data REST or simple controllers for supporting contexts (e.g. a "Reference data" context for countries and currencies).

    How DDD work actually happens

    1. Discover the domain together. Run an Event Storming session with domain experts: put orange sticky notes on a wall for every business event ("Order placed", "Payment captured", "Stock reserved").
    2. Find the boundaries. Look for clusters of events, and for words that change meaning. These become candidate bounded contexts.
    3. Model the core first. Find the commands, the aggregates that handle them, and the rules (invariants) each aggregate protects.
    4. Write the model as plain Java with unit tests before touching controllers or the database. See Testing.
    5. Add adapters: persistence, REST, UI.
    6. Refactor toward deeper insight. When a domain expert says something that doesn't fit the model, change the model. This is expected and healthy.

    Further reading

    • Learning Domain-Driven Design, Vlad Khononov (O'Reilly, 2021). The most approachable modern introduction; start here.
    • Implementing Domain-Driven Design, Vaughn Vernon (2013). The "red book": practical, Java-flavoured, with a deep treatment of aggregates.
    • Domain-Driven Design Distilled, Vaughn Vernon (2016). A short summary of everything.
    • Domain-Driven Design, Eric Evans (2003). The original "blue book". Read Part IV (strategic design) even if you skim the rest.
    • Effective Aggregate Design, Vaughn Vernon. Three free essays; the best material on sizing aggregates.
    • Get Your Hands Dirty on Clean Architecture, Tom Hombergs. Hexagonal architecture with Spring Boot, very close to this template.
