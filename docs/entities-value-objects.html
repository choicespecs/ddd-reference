    Modelling the objects

    Entities & value objects

    The DDD distinction between things with identity and things defined by their value decides how each object appears in the UI. Entities get their own pages; value objects become widgets inside them.

    The distinction

    Entity
    An object with a lasting identity. It stays the same object even as its attributes change. An Event renamed from "Summer Jam" to "Summer Jam 2026" is still the same event.
    Value object
    An immutable object defined entirely by its attributes, with no identity. Two Money(45.00, GBP) instances are interchangeable. It validates itself when it's created.

    How each one renders

    EntityValue object
    Own URL / page?Yes: /objects/Event/42No: it lives inside its owner
    When referencedA link to its page, plus a lookup to choose oneAn inline widget showing its value
    In a listA table row that opens the objectA formatted cell ("£45.00")
    EditingEdit its properties and invoke its actionsReplace the whole value through one widget
    NeedsAn id and a titleA parser/formatter, or a composite widget

    Type → widget mapping

    The renderer picks a widget from each property's type. This mapping is the heart of "creating a POJO creates the UI":

    Java typeJSON SchemaWidget
    String"type": "string"Text box (textarea if maxLength > 255)
    int, long, BigDecimal"integer" / "number"Number input with min/max
    boolean"boolean"Checkbox / toggle
    enum"enum": [...]Dropdown (or badge if read-only)
    LocalDate"format": "date"Date picker
    LocalDateTime, Instant"format": "date-time"Date-time picker
    Value object, e.g. Money"$ref": "#/$defs/Money"Registered custom widget (amount + currency)
    Value object, e.g. EmailAddress"format": "email"Text box with format validation
    Reference to an entity, e.g. Venue"format": "ref:Venue"Link + autocomplete lookup
    List<Entity>"type": "array"Table of rows linking to each object

    Value objects in code

    Value objects are the best way to make generated UIs smart. A raw BigDecimal price gives a bare number box. A Money value object gives a currency-aware widget that is formatted and validated in one place:

    Java
    @ValueType(widget = "money")                 // tells the renderer which widget to use
public record Money(BigDecimal amount, Currency currency) {
    public Money {
        Objects.requireNonNull(amount); Objects.requireNonNull(currency);
        if (amount.signum() < 0) throw new IllegalArgumentException("Money cannot be negative");
        if (amount.scale() > currency.getDefaultFractionDigits())
            throw new IllegalArgumentException("Too many decimal places for " + currency);
    }
    public static Money parse(String text) { … }   // "GBP 45.00" → Money
    @Override public String toString() { … }       // Money → "£45.00"
}

public record EmailAddress(String value) {
    public EmailAddress {
        if (value == null || !value.matches("^[^@\\s]+@[^@\\s]+\\.[^@\\s]+$"))
            throw new IllegalArgumentException("Not a valid email address");
    }
}

    Each value type needs a way to cross the wire: a parser and formatter (text in, text out) for simple values, or a JSON shape plus a custom widget for composite values like Money. Register each value type once, and every object that uses it gets the right widget.

    Entities in code

    An entity needs two things beyond its fields for the UI to work:

    • An identity that can go in a URL: /objects/Event/42.
    • A title, the human-readable name used in page headings, links and lookups ("Summer Jam 2026", not "Event#42").
    Java
    @DomainObject(title = "name")                // or implement a title() method
public class Venue {
    @Id private VenueId id;
    @Property @NotBlank private String name;
    @Property private String city;

    public String title() { return name + " (" + city + ")"; }   // "Riverside Arena (Leeds)"
}
    Rule of thumb

    If users talk about "this one" and expect to come back to it, it's an entity and gets a page. If users only care about what it is, it's a value and becomes a widget. Prefer value objects over primitives: every one you add makes the generated UI more specific with no UI code.
