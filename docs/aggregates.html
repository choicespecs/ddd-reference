    Tactical design

    Aggregates

    An aggregate is a cluster of objects treated as one unit for changes. It is the boundary inside which business rules must always hold. Sizing aggregates well is the hardest and most important tactical decision.

    Definition

    Aggregate
    A cluster of entities and value objects with a defined boundary and a single entry point, the aggregate root. Outside objects may hold references only to the root. All changes go through the root, which guarantees the aggregate's invariants after every operation.
    Invariant
    A business rule that must be true whenever the aggregate is saved. Example: "no seat in an event is held or sold to more than one buyer."

    The four rules of aggregate design

    Vaughn Vernon's rules from Implementing Domain-Driven Design are the best starting point:

    1. Model true invariants in consistency boundaries

    Put objects in the same aggregate only if a business rule requires them to be consistent at the same instant. "A seat can't be held twice" requires every seat allocation for an event to be checked together, so they belong in one aggregate. "An order's total should appear on the buyer's dashboard" doesn't need instant consistency. A few seconds of delay is fine.

    2. Design small aggregates

    Large aggregates load slowly, lock widely, and cause concurrency conflicts. If Event contained seats, holds, orders and reviews, every buyer during an on-sale would fight over the same row. Aim for a root plus a few values, and add more only when an invariant demands it.

    3. Reference other aggregates by identity

    Hold an EventId, not an Event object. This keeps boundaries clear, avoids accidentally loading and modifying huge graphs, and makes it possible to put aggregates in different databases or services later.

    Java
    public class Hold {
    private final HoldId id;
    private final EventId event;      // ✓ id reference
    private final BuyerId buyer;      // ✓ id reference
    // private Event event;           // ✗ object reference across aggregates
}

    4. Use eventual consistency outside the boundary

    Change one aggregate per transaction. When something else needs to react, such as releasing seats after a hold expires or issuing tickets after an order confirms, publish a domain event and handle it in a separate transaction.

    Ask the experts

    Whether a rule really needs immediate consistency is a business question. Ask "what would happen if this were true a few seconds later?" Experts often reveal the business has always tolerated delays, for example reconciling at the end of the day.

    Worked example: on-sale seating

    The invariant "no seat is held or sold twice" spans every seat in the event, so EventSeating is the aggregate. A Hold is a separate aggregate with its own lifecycle (pay, expire, cancel). They coordinate through events.

    Java
    public class EventSeating {                                   // aggregate root
    private final EventId id;
    private final Instant onSaleAt;
    private final Map<SeatId, SeatAllocation> seats;
    private final List<DomainEvent> events = new ArrayList<>();
    private long version;                                     // optimistic locking

    public HoldId hold(BuyerId buyer, SeatSelection selection, Instant now) {
        if (now.isBefore(onSaleAt)) throw new OnSaleNotOpen(id, onSaleAt);
        for (SeatId seat : selection.seats()) {
            SeatAllocation a = seats.get(seat);
            if (a == null)          throw new UnknownSeat(seat);
            if (!a.isAvailable())   throw new SeatUnavailable(seat);
        }
        HoldId hold = HoldId.newId();
        selection.seats().forEach(s -> seats.get(s).holdFor(hold));
        events.add(new SeatsHeld(id, hold, buyer, selection, now));
        return hold;
    }

    public void release(HoldId hold) {
        seats.values().stream().filter(a -> a.isHeldBy(hold)).forEach(SeatAllocation::release);
        events.add(new SeatsReleased(id, hold));
    }

    public void markSold(HoldId hold) {
        seats.values().stream().filter(a -> a.isHeldBy(hold)).forEach(SeatAllocation::sell);
    }
}

    Sizing trade-offs

    Too largeToo small
    Contention: concurrent users get optimistic-lock failuresInvariants can't be enforced, so you get race conditions across aggregates
    Slow loads; memory pressureMany cross-aggregate transactions (a sign the boundary is wrong)
    Hard to understand and testBusiness logic leaks into application services to coordinate
    Scaling the Fieldhouse example

    A stadium with 60,000 seats as a single EventSeating aggregate would bottleneck during an on-sale. The domain gives a way out: seats in different sections never conflict. Partition the aggregate as SectionSeating(eventId, sectionId), which still enforces "no seat twice" but spreads contention across many sections. The purchase limit spans sections, so it has to be enforced differently. Options include a small per-buyer BuyerAllowance aggregate updated first, or checking eventually and cancelling holds that go over the limit. Neither choice is purely technical; both are business trade-offs.

    Concurrency

    An aggregate is also the unit of locking. Two common strategies:

    • Optimistic locking (default): store a version number. A save fails if someone else saved first, and the caller retries or reports a conflict. This works well when conflicts are rare.
    • Pessimistic locking: lock the row on load. Use it sparingly for very hot, short operations.

    Frequent version conflicts are a design signal. Either the aggregate is too big or two unrelated use cases are sharing it.

    Aggregate design checklist

    • Can you name the invariant(s) this boundary protects?
    • Does every change go through a method on the root?
    • Are references to other aggregates by id only?
    • Does each use case modify exactly one aggregate instance?
    • Is it small enough to load, lock and test cheaply?
    • Are its internals (child entities) hidden from outside code?
