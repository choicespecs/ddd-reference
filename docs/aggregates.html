    Modelling the objects

    Aggregates

    An aggregate is a cluster of objects that changes together as one unit, with one root. In a generated UI, aggregate boundaries decide what goes on a page, what is nested inside it, and what is a link to elsewhere.

    Definition

    Aggregate
    A cluster of entities and value objects with a single entry point, the aggregate root. Outside code refers only to the root, and all changes go through the root, which keeps the business rules (invariants) true.

    In Fieldhouse, an Event and its PriceTiers form one aggregate. Tiers have no meaning without their event, and the rule "an event can't be published without at least one tier" spans both. A Venue is a separate aggregate that many events refer to.

    Model elementUI element
    Aggregate rootIts own page and URL, and an entry in the menu or list views
    Child entities and valuesShown inside the root's page as nested tables or groups, with no URL of their own
    Reference to another aggregateA link to that aggregate's page
    ActionsButtons on the root, including actions that change children (addTier, removeTier)

    Change children through the root

    A generic UI makes it tempting to let users edit any table cell directly. Don't expose child collections as freely editable. Model the operations as actions on the root, so the root can enforce its rules:

    Java
    public class Event {
    @Collection(label = "Price tiers", editable = false)   // displayed, not freely editable
    private final List<PriceTier> tiers = new ArrayList<>();

    @Action(label = "Add price tier")
    public PriceTier addTier(@NotBlank String name, @NotNull Money price, @Min(1) int capacity) {
        if (tiers.stream().anyMatch(t -> t.name().equalsIgnoreCase(name)))
            throw new BusinessRuleViolation("A tier called '" + name + "' already exists");
        var tier = new PriceTier(name, price, capacity);
        tiers.add(tier);
        return tier;
    }

    @Action(label = "Remove price tier")
    public void removeTier(PriceTier tier) { tiers.remove(tier); }
    public List<PriceTier> choices0RemoveTier() { return tiers; }   // dropdown of this event's tiers
    public String disableRemoveTier() {
        return status == EventStatus.ON_SALE ? "Tiers can't be removed once on sale" : null;
    }
}

    Reference other aggregates, don't embed them

    When Event refers to a Venue, it renders as a link plus a lookup, not as editable venue fields inside the event form. Editing the venue's address from an event page would silently change it for every other event at that venue. Each aggregate is edited on its own page.

    The lookup needs a list of candidates. Provide them with a convention method, or with a reference to a search endpoint in the metadata:

    Java
    public List<Venue> autoCompleteVenue(String search) {      // called once 2+ characters are typed
    return venues.findByNameContaining(search);   // feeds the venue lookup widget
}

    Keep aggregates small

    Large aggregates are a problem on screen as well as in the database. If Event also contained every hold, order and ticket, its page would try to load thousands of rows. Keep aggregates small. Show related aggregates as links or as a paged, read-only list loaded on demand (for example "Holds for this event" fetched from the Hold collection), rather than as nested children.
