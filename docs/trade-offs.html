    Trade-offs

    When a model-driven UI is a big win, when it gets in the way, and the security and performance issues to design for from the start.

    Where it fits

    Strong fit

    • Back-office, internal and expert tools: administration, operations, case management
    • Many entity types with lots of rules (insurance, ticketing, logistics, government)
    • Domains that change often, where hand-built screens can't keep up
    • Small teams that need a working UI quickly, such as prototypes that grow into products
    • Expert users who prefer direct access to objects over guided wizards

    Weak fit

    • Consumer-facing products where every pixel and flow is designed
    • Highly visual interfaces (maps, canvases, dashboards with charts)
    • Linear flows that cut across many objects (checkout, onboarding)
    • Domains with little behaviour, where a plain admin generator is enough
    • Teams whose designers expect full control over every screen

    A common and effective split: generate the back office, hand-build the customer-facing front. Both use the same domain objects and the same generic API.

    Benefits

    • Much less code. One class instead of entity + DTO + controller + form + table.
    • Consistency. Every screen behaves the same way, so users learn the app once.
    • Rules in one place. See Rules once, enforced everywhere.
    • Fast feedback on the model. Domain experts can click through a new concept the same day it's coded and correct the language.
    • Pressure toward good design. Anemic objects produce obviously poor UIs, which pushes behaviour onto the objects where it belongs.

    Costs

    • Generic look and feel. Screens look like the model. Good for experts, sometimes poor for occasional users.
    • The model becomes a UI contract. Renaming a field changes the screen and the API. That's intended, but it needs review and API versioning if external clients exist.
    • Framework learning curve, or the cost of maintaining your own introspector and renderer.
    • Edge cases need escape hatches. Plan for customisation from the start.

    Security

    A generic API that can reach any object is powerful, and dangerous if it's designed carelessly. Build these in from the beginning:

    RiskMitigation
    Exposing classes or methods that were never meant to be publicAllowlist: only @DomainObject types and explicitly annotated @Property/@Action members are reachable. Never expose a member just because it's public.
    Mass assignment: the client sets fields it shouldn't (status, price)Edit one property at a time through the spec. Reject non-editable properties. Never bind client JSON directly onto entities.
    Calling arbitrary methods by nameInvoke only Method handles captured in the registry at startup. Never call getMethod(nameFromRequest).
    Bypassing rules by calling the API directlyThe server re-runs hide/disable/validate on every request (see invoke).
    Insecure direct object references (reading someone else's object by id)Per-object authorisation in the generic loader (tenant, owner, role), not only per type.
    Leaking sensitive fieldsPer-member view permissions, applied when building the representation.
    Deserialisation attacksBind values by declared parameter type only; load references from repositories; no polymorphic type info from the client.

    Performance

    • Reflection cost: build specs and method handles once at startup; never reflect per request.
    • Supporting methods per row: computing disableX() for every action on every row of a 500-row table adds up. Compute member state only on the object page, not in list views.
    • N+1 queries: titles of referenced objects and collection rows can trigger many loads. Batch-fetch references, page collections, and use read-optimised queries for list views.
    • Large collections: never render an unbounded collection inline. Page it, or show it as a link to a filtered list.
    • Cache type metadata on the client (it changes only on deploy). Never cache instance representations.

    Related approaches

    ApproachDifference
    Admin generators (Django admin, Rails scaffolds, JHipster)Generate CRUD screens from the data model; usually little support for behaviour or actions
    Low-code platformsThe model is defined in a visual tool rather than in code; less control and versioning
    Server-driven UI (common in mobile apps)The server sends layout and components as JSON; focused on presentation rather than domain objects
    Hand-built UI over a rich domain modelClassic DDD: full control over screens, but much more code, and rules tend to get duplicated
