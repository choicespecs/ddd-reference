    Frontend

    Vue frontend

    Structuring a Vue 3 + TypeScript app to sit cleanly on top of a domain-driven backend, without re-implementing the domain in the browser.

    Principles

    1. The backend owns the rules. The UI may hint (hide the Place button on a placed order), but it never decides. It sends commands and displays the resulting state or error.
    2. Mirror the bounded contexts. features/catalog and features/ordering match the backend packages, so the language is the same on both sides.
    3. One API module per context, with functions named after the use cases (orderingApi.place(id)).
    4. Typed contracts. TS interfaces mirror the Java read models, and are ideally generated from OpenAPI.

    Folder structure

    frontend/ ├── index.html ├── vite.config.ts dev server :5173, proxy /api → :8080 ├── package.json └── src/ ├── main.ts createApp + router ├── router.ts routes grouped by context, lazy-loaded ├── App.vue shell: top nav per context ├── style.css ├── format.ts money(), dateTime() ├── api/ │ ├── http.ts fetch wrapper → ApiError(ProblemDetail) │ ├── types.ts Product, Order, OrderLine (mirror backend views) │ ├── catalog.ts catalogApi.list / create / changePrice / receiveStock │ └── ordering.ts orderingApi.start / addLine / place / cancel … ├── composables/ │ └── useAsync.ts loading / error / data wrapper └── features/ ├── catalog/ │ ├── ProductListView.vue │ └── NewProductForm.vue └── ordering/ ├── OrderListView.vue ├── OrderDetailView.vue └── StatusBadge.vue

    The API client

    TypeScript
    // src/api/http.ts
export class ApiError extends Error {
  constructor(public readonly problem: ProblemDetail) {
    super(problem.detail ?? problem.title)       // the domain's own message
  }
}

export async function http<T>(path: string, init: RequestInit = {}): Promise<T> {
  const res = await fetch(path, { ...init, headers: { 'Content-Type': 'application/json', ...init.headers } })
  if (!res.ok) throw new ApiError(await res.json().catch(() => ({ title: res.statusText, status: res.status })))
  return res.status === 204 ? (undefined as T) : res.json()
}
    TypeScript
    // src/api/ordering.ts — reads like the application service
export const orderingApi = {
  get:     (id: string) => get<Order>(`/api/orders/${id}`),
  start:   (customerEmail: string) => post<Order>('/api/orders', { customerEmail }),
  addLine: (id: string, productId: string, quantity: number) =>
             post<Order>(`/api/orders/${id}/lines`, { productId, quantity }),
  place:   (id: string) => post<Order>(`/api/orders/${id}/place`),
  cancel:  (id: string) => post<Order>(`/api/orders/${id}/cancel`),
}

    Why fetch and not axios? Fewer dependencies, and the wrapper is 20 lines. Axios is a fine choice if you want interceptors (auth token refresh) out of the box.

    State: composables vs Pinia

    The template keeps state local to views with a small composable:

    TypeScript
    // src/composables/useAsync.ts
export function useAsync<T, A extends unknown[] = []>(fn: (...args: A) => Promise<T>) {
  const data = shallowRef<T | null>(null)
  const loading = ref(false)
  const error = ref<string | null>(null)
  async function run(...args: A) {
    loading.value = true; error.value = null
    try { return (data.value = await fn(...args)) }
    catch (e) { error.value = e instanceof ApiError ? e.message : String(e); return null }
    finally { loading.value = false }
  }
  return { data, loading, error, run }
}
    Vue SFC
    <script setup lang="ts">
const { data: products, loading, error, run: load } = useAsync(() => catalogApi.list())
onMounted(load)
</script>
    OptionGood forNotes
    Local refs + composables (template)Page-scoped data; most CRUD and workflow screensSimplest; data is refetched on navigation
    PiniaState shared across many components/routes: current user, cart, feature flagsThe official Vue store; devtools support
    TanStack Query (vue-query)Server-state caching, background refetch, deduplication, paginationExcellent when many screens show the same server data
    TypeScript
    // If you add Pinia — a store per context, actions call the API module
export const useCartStore = defineStore('cart', () => {
  const order = ref<Order | null>(null)
  const itemCount = computed(() => order.value?.lines.reduce((n, l) => n + l.quantity, 0) ?? 0)
  async function add(productId: string) {
    order.value ??= await orderingApi.start(currentUser.email)
    order.value = await orderingApi.addLine(order.value.id, productId, 1)
  }
  return { order, itemCount, add }
})
    Don't mirror the aggregate in the store

    A store that recomputes totals or checks "can this be placed?" duplicates the domain, and the two copies will drift. Store the server's OrderView as-is and replace it with whatever the next command returns.

    Sending commands, rendering results

    TypeScript
    // OrderDetailView.vue — every command returns the new OrderView; just swap it in
const { loading, error, run: exec } = useAsync(async (command: () => Promise<Order>) => {
  order.value = await command()
})
const place  = () => exec(() => orderingApi.place(props.id))
const cancel = () => exec(() => orderingApi.cancel(props.id))
    Vue SFC
    <button v-if="order.status === 'DRAFT'" :disabled="loading" @click="place">Place order</button>
<p v-if="error" class="error">{{ error }}</p>   <!-- e.g. "Cannot place an empty order" -->

    Better: let the server say which actions are allowed

    The v-if="order.status === 'DRAFT'" check repeats a small piece of domain knowledge in the UI. For complex state machines, have the read model include the allowed actions:

    Java
    // backend
public record OrderView(…, Set<String> allowedActions) {}
// built from the aggregate: order.canPlace(), order.canCancel() …
    Vue SFC
    <button v-if="order.allowedActions.includes('place')" @click="place">Place order</button>

    Forms and validation

    • Use HTML attributes (required, min, type="email") for instant feedback.
    • Show server ProblemDetail messages for everything else. They come from the domain and are already user-readable.
    • For field-level server errors, extend GlobalExceptionHandler to add an errors: { field: message } property to the ProblemDetail for 400s, then map those messages next to the matching inputs.
    • For complex forms, libraries such as VeeValidate + Zod give schema-driven client validation.

    Keeping TypeScript types in sync

    Shell
    npm i -D openapi-typescript
npx openapi-typescript http://localhost:8080/v3/api-docs -o src/api/schema.d.ts
    TypeScript
    import type { components } from './schema'
export type Order = components['schemas']['OrderView']
export type Product = components['schemas']['ProductView']

    Add this as an npm script ("gen:api") and run it in CI. That way a backend change that breaks the frontend fails the build instead of failing in production.

    Dev server and the proxy

    TypeScript
    // vite.config.ts
server: { port: 5173, proxy: { '/api': 'http://localhost:8080' } }

    In the browser everything is same-origin (:5173), so there are no CORS preflights and no cookie headaches. The backend also has a CORS config (WebConfig) for when you point the frontend at the API by absolute URL.

    Testing the frontend

    • Vitest + @vue/test-utils for components and composables. Mock the API modules, not fetch.
    • Playwright for a handful of end-to-end flows against the real backend ("create order → add line → place").
    TypeScript
    // Example Vitest test for useAsync
import { useAsync } from '@/composables/useAsync'
import { ApiError } from '@/api/http'

it('exposes the ProblemDetail message', async () => {
  const { error, run } = useAsync(() => Promise.reject(new ApiError({ title: 'x', status: 409, detail: 'Cannot place an empty order' })))
  await run()
  expect(error.value).toBe('Cannot place an empty order')
})
